# 작업 계획 — 진행 상황 통제 문서

> **이 파일과 [`HANDOFF.md`](../HANDOFF.md) 둘이 한 쌍이다.**

> 이 파일은 **앞으로 무엇을 어느 순서로 하는가**(진행 통제)를 적는다.

## 0. 이 문서를 쓰는 법

### 새 세션을 열 때

**전문은 [`HANDOFF.md`](../HANDOFF.md) 맨 위의 「새 대화를 여는 프롬프트」에 있다.** 요지는 이렇다.

```
SamChess 작업을 이어간다. 먼저 이 두 문서를 순서대로 읽어줘.

1. HANDOFF.md 전체 — 현재 상태의 정본
2. docs/작업계획.md — 진행 통제. 「지금 어디까지 왔는가」가 §2 표에 있다

읽고 나서 상태를 확인해줘:
  npm run extract && npm run typecheck && npm test

그다음 §2 표에서 **아직 ⬜인 가장 위 세션**을 골라 진행한다.
설계안을 먼저 보여주고, 내가 확인하면 구현으로 넘어가자.
```

### 세션을 마칠 때 — **반드시** 이 넷을 한다

1. **§2 표의 상태를 갱신한다** (⬜ → ✅). 부분만 됐으면 🔶로 두고 §3의 해당 항목에 **어디까지 됐는지** 적는다
2. **§4 「열린 질문」에서 답이 나온 것을 §5 「결정 로그」로 옮긴다**
3. 규칙·수치·계약이 바뀌었으면 **`Design/GDD.md`와 `HANDOFF.md`에도 반영한다** — 이 파일은 계획이지 사양이 아니다.
   다시 밟으면 안 될 것은 **`CLAUDE.md`**에도 한 줄 남긴다
4. **`history/{날짜}_{제목}.md`에 「왜 그렇게 정했고 어디서 넘어졌는가」를 남긴다** —
   이 파일들과 역할이 갈린다. 여기는 **지금**, `history/`는 **그때**다

> **이 파일이 사양의 출처가 되면 안 된다.** 확정된 것은 GDD로, 굳은 계약은 HANDOFF로 간다.
> 여기 남는 것은 「순서」와 「아직 안 정해진 것」뿐이다.

### B — 레벨/스킬 관리 · 재설계 (39쪽) ⬜ ★ 저장 형식 v2

**여기가 형식 변경의 진짜 자리다.** 지금 모델은 레벨과 선택이 1:1로 대응하지 않는다.

```
지금   statPicks: ['hp','hp','at']        길이 = level - 1
       tactics:   ['공포','화계','진화']   ← Lv6·7이 둘씩 들어와 길이가 어긋난다
```

그래서 「Lv7을 Lv5로 내려라」(E)를 정확히 자를 수 없다. 레벨별로 묶는다.

```ts
/** 레벨업 한 번에 고른 것. growth[0]이 Lv1→Lv2다. 길이 = level - 1 */
growth: { stat: StatPick; tactics: TacticId[] }[]
```

- **레벨 하향 = `growth.slice(0, cap - 1)`**, 재설계 = 스택을 비우고 처음부터
- 파생 함수 `statPicksOf(inst, cap?)` · `tacticsOf(inst, cap?)`를 meta에 두고
  **화면도 편성도 엔진도 이 둘만 부른다**(단일 출처). `toRosterEntries`가 평탄화하므로
  **룰 엔진은 안 건드린다**
- `loadProfile`을 **버리기에서 채워 넣기(마이그레이션)** 로 바꾼다 — v1의 평면 배열을
  `tacticsForLevel()`로 되접는다. 지금은 버전이 다르면 계정을 통째로 버리는데,
  부대와 전적이 쌓이기 시작하면 아프다
- **레벨 관리 화면** — 스탯 찍은 횟수 · `HP 10 → +5 15` 증분 미리보기 · 책략 택1 + 설명 · [확정]/[뒤로]
- **재설계(둔갑천서)** — 레벨 유지, 스택을 비우고 Lv2부터 순서대로 다시 고르는 마법사.
  **[확정] 전까지 프로필에 반영하지 않는다** (중간에 나가면 원래대로)

**완료 조건** — v1 프로필이 v2로 정확히 되접히는가 · `growth.length === level - 1`이 항상 참인가 ·
재설계 결과가 같은 레벨의 정상 성장과 구별되지 않는가 ·
**`slice`로 자른 Lv5가 진짜 Lv5 캐릭터와 같은가**(E의 전제를 여기서 미리 고정한다).

### C1 — 전적 · 보상 개편 (40쪽 + 45쪽 보상표) ⬜ ★ 저장 형식 v3

전적과 보상이 [`rewards.ts`](../packages/meta/src/rewards.ts)의 `applyBattleResult` 한 함수에 있어 같이 연다.

**전적**

```
OfficerInstance.record  →  기물별 × 모드별. 온라인만 카운트
PlayerProfile.record    →  도시 전적 (C2가 쓴다)
```

- **AI 대전에도 전적을 올리던 것을 고친다** — 45쪽 「전적 기록을 하지 않습니다」가 정본이다.
  지금 `applyBattleResult`는 `opponent`와 무관하게 `record`를 올린다
- 「적격파」 = **적 격파(kills)**. 캐릭터마다 몇 명을 퇴각시켰는지 온라인에서만 센다

**보상** — `BattleOutcome.won: boolean` → `result: 'win' | 'draw' | 'lose'`

> 엔진은 **이미 진짜 무승부를 낸다** — `time 6000`에서 HP 합계까지 같으면
> `winner: null, outcome: 'draw'` ([`state.ts:307`](../packages/rules/src/state.ts#L307), 실측 0.02%).
> 그걸 메타 층이 `boolean`으로 뭉개고 있었다. 새 보상표가 무승부를 요구하니 여기가 먼저 열린다.

| | 카드 | 재료 | 군량 |
|---|---|---|---|
| 승리 | 1장 (등급은 아래) | 1 | 3v3 **1** / 5v5 **2** |
| 무승부 | **셋 중 택1** — 결과 화면에서 고른다 (양쪽 다) | | |
| 패배 | — | — | 승리와 **같은 양** |

- **AI 대전은 승리 시 군량만**, 모드별 1/2
- 무승부 택1은 **고르기 전까지 계정에 반영하지 않는다**

**카드 등급 — 전투력 격차 보정 (신규, §5-9)**

```
gap = 상대 전투력 − 내 전투력      (양수 = 내가 열세)
열세가 클수록 좋은 등급
```

- 구간 경계와 상한은 **D의 분포를 보고 정한다.** 지금 숫자를 적으면 실측 없이 굳는다
- 「팀에 D급이 몇 명」(GDD §6.4 옛 표)은 **버린다** — 상대를 안 보는 것이 문제의 원인이었다
- **온라인 전용** (AI는 카드가 없다)

**완료 조건** — 세 결말 × 두 모드 × AI/온라인 12조합이 표와 일치 ·
**동일 전투력끼리 붙으면 어느 쪽이 이겨도 같은 등급**(옛 규칙이 깨지던 자리를 회귀로 박는다) ·
기물별 합 = 총합 · AI 대전이 전적·카드·재료를 하나도 안 건드림.

#### 온라인 매칭의 군량 프로세스 (§5-15·§5-16) ★

「다시 찾기」는 **매칭 거절 패널티**다. 취지는 **거절당하는 쪽을 지키는 것** —
상대가 계속 거절만 당하지 않도록 **거절하는 쪽**이 군량 **−1**을 낸다.

> 45쪽 목업 글자는 **「다시 찾기 (군량 3소모)」**이지만 **−1로 확정됐다.** 화면 문구는
> **「다시 찾기 (군량 1소모)」**로 적는다. 목업과 갈리는 자리라 여기 남긴다.

**참가비는 여전히 기물 수만큼이다** — `grainCost(mode)` = 3v3 **3** · 5v5 **5**
([`roster.ts`](../packages/meta/src/roster.ts)). 거절 −1은 **그 위에 얹히는 별도 지출**이라,
거절하려면 참가비를 남겨 둔 채로 낼 수 있어야 한다. 그래서 경계가 이렇게 갈린다.

| 잔여 군량 | 출전 | 거절 |
|---|---|---|
| `< cost` | ✕ 불가 | — |
| `= cost` (3v3 **3** · 5v5 **5**) | ○ | **✕ 불가 — 매칭된 상대와 반드시 싸운다** |
| `> cost` | ○ | ○ (거절할 때마다 −1) |

**군량 체크는 「상대를 찾는 화면」으로 넘어가기 전에 한다.** 딱 최소면 안내문을 먼저 띄우고
**[확인]을 받은 뒤에** 매칭을 시작한다 — 들어간 뒤에 「거절이 안 된다」를 알면 늦다.

```
「대전을 위한 최소군량만 있을 때는 상대 매칭 시 거절을 할 수 없습니다.」
                                                        [확인] [취소]
```

- **거절을 반복하면 바닥에 닿는다.** `−1`씩 줄다 `cost`에 이르면 그때부터 거절할 수 없으니,
  **매칭 화면 안에서도 [다시 찾기]가 사라져야 한다** — 진입 전 안내문만으로는 못 막는 자리다
- **AI 대전에는 이 프로세스 전체가 없다.** 상대를 「생성」하는 것이라 거절당하는 상대가 없다.
  AI는 예전처럼 `grain >= cost`만 본다
- 매칭은 서버가 붙어야 진짜로 돌므로, F는 **버튼·안내문·군량 차감까지** 만들고
  「다시 찾기가 실제로 다른 상대를 물어 온다」는 **Colyseus 세션**이 잇는다

**출전 군량은 [전투준비]에서 낸다.** 지금은 편성 화면의 「출전」에서 내지만
(`spendGrain`), 위 표가 **참가비를 내기 전의 잔여 군량**을 기준으로 갈리므로
차감 시점이 매칭 뒤로 옮겨진다. 매칭만 하고 안 싸웠는데 참가비를 떼면 거절 −1과
이중으로 물리기도 한다.

> **판정은 `@samchess/meta`에 둔다** — `canDeclineMatch(profile, mode)` ·
> `MATCH_DECLINE_GRAIN = 1`. 화면이 `grain > cost`를 다시 적으면 참가비가 바뀌었을 때
> 조용히 어긋난다. 「화면이 미리 보여 주는 숫자는 엔진이 낸다」와 같은 결이다.

> **이 순서의 근거는 2026-08-04에 순서를 뒤집었던 것과 같다** — 서버가 반드시 검증해야 할 것
> (부대·전투력·매칭 기준)을 오프라인에서 굳혀 두면 프로토콜을 두 번 손대지 않는다.

**완료 조건** — 세 갈래가 각각 옳은 다음 화면으로 가는가 · AI 상대가 **내 부대와 가까운
전투력**으로 뽑히는가 · **`grain === cost`에서 안내문이 뜨고 [다시 찾기]가 아예 안 나오는가**
(3v3 3 · 5v5 5를 각각) · **거절을 반복해 바닥에 닿으면 화면 안에서 [다시 찾기]가 사라지는가** ·
참가비가 **[전투준비]에서만** 나가는가 · 온라인 갈래가 **상대를 못 찾아도 화면이 막히지
않는가**(뒤로 가기가 산다).
