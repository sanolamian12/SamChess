# 시스템 엔지니어 — W04 · 2026-08-23 ~ 08-29

> **이번 주 요지** — `packages/meta`에 가챠 모듈(`gacha.ts`)이 생겼다: 25,200장 배열을 저장하지 않고 `{seed, drawn}`만 들고 같은 시드로 다시 섞는 구조, 그 위에 골드 검증·지급을 묶은 구매 계층. 도시 이름 변경 규칙(`canRenameCity`/`applyRenameCity`)과 랭킹 행을 만드는 순수 함수(`ranking.ts`, 서버·클라 공용)가 더해졌고, 부대에 처음으로 전적(`Squad.record`)이 붙었다. 데이터 쪽에서는 `ECONOMY`의 가챠 필드를 새 모델로 바꾸고, 인물 서사(G1)를 `sam_people.csv`에서 10개 언어 맵으로 추출하게 했다.

## 메타 시스템

### `gacha.ts` 신설 — 유한 배열 가챠 (08-24)
- 함수: `gachaSlotsPerOfficer()` · `gachaDeckBase()` · `shuffledGachaDeck()` · `drawGacha()`.
- **슬롯 수는 계산한다**: `gachaSlotsPerOfficer()` = `cardsSpentOn(GROWTH.maxLevel)`(기존 함수, `growth.json`이 정본) × `economy.json`의 `gachaSlotMultiplier`. `growth.json`이 바뀌면 슬롯 수도 따라간다 (→ 결정·교훈 참조).
- **배열을 저장하지 않는다**: `PlayerProfile.gachaPool?: {seed, drawn}` 정수 둘만 저장하고, 필요할 때마다 `shuffle({seed, rngCursor: 0}, deck)`(`packages/rules/src/rng.ts`)으로 같은 순서를 다시 만들어 `drawn`개를 건너뛴다 — 전투 리플레이가 로그 대신 `seed`·`rngCursor`만 들고 다니는 것과 같은 패턴이다. 배열을 통째로 저장·복원하면 「재접속마다 다시 섞지 않는다」를 지키는 코드를 매번 새로 써야 하고 용량도 계정마다 수만 항목이다.
- **시드는 호출자가 준다**: `drawGacha(profile, count, newSeed)` — 계정에 이미 `gachaPool`이 있으면 `newSeed`는 무시된다(재접속마다 안 섞이는 것과 같은 이유). `applyBattleResult(profile, outcome, seed)`가 보상 카드 추첨에 쓰던 자리와 같다. 첫 구현은 `Date.now()`/`Math.random()`으로 시드를 자체 생성했다가 고쳤다 (→ 결정·교훈 참조).
- **소진은 값으로 알린다**: 요청 수보다 적게 나오면 `RangeError` 대신 `exhausted: true`와 함께 있는 만큼만 돌려준다.
- **저장 형식 버전은 안 올렸다** — 필드 추가일 뿐 기존 필드의 뜻이 안 바뀐다(`squads`·`grainAt`과 같은 자리).
- 회귀 12건 (→ QA).

### 가챠 구매 계층 — `buyGacha()` (08-24)
`gacha.ts`에 `gachaPullCost()` · `canAffordGacha()` · `buyGacha()`를 더했다. 골드 검증 → `drawGacha()`(배열 소비) → `addCard()`(기존 `profile.ts`, 지급)를 한 함수로 묶었다. 「화면이 판정하지 않는다」를 상점에도 적용한 것이다 — 화면은 `canAffordGacha()`로 버튼을 잠그고 눌리면 `buyGacha()`를 부를 뿐이며, **최종 골드 검증은 그 함수 안에서 다시 한다**(버튼이 잠겨 있어도 호출 경로가 하나 더 있으면 거기서 다시 확인해야 한다 — 전투 UI가 `validate()`를 다시 묻는 것과 같은 결). 회귀 3건 추가.

### 도시 이름 변경 규칙 (08-25)
- `types.ts`: `PlayerProfile.cityNameChangedAt?: number` (없으면 한 번도 안 바꾼 것).
- `profile.ts`: `CITY_RENAME_GOLD`(= `RESPEC_GOLD`), `RENAME_COOLDOWN_MS`(3일), `CITY_NAME_MAX`, `canRenameCity(profile, name, nowMs)` / `applyRenameCity(profile, name, nowMs)`. `syncGrain`·`applyCityUpgrade`와 같은 규약으로 `nowMs`를 인자로 받는다 — meta는 시계를 스스로 안 읽는다. 화면은 `canRenameCity()`가 낸 실패 사유를 그대로 띄운다.
- `migrate.ts`: `cityNameChangedAt`을 되접기에서 놓치면 서버가 매 `GET /profile`마다 재구성하는 되접기에서 조용히 사라져 쿨다운이 무의미해진다. `exactOptionalPropertyTypes` 때문에 `undefined`를 직접 대입할 수 없어 **조건부 스프레드**로 넣었다.
- 그 대조 중에 **`gachaPool` 필드가 `migrate.ts`에서 아예 되접히지 않는 것**을 발견했다 — 이번에 고치지는 않았다 (→ 결정·교훈 참조).

### 랭킹 행 계산 `ranking.ts` · 부대 전적 (08-27)
- `packages/meta/src/ranking.ts`(신설) — `cityRankRow` / `squadRankRows` / `officerRankRows` 세 함수가 **서버(전체 유저 스캔)와 클라(내 프로필 하나)에서 똑같이** 쓰인다. 「내 랭킹」은 클라이언트가 이 함수를 직접 돌려 만들므로 서버 왕복이 없다(§5-61과 같은 결 — 서버가 죽어도 내 것은 보인다).
- **부대에 전적이 없었다** — `Squad`에 `record`가 없어 이력(`matches[]`, 200줄에서 꼬리를 던다)에서 파생시키면 오래 쓴 부대일수록 통산이 조용히 줄었을 것이다. 계정 전적과 같은 패턴으로 `Squad.record`를 붙이고, `applyBattleResult()`가 `outcome.mySquad`(부대 **이름** — `BattleScreen.tsx`가 그렇게 싣는다)로 찾아 함께 올린다 (→ 결정·교훈 참조).
- **책략은 서버가 미리 계산해 싣는다** — 고유기술은 장수 고정값이라 클라이언트가 `skillById`로 직접 찾지만(레벨 무관), 책략은 계정마다 달라 `OfficerRankRow.tactics`에 `tacticsOf()`로 계산해 넣는다.
- 부대 「전투력」 열용으로 `squadDisplayPower()`(등급 점수 × 레벨의 합, 계수 없음)를 만들었다가 열이 빠지며 함수째 제거했다.
- **장수 랭킹 모드 필터**(둘째 세션): `officerRankRows(profile, filter, mode?)`가 선택적 모드 인자를 받는다 — `mode`가 있으면 `sumTally(inst.record, {...whereOf(filter), mode})`로 직접 계산하고, 없으면 기존 `totalTally()` 그대로다. 도시·부대 랭킹과 같은 구조가 됐다.
- **언어별 서사 맵을 그대로 나른다**: `OfficerRankRow`가 `courtesyName`/`story`의 언어별 맵 전체를 싣는다 — meta는 「지금 UI 언어가 뭔지」 모른다. 고르는 자리는 클라이언트의 `pickStory()`다.
