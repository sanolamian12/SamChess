## L-02-06 | ALL,CLI | 스모크 자리 확인은 DOM 속성이 아니라 실측 좌표(`getBoundingClientRect`·`elementFromPoint`)로 한다
- 상황: 커맨드 패널이 좌상단에 눌러앉았는데 `data-x="right" data-y="bottom"`이 붙어 있어 「자리는 맞다」고 보고 엉뚱한 곳을 뒤졌다. 책략 대상 칸 위에 「취소」 버튼이 떠 있어 클릭이 막힌 것도 `elementFromPoint`로 찍고서야 보였다.

## L-02-36 | SYS | 데이터(DSL)만 보고 동작을 판단하지 말고 스크립트 핸들러까지 확인하며, 대조 스크립트도 본 파이프라인과 같은 정규화를 거치게 한다
- 상황: 한 고유기술은 DSL만 보면 적에게만 강제 표적 상태가 걸려 시전자 쪽 예외를 만들려 했는데, 스크립트 핸들러가 이미 시전자에게도 같은 상태를 걸고 있었다. 또 다른 기술 이름 어긋남은 대조 스크립트가 이름 정정 표를 안 거쳐서 생긴 착시였다.
- 왜 조용했나: 데이터와 코드 두 곳에 동작이 나뉘어 있으면 한쪽만 읽은 결론도 그럴듯하다.
- 규칙: 데이터 구동 시스템에서는 데이터 + 예외 핸들러를 함께 읽고 판단한다. 검증용 스크립트는 본 추출기와 같은 정규화 단계를 공유해야 착시 차이를 만들지 않는다.
- 날짜: 08-14

## L-02-37 | GD,SYS | 이미 코드에서 뜻이 정해진 이름을 다른 개념에 다시 쓰지 않는다 — 같은 대상이라도 층이 다르면 이름도 가른다
- 상황: 엑셀 시트 이름 「오라매핑」의 그림 층을 「오라」로 부르면, 엔진의 「오라」(여포·허저의 반경 판정)와 섞여 「여포의 오라」가 시전자 표식인지 반경 안 적이 보는 그림인지 말할 수 없었다(실제로 다른 그림이다). 그래서 그림 층은 `visualEffect`로 불렀다. 같은 결로 성지 칸의 지형 그림(「여기가 성지다」)과 유닛의 링(「이 유닛이 효과를 받는 중」)은 같은 사실을 두 번 그리는 것 같아도 다른 층에 둔다.
- 규칙: 용어 충돌은 원본(엑셀) 이름을 바꾸지 말고 코드 쪽 이름을 갈라 문서에 「이 이름은 언제나 이 뜻」으로 적는다. 칸에 붙는 것과 유닛에 붙는 것은 다른 컨테이너에 둔다.

## L-02-39 | DSN | 배경 세기 조정은 화면에 막을 덮지 말고 굽는 단계에서 누르고, 한 장 띠는 칸마다 잘라 굽는다
- 상황: 반투명 막으로 판을 덮는 것이 가장 쉬웠지만 하이라이트·기물까지 뿌예져 기각하고 지도 세기는 굽는 단계에서 눌렀다. 시간대 배경 띠는 CSS `background-position`으로 한 장에서 잘라 쓰지 않고 칸마다 잘라 JPG로 냈다(PNG 25MB 이상 → JPG 4.2MB).

- 규칙: 표시 조정은 가능한 한 에셋 파이프라인에서 끝내 런타임 레이어를 늘리지 않고, 같은 사실(칸 수)을 두 곳에 적게 만드는 방식은 피한다.
