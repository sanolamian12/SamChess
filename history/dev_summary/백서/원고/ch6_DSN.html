디자인 엔지니어

그림을 화면에 올리고, 화면이 그림대로 보이게 만드는 사람

이 장은 에셋 파이프라인(원본 그림을 게임이 읽는 파일로 굽는 도구)과 화면 스타일(CSS)을 맡는 사람을 위한 것이다. 이 자리에서 나는 실수는 거의 다 오류 메시지가 없다. CSS는 규칙이 지거나 아예 안 걸려도 경고하지 않는다. 굽기 도구는 「몇 장 만들었다」만 말하고, 잘 만들었는지는 말하지 않는다. 이미지 처리는 수치가 정상이어도 그림이 깨질 수 있다. 그래서 주니어가 가장 자주 조용히 틀리는 것은 「봤으니 됐다」고 믿는 일이다. 이 장의 원칙은 대부분 「무엇을 재고, 어디서 보고, 무엇을 구조로 막을 것인가」다. 사례는 웹·모바일로 내는 턴제 전술 게임(체스 기물처럼 움직이는 캐릭터 260명, 가챠와 캐릭터 육성, 열 개 언어)을 두 달 동안 만들며 실제로 밟은 것들이다.

이 장의 원칙

  1. 새 화면의 클래스는 처음부터 화면 접두사로 시작한다
  2. 덮어쓸 규칙의 세기는 :not() 안까지 세고, 이겼는지는 계산된 값으로 확인한다
  3. 단축 속성이 무엇을 초기화하는지 기억한다
  4. 화풍을 그림 테두리로 바꾸면 상태 표시를 처음부터 다시 만든다
  5. 쌓임 맥락과 CSS 애니메이션은 다른 효과를 오류 없이 지운다
  6. 잘리면 안 되는 것은 flex 비율에 맡기지 말고 구조로 지킨다
  7. 트랙 폭은 내용이 아니라 틀에 못 박고, 「이 칸만 넓다」면 min-width: auto부터 의심한다
  8. 오버레이는 컨테이너 밖에 그리고, 크기가 이상하면 기준 조상부터 센다
  9. 빈 요소와 띄운 판은 클릭을 통과시킨다
  10. 단추 이름은 접히지 않게 하고, 긴 글자는 가장 싼 쪽에서 흡수한다
  11. 크기 지정은 눈대중으로 환산하지 말고 실측한 상자에 곱한다
  12. 스프라이트의 위치값은 프레임 경계에서 계산하고 찍어서 확인한다
  13. 줄여서 맞춘 값과 이유가 걸린 값은 이유가 사라지면 함께 지운다
  14. 고치기 전과 후를 재서, 수정이 정말 무언가를 바꿨는지 확인한다
  15. 정보가 가장 많은 원본을 받고, 화면이 이상하면 파이프라인을 거꾸로 짚는다
  16. 저장 형식은 런타임이 소비하는 방식과 대상 플랫폼으로 고른다
  17. 표시 조정과 정규화는 런타임이 아니라 굽는 단계에서 끝낸다
  18. 파라미터를 고치면 전체를 다시 굽고, 건너뛰기는 존재가 아니라 내용으로 판단한다
  19. 굽기 도구는 자기 이름만 지우고, 경고는 측정값으로 내고, 짝이 될 경고는 나란히 찍는다
  20. 그림 시트는 등분하지 말고 픽셀로 경계를 찾고, 찾은 수를 단언한다
  21. 표본은 대표값 하나로 접지 말고, 임계값은 정상값의 최댓값을 재고 정한다
  22. 한 축에서 상충이 풀리지 않으면 다른 축을 찾고, 틀림의 무늬를 본다
  23. 자기 출력을 다시 넣는 단계와 정답 표본은 둘 다 의심하고 잰다
  24. 자동 처리는 다수에 맞추고, 예외는 표시와 수동 통로로 처리한다
  25. 다른 바탕에 올릴 소재는 가장자리와 그림자를 다시 만든다
  26. 투명 이미지는 모든 바탕 위에서, 크게, 극단 표본으로 보고 판단은 픽셀 통계로 한다
  27. 꽉 채우는 그림은 가장 큰 프레임에서, 에셋이 다 온 뒤에 본다
  28. 「안 보인다」「폰트가 다르다」는 굵기·색보다 좌표계를 먼저 본다
  29. 장식 효과는 결정적으로 만들고, 불변 성질은 좌표로 검사한다
  30. 목업은 결함을 찾는 데 쓰고, 느낌은 실제 화면에서 판단한다

6.1 CSS는 틀려도 말하지 않는다

CSS에는 컴파일 오류가 없다. 이름이 겹쳐도, 세기(specificity, 어느 규칙이 이기는지 정하는 점수)에서 져도, 단축 속성이 다른 값을 지워도 브라우저는 다른 규칙을 조용히 적용한다. 타입 검사와 테스트는 전부 통과하고, 화면을 직접 봐야만 안다. 우리는 같은 종류의 사고를 한 주에 다섯 번씩 냈다. 막는 방법은 셋이다. 이름 규약, 세기 계산, 그리고 계산된 값(getComputedStyle)을 읽는 검사.

새 화면의 클래스는 처음부터 화면 접두사로 시작한다

전역 CSS에 .panel·.card·.bar·.head 같은 흔한 이름을 새로 쓰면, 어딘가에 이미 있는 같은 이름의 규칙이 끼어든다. 새 화면은 .shop-·.inv-처럼 화면 접두사로 시작하고, 접두사 뒤에도 head·row 같은 흔한 낱말은 피한다. 접두사를 붙여도 같은 파일 안에서 겹칠 수 있고, 뜻이 같다고 같은 이름을 쓰면 그냥 겹친다. 여러 화면이 함께 쓰는 범용 클래스(팝업 .modal, 선택지 .opt 등)에 새 화풍을 입힐 때는 .modal[data-modal="settings"]처럼 속성 선택자로 좁힌다.

사례 · 이름 충돌

무슨 일이 새 메뉴 화면의 판때기에 .panel을 붙였더니, 전투 화면의 플로팅 명령 패널 규칙(position: absolute, 폭은 판 크기의 3/8)이 먹어 판때기가 오른쪽 아래에 좁게 붙었다. 사흘 전에도 같은 이름이 다른 옛 규칙(position: relative)과 부딪혀 패널이 좌상단에 붙은 적이 있었다. 같은 이름이 두 번 사고를 냈다. 왜 조용했나 이름이 겹쳐도 CSS는 오류가 없고 테스트도 통과한다. 잡은 방법 화면을 직접 보고 찾았다. 이후 실제 좌표를 재는 스모크 테스트(실제 화면을 띄워 끝까지 눌러 보는 자동 검사)를 넣었다.

사례 · 접두사 안의 충돌

무슨 일이 캐릭터 목록 화면에서 접두사를 붙인 -head 클래스 하나를 표 머리(grid)와 상세 머리(flex)에 함께 써서 한쪽이 무너졌다. 같은 주에 도시 관리 화면을 만들며, 메인 화면에 이미 있는 「도시」 클래스와 뜻이 같다고 같은 이름을 쓰려다 멈췄다. 잡은 방법 표 머리와 상세 머리에 서로 다른 이름을 주고, 도시 관리 화면에는 별도 접두사를 붙였다.

덮어쓸 규칙의 세기는 :not() 안까지 세고, 이겼는지는 계산된 값으로 확인한다

화면 단위로 넓은 화풍 규칙을 깔면, 그 뒤에 쓰는 예외는 세기를 넘겨야 이긴다. :not() 안의 클래스도 세기에 들어간다. button.x { font: inherit } 같은 리셋 규칙(요소+클래스)은 클래스 하나짜리 글자 크기 규칙을 이긴다. 세기가 같으면 파일 순서로 갈린다. 예외를 쓴 뒤에는 「덮었다」고 믿지 말고 getComputedStyle로 실제 값을 읽는다. 일부 요소만 멀쩡한 화면은 에셋 문제처럼 보이지만 대개 우선순위 문제다. 쪽 넘김 단추 같은 공용 부품은 넓은 규칙에서 처음부터 :not()으로 빼 둔다.

사례 · 화풍 교체

무슨 일이 목록 화면의 단추에 목판 그림을 입히는 규칙은 .screen-x .btn:not(.ghost):not(.primary), 클래스가 넷이다. 이것을 클래스 셋짜리 규칙으로 덮으려다 실패했다. 속성 선택자 한 칸이 더 붙어 우연히 이긴 [처음]·[마지막] 단추만 멀쩡했다. 왜 조용했나 일부만 정상이라 「그림 하나가 빠졌나」로 읽혔다. 잡은 방법 정상인 단추와 아닌 단추를 나란히 놓고 선택자 세기를 손으로 셌다.

사례 · 같은 주에 다섯 번

무슨 일이 팀 편집 화면에서 같은 사고가 한 주에 다섯 번 났다. 붉은 삭제 단추 .btn.del(0,3,0)이 화면 단위 규칙 .screen-y .btn:not(.ghost):not(.primary)(0,4,0)에 파일 순서와 상관없이 졌다. 그런데 주석에는 「순서로 갈린다」고 틀리게 적혀 있었다. 쪽 넘김 단추도 .btn이라 참나무 액자 그림에 갇혔고, 단추 요소의 font: inherit(0,1,1)가 목록 글자 크기(0,1,0)를 이겼다. 잡은 방법 공용 부품을 넓은 규칙에서 :not()으로 빼고, 예외를 쓸 때마다 계산된 값으로 승패를 확인했다.

단축 속성이 무엇을 초기화하는지 기억한다

border: 단축 속성은 border-image를 초기화한다. 9분할 이미지(그림을 아홉 조각으로 나눠 모서리는 그대로 두고 변만 늘리는 테두리, CSS border-image)를 입힌 클래스가 border:를 쓰는 클래스와 같은 세기로 겹치면, 파일에서 아래에 있는 쪽이 이겨 그림이 통째로 사라진다. 장식 그림을 입힌 요소는 선택자를 한 칸 세게 적어(.modal.done처럼) 겹침을 끊는다. 크기를 좁힐 때는 padding을 조절하고, 장식이 든 border-width는 건드리지 않는다. 요점이 되는 선언(display: inline-flex 등)에는 「이것이 빠지면 무엇이 무너진다」는 경고 주석을 단다.

사례 · 사라진 액자

무슨 일이 건물 증축 완료를 축하하는 팝업의 액자 그림이 통째로 사라졌다. 액자를 입힌 클래스 하나가 파일 아래쪽 범용 .modal의 border:에 졌다. 앞서 기술 설명 팝업에서 한 번 밟은 자리였다. 같은 주에는 이미 */로 닫힌 주석 뒤에 설명 세 줄을 덧붙였더니, 파서가 그 글과 바로 뒤의 규칙 하나를 한 덩어리로 삼켜 버렸다. 그 규칙의 inline-flex가 날아가 「글씨는 커졌는데 아이콘만 사라졌다」. 왜 조용했나 두 경우 모두 브라우저는 경고 없이 다른 규칙을 적용한다. 잡은 방법 스크린샷 눈검사로 증상을 보고 거꾸로 추적했다. 액자는 선택자를 두 클래스로 세게 적어 고쳤다.

화풍을 그림 테두리로 바꾸면 상태 표시를 처음부터 다시 만든다

테두리가 그림이면 border-color와 inset box-shadow는 아무 일도 안 한다. 9분할 그림의 fill(가운데 칸 채우기)이 안쪽 그림자도 덮는다. 리스킨(화풍 교체)을 하면 「선택됨」「눌림」 같은 기존 상태 표시를 전부 그림 교체나 필터 기반으로 다시 만들고, 눈 대신 계산된 값으로 확인한다. 스타일을 다른 자리로 옮길 때는 모양과 배색 변수를 한 묶음으로 옮긴다. 펼친 상태까지 화풍이 필요한 컨트롤은 네이티브 <select>가 아니라 버튼 + 뜨는 패널로 처음부터 만든다. 닫힌 상자만 CSS로 꾸며지고 펼친 목록은 OS가 그린다.

사례 · 리스킨

무슨 일이 팀 편성 화면을 그림 테두리로 리스킨하자 「고른 칸」을 표시하던 상태 규칙 넷이 전부 죽었고, 참나무 목판 위의 inset box-shadow도 보이지 않았다. 왜 조용했나 효과가 없어도 오류가 없다. 「눌렀는데 아무 표시가 없다」로만 남는다. 잡은 방법 getComputedStyle의 borderImageSource·filter·backgroundColor를 읽어 「고른 칩이 옥색인가」를 검사했다. 랭킹 화면의 필터 <select>도 같은 이유로 펼친 목록만 OS 모양이라 커스텀 드롭다운으로 바꿨다.

쌓임 맥락과 CSS 애니메이션은 다른 효과를 오류 없이 지운다

container-type·transform·isolation은 쌓임 맥락(stacking context, 자식들이 바깥과 따로 합성되는 묶음)을 만들고, 그 안의 mix-blend-mode는 바깥과 섞이지 못한다. 블렌드가 필요한 요소의 조상에는 이것들을 두지 않는다. CSS 애니메이션은 인라인 스타일을 이기므로, JS 시간표가 쥐는 속성(opacity 등)에는 CSS 애니메이션을 걸지 않는다. 마스크는 그림이 아니라 상자에 걸리므로, 마스크를 걸 상자는 그림 비율에 맞춘다.

사례 · 연출 합성

무슨 일이 두루마리가 펼쳐지는 연출에서 종이 요소에 건 container-type 때문에 장면의 블렌드가 두루마리가 아니라 투명한 바닥하고만 섞였다. 설명·라벨에 남아 있던 먹 번짐 CSS 애니메이션은 시간표 코드가 인라인으로 쥐는 opacity를 덮어 겹침 순서를 깨뜨렸다. object-fit: contain으로 생긴 여백에서는 마스크 경계가 딱딱하게 남았다. 잡은 방법 세 효과를 하나씩 끄고 켜며 원인을 갈랐다.

6.2 레이아웃 — 누가 줄고 누가 늘어나는가

flex와 grid는 공간이 모자라거나 남을 때 누구를 줄이고 누구를 늘릴지 기본값으로 정한다. 그 기본값(flex-shrink: 1, min-width: auto, 트랙 auto)은 여유 있는 화면에서는 아무 문제가 없다가, 내용이 넘치는 데이터·좁은 해상도·다른 인원 구성에서만 드러난다. 증상은 「글자가 없다」「그림이 크다」처럼 다른 곳의 문제로 보인다.

잘리면 안 되는 것은 flex 비율에 맡기지 말고 구조로 지킨다

세로 flex 안의 줄은 기본이 flex-shrink: 1이라, 영역이 얇아지면 필요한 높이보다 작게 눌린다. 내용이 잘리면 안 되는 자식에는 flex: none을 준다. 저장 단추처럼 절대 줄어들면 안 되는 것은 flex 비율 조정으로 지키지 말고, 스크롤 묶음과 바닥 판을 갈라 구조로 빼낸다. 비율을 만지면 잘리는 자리만 옮겨 다닌다. 검증은 여유 있는 기본 크기가 아니라 영역을 일부러 극단적으로 좁히거나 내용이 넘치는 데이터로 한다.

사례 · 사라진 글자

무슨 일이 전투 화면의 시스템 메시지 창에서 상자만 그려지고 글자가 사라졌다. 줄 높이가 필요한 19px보다 작은 15.5px로 눌려 있었다. 왜 조용했나 디버그 함수로 보면 줄은 다 들어 있었다. 상단 정보 표시(HUD)가 두꺼운 5대5 대전에서만 늘 났고 3대3은 멀쩡해서 「가끔 안 보인다」로만 보였다. 잡은 방법 기획자가 플레이 중에 발견했고, 해상도 셋에서 줄 높이를 실측했다. 스모크 테스트가 영역을 20px로 좁혀 그 성질을 지키게 했다.

사례 · 밀려난 저장 단추

무슨 일이 팀 편성 화면의 [등록 완료] 단추가 화면 밖으로 밀렸다. 첫 원인은 아무 규칙에도 안 걸린 클래스 낱말(grow) 하나였다. 고치자 리스킨 테두리가 다시 밀었고, 테두리를 줄이자 캐릭터 표가 0줄이 됐고, min-height를 옮기자 잘린 자리만 바뀌었다. 잡은 방법 캐릭터 44명을 가진 시험 계정을 심어 일부러 넘치는 상태를 만들어 재현하고, 바닥 판을 스크롤 묶음 밖으로 뺐다.

트랙 폭은 내용이 아니라 틀에 못 박고, 「이 칸만 넓다」면 min-width: auto부터 의심한다

grid의 줄·열을 auto나 max-content로 두면 내용이 틀을 정한다. 줄마다 제 grid를 갖는 목록은 줄마다 폭이 달라지고, 구성이 다른 화면은 한 구성에서만 넘친다. 줄은 minmax(0, 1fr), 열은 고정 폭으로 못 박는다. grid·flex 아이템의 기본값 min-width: auto는 nowrap인 긴 글자가 칸을 넓히게 만든다. 안쪽 요소에 min-width: 0을 줘도 조상 아이템이 auto면 소용없으므로, 아이템 자체에 준다. 증상을 에셋 탓으로 돌리기 전에 레이아웃 계산부터 본다.

사례 · 구성마다 다른 화면

무슨 일이 전투 화면 아래 캐릭터 카드 띠의 grid 줄이 auto라, 3대3에서만 카드가 띠를 넘어 HP·대기 시간·고유 스킬 줄이 잘렸다. 5대5는 우연히 높이가 맞았다. 왜 조용했나 5대5만 확인했다. 한 장면만 보면 통과한다. 잡은 방법 3대3을 열어 보고 「카드 높이 > 칸 높이」 스모크 검사를 넣은 뒤, 수정을 일부러 되돌려 검사가 실제로 실패하는 것까지 확인했다.

사례 · 커 보이는 그림

무슨 일이 장비 화면에서 방어구 그림이 커 보여서, 종류별 축소와 품목별 축소까지 두 라운드를 돌렸다. 진짜 원인은 grid 아이템의 min-width: auto였다. nowrap인 긴 이름이 그 열을 넓혔고, 같은 열을 쓰는 다른 줄까지 함께 넓어졌다. 줄마다 독립 grid인 다른 표에서는 단추 칸을 auto로 두자 단추가 없는 머리줄만 이름 칸이 넓어졌다. 잡은 방법 기획자가 「액자 자체가 옆 칸보다 넓다」고 짚었다.

오버레이는 컨테이너 밖에 그리고, 크기가 이상하면 기준 조상부터 센다

팝업을 position: relative가 걸린 판 안에 두면 판 크기만 한 팝업이 된다. 「자식 전부에 position: relative」 같은 상위 규칙(.screen > *)에 걸리면 화면 가운데가 아니라 내용 맨 아래에 흘러 붙는다. 오버레이는 조각(fragment)이나 포털로 컨테이너 밖, 화면 최상위 바로 밑에 그린다. 크기가 안 맞으면 CSS 숫자를 더 넣기 전에 inset: 0의 기준이 되는 조상이 누구인지 센다. 이름과 단추를 함께 가운데 두는 줄은 flex가 아니라 1fr auto 1fr 격자로 둔다. 검사는 「떠 있는가」와 「제자리에 있는가」를 따로 둔다.

사례 · 흘러내린 팝업

무슨 일이 배경 그림을 깐 화면 위의 팝업이 2주 전부터 화면 한가운데가 아니라 내용 맨 아래에 붙어 있었다. 배경 화면의 「모든 자식에 position: relative」 규칙이 팝업 뒷막의 absolute를 덮었다. 왜 조용했나 팝업 스모크 테스트는 「떠 있는가」만 봤다. 잡은 방법 가장 큰 프레임(700px) 눈검사로 찾고, 팝업이 프레임을 실제로 덮는지 좌표로 확인하는 검사를 더했다.

사례 · 판 안의 팝업

무슨 일이 캐릭터 육성 화면의 [이름 변경] 팝업을 판 안에 두자 판 크기만 해졌다. flex로 이름과 단추를 가운데 두자 단추가 이름을 52px 옆으로 밀었다. 잡은 방법 확인 도구가 좌표로 「제자리에 있는가」를 봤다. 팝업 안에서 또 팝업을 여는 중첩 모달의 기준 조상 문제는 → 5장 클라이언트 엔지니어에서 다룬다.

빈 요소와 띄운 판은 클릭을 통과시킨다

자리만 지키는 빈 요소나 판 위에 띄운 패널은 투명해도 그 아래 클릭을 삼킨다. 빈 자리 요소와 오버레이 컨테이너에는 pointer-events: none을 주고, 조작하는 요소만 auto로 둔다. 그림에 붙어야 하는 클릭 영역은 그림과 같은 층에 둔다. 브라우저 자동화의 실제 클릭·호버는 가로채기를 알려 주므로 좌표 검사보다 낫다.

사례 · 투명한 벽

무슨 일이 메인 화면의 빈 지도 자리 <div> 하나가 「배경 위 내용은 z-index 2」 규칙에 걸려 떠올랐다. 그 결과 z-index 0인 그림 층 안에 있는 건물 클릭 영역이 전부 막혔다. 왜 조용했나 투명한 빈 요소라 눈에 안 보이고, CSS는 오류를 내지 않는다. 잡은 방법 Playwright의 hover()가 「이 div가 포인터 이벤트를 가로챈다(intercepts pointer events)」고 알려 줬다.

단추 이름은 접히지 않게 하고, 긴 글자는 가장 싼 쪽에서 흡수한다

단추 라벨에는 white-space: nowrap을 기본으로 걸고, 길이는 설명문이 접히며 감당하게 한다. 안내문은 그것이 설명하는 단추 바로 밑에 둔다. 긴 번역 같은 극단값 하나 때문에 레이아웃 전체를 바꾸지 않는다. 레이아웃 조정, 콘텐츠(이름) 조정, 지정값의 미세 조정 중 가장 싼 쪽을 고르고, 지정값을 바꾸면 그 이유(몇 px 모자랐는지)를 남긴다. 다국어 화면 검사 방법은 → 5장 클라이언트 엔지니어를 본다.

사례 · 꺾인 단추 이름

무슨 일이 단추 라벨에 nowrap이 없어 「튜토리얼 시나리 / 오」로 꺾였다. 화면 끝에 몰아 둔 안내문은 어느 단추 이야기인지 알 수 없었다. 왜 조용했나 둘 다 오류가 없고, 가장 큰 프레임 눈검사에서만 보였다.

사례 · 다국어

무슨 일이 열 개 언어 중 긴 번역 이름 때문에 캐릭터 카드를 표로 바꿀지 고민했다. 결국 두 줄 + 글자 크기 조정으로 카드를 지켰고, 그래도 세 줄이 되는 두 언어(이탈리아어·몽골어)는 번역 이름을 줄였다. 기획자가 지정한 패널 폭 ×1.1(391px)은 한국어 최장 줄 392px에 1px 모자라 ×1.114로 밀고 그 이유를 적었다. 모든 언어를 한 줄에 넣으려면 ×1.34가 필요해 화면을 잡아먹었다.

6.3 숫자는 재서 정하고, 이유와 함께 지운다

스타일 값은 눈대중으로 정하기 쉽고, 한 번 들어가면 이유 없이 남는다. 정할 때는 실측한 값에서 출발하고, 고친 뒤에는 실제로 바뀌었는지 재고, 이유가 사라지면 값도 지운다. 화면·문서에 뜨는 숫자와 색은 손으로 옮겨 적지 않고 출처(상수·계산 함수·원본 그림)에서 부른다 → 2장 게임 디자이너.

크기 지정은 눈대중으로 환산하지 말고 실측한 상자에 곱한다

「1.3배 키워 달라」는 요청을 받으면 지금 렌더된 상자의 치수를 재고 거기에 곱한다. 스크린샷을 보고 rem으로 환산하면 틀린다. 「줄 높이 × 줄 수」처럼 CSS 값을 손으로 합산해도 실측과 어긋난다. 높이는 가장 꽉 찬 상태를 재서 고정하고, 스모크 테스트가 그 상자를 잰다. 치환 요소(<img>)에는 퍼센트로 상자를 준다. 절대 배치된 <img>의 width: auto는 원본 폭으로 풀린다.

사례 · 배수 요청

무슨 일이 「폭 1.3배, 높이 1.2배」를 스크린샷 눈대중으로 환산했다가 오히려 더 작게(74×28) 만들었다. 「줄 높이 × 쪽 크기」를 손으로 계산한 목록 표는 쪽마다 3px씩 줄었다. 절대 배치된 무기 그림은 원본 폭으로 풀려 화면 밖으로 사라졌다. 잡은 방법 렌더된 상자를 재고 곱하는 방식으로 다시 했고, 스모크 테스트가 상자 치수를 단언하게 했다.

스프라이트의 위치값은 프레임 경계에서 계산하고 찍어서 확인한다

background-position 퍼센트로 N칸 가로 스프라이트(여러 프레임을 한 장에 나란히 붙인 그림)를 steps(N)으로 넘길 때, 종료 위치는 100%가 아니라 100 × N/(N−1)%다. 퍼센트 위치는 「상자와 그림의 크기 차이」에 대한 비율이라 직관과 다르다. 프레임 경계를 직접 계산해 넣고, 계산된 값이 그 경계에 정확히 찍히는지 확인한다.

사례 · 스프라이트 애니메이션

무슨 일이 레벨업 도장 연출(3프레임)의 종료 위치를 100%로 두자 단계값(0/33.3/66.7%)이 실제 프레임 경계(0/50/100%)와 어긋나 두 그림이 겹쳐 보였다. 잡은 방법 150%로 고치고, getComputedStyle().backgroundPosition이 정확히 0% / 50% / 100%로 찍히는지, 세 프레임이 겹침 없이 갈라지는지를 확인했다.

줄여서 맞춘 값과 이유가 걸린 값은 이유가 사라지면 함께 지운다

「글자를 줄여 맞춘다」는 대개 다른 무언가가 자리를 잡아먹고 있다는 신호다. 그 원인을 치운 뒤 줄였던 값을 되돌리지 않으면 「왜 이 글자만 작지」가 근거 없이 남는다. 간격·폭 규칙도 마찬가지다. 내용을 빼거나 요소를 옮길 때는 그 요소에 걸린 규칙과, 그 이유를 적은 주석을 함께 찾아 지운다. 남기면 주석이 이미 없는 이유를 설명하게 된다.

사례 · 남은 축소값

무슨 일이 캐릭터 명패가 좁아서(레벨 배지가 폭을 차지했다) 글자를 .85rem에서 .72rem으로 줄였다. 나중에 배지를 빼자 줄인 이유가 사라졌다. 잡은 방법 실측으로 원래 값을 복원했다.

사례 · 자리를 옮긴 요소

무슨 일이 단추 판의 아래 여백은 「마지막 줄이 안내문」이라서 있었는데, 안내문이 빠지자 판이 기울어 보였다. 삭제 단추의 폭 규칙(width: 3.3rem)은 목록 줄 끝의 작은 단추용이었는데, 그 단추가 편성 화면의 폭 전체를 쓰는 단추로 옮겨 갔다. 규칙을 남겼으면 새 자리에서 짜부라졌을 것이다.

고치기 전과 후를 재서, 수정이 정말 무언가를 바꿨는지 확인한다

전후 차이가 0이면 그 수정은 지금 환경에서 아무 일도 안 한 것이다. CSS에서는 부모의 max-width가 width 수정을 조용히 누르고, 빌려 쓴 클래스의 규칙이 다른 컨테이너 안에만 있어 안 걸리기도 한다. 폭을 바꿀 때는 max-width/min-width도 함께 보고, 다른 화면의 클래스를 빌리지 말고 제 이름을 만든다. 회전·확대 장식은 외접 상자 기준으로 공간을 잡는다. 라이브러리 버전에 의존하는 방어 코드는 남길 수 있지만, 확인한 사실과 추측을 구분해 적는다.

사례 · 하지 않아도 됐던 수정

무슨 일이 초상화를 축소할 때 투명 픽셀의 색이 번질 것을 걱정해 프리멀티플라이(색에 알파를 미리 곱해 두는 방식) 경유를 넣었는데, 출력이 바이트 단위로 같았다. 쓰던 이미지 라이브러리(Pillow 12)는 원래 번지지 않았다. 왜 조용했나 재 보지 않았으면 「이렇게 안 하면 번진다」는 주석과 함께 없는 문제를 해결했다고 남길 뻔했다. 잡은 방법 전후 출력을 비교하고, 합성 시험 이미지(왼쪽 불투명 흰색 | 오른쪽 투명한 빨강)로 따로 쟀다.

사례 · 안 걸린 수정 넷

무슨 일이 한 주에 넷이 났다. 부모의 max-width: 19rem이 width 수정을 눌렀다. 다른 화면에서 빌려 쓴 클래스가 그 화면의 컨테이너 안에서만 걸려, 경고문이 본문보다 큰 글자로 떴다. 45° 회전한 네모의 외접 상자가 √2배라 가로 스크롤이 생겼다. margin-top: auto 둘이 빈자리를 나눠 가져 목록이 가운데로 흘렀다. 잡은 방법 스모크 테스트가 「상한에 눌렸는가」 같은 치수를 재게 했다.

6.4 에셋 파이프라인 — 원본에서 화면까지

원본 그림과 화면 사이에 굽기 도구를 한 층 두면, 원본을 갈아 끼워도 화면 코드는 한 줄도 바뀌지 않는다 → 3장 시스템 엔지니어. 대신 그 도구가 새 실패 지점이 된다. 도구는 「몇 장 만들었다」만 보고하고, 잘 만들었는지는 말하지 않는다. 이 절은 도구가 정보를 잃지 않고, 섞이지 않고, 정직하게 보고하게 만드는 원칙이다.

정보가 가장 많은 원본을 받고, 화면이 이상하면 파이프라인을 거꾸로 짚는다

원본 정보를 지우는 전처리를 먼저 거친 파일을 받으면, 뒤 단계에서는 복원할 근거가 없다. 배경을 이미 지운 PNG보다 크로마키 합성본(단색 배경 위의 그림)을 받아 알파까지 다시 푸는 쪽이 정확하다. 화면이 이상하면 CSS로 우회하지 말고 원본 → 중간 → 결과물을 순서대로 픽셀로 찍어 차이가 생긴 단계를 찾는다. 「같은 그림인데 다르게 보인다」면 증상을 재서 보정하기 전에 둘이 왜 달라졌는지부터 찾는다. 새 에셋 파일이 오면 치수를 다시 잰다. 그림은 아무 말 없이 바뀌어 온다.

사례 · 크로마키

무슨 일이 외부 배경 제거 도구가 알파만 만들고 RGB에는 마젠타(크로마키 색)를 남겼다. 색만 걷으면 과대평가된 알파 탓에 마젠타가 남았고(470 → 216), 수학적 하한을 쓰면 파란 투구가 84% 투명해졌다. 왜 조용했나 배경 제거가 「이 픽셀이 얼마나 배경이었는지」라는 정보를 지워 버려, 뒤에서는 되살릴 근거가 없었다. 잡은 방법 알파 구간별 평균 RGB를 재서 원인을 확인했다. 마젠타 배경 위의 합성 JPG를 받아 직접 풀자 잔여 픽셀이 약 30,000에서 약 100으로 줄었다.

사례 · 화면에서 우회하려다

무슨 일이 굽기 도구의 im.convert("RGB")가 원본 알파를 지워 사진이 검은 배경으로 보였는데, 처음에는 화면에서 mix-blend-mode로 우회하려 했다. 장비 제작 화면의 옥색·붉은 단추는 같은 79×40 상자인데 크기가 달라 보여, 옥색만 border-image-outset으로 키웠더니 오히려 옥색이 커 보였다. 원인은 붉은 그림 구석의 알파 8짜리 점 하나 때문에 도구가 경계상자를 다르게 자른 것(828×225 vs 846×244)이었다. 액자 그림은 아무 말 없이 927×672에서 940×691로 바뀌어 오기도 했다. 잡은 방법 알파는 getpixel()로 원본 픽셀을 찍어 확인했다. 단추는 기획자가 원본 두 장을 열어 「크기가 똑같고 색만 다르다」고 짚었다. 이후 검사는 배경에 흔들리는 픽셀 측정 대신 구조로 보장되는 값(borderImageSlice)을 보게 했다.

저장 형식은 런타임이 소비하는 방식과 대상 플랫폼으로 고른다

에셋 포맷은 요청 수, 상태 전환 비용, 엔진 내장 기능을 쓸 수 있는지를 표로 비교해 정한다. 움직이는 그림을 브라우저에 그대로 재생시키면 역재생·재시작·다른 연출 시계와의 동기화가 안 되므로, 칸 단위 띠(스프라이트)로 펴서 코드의 시간표가 칸을 고르게 한다. 투명 애니메이션은 모든 대상 플랫폼에서 도는 형식으로 굽는다. 데스크톱 크롬에서 보인다고 판단하지 않는다.

사례 · 투명 애니메이션

무슨 일이 두루마리 펼침 연출의 원본은 .gif(알파가 1비트라 반투명이 탈락한다)·APNG(1.7MB) 대신 webp를 골랐고, 그마저 그대로 재생하지 않고 띠로 폈다. 생성 AI로 만든 주사위 영상(1280×720, 55프레임)은 투명하게 띄워야 했는데, 사파리가 알파 WebM을 재생하지 못한다(iOS가 출시 대상이다). 그래서 알파 WebP 스프라이트 시트 + 별도 음원으로 구웠다.

표시 조정과 정규화는 런타임이 아니라 굽는 단계에서 끝낸다

배경 세기를 낮추려고 화면에 반투명 막을 덮으면 그 위의 하이라이트와 캐릭터까지 뿌예진다. 표시 조정은 가능한 한 굽는 단계에서 끝내 런타임 레이어를 늘리지 않는다. 같은 자리에 들어갈 수 있는 에셋 계열들은 정규화 기준(채움 비율·기준선)을 하나로 정해 문서에 적는다. 반대로 짝으로 맞춰 그린 상태 그림(기본/선택)은 원본이 이미 정렬해 둔 것이므로 따로 트리밍(여백 자르기)하지 않고 예외 목록에 넣는다.

사례 · 배경 굽기

무슨 일이 반투명 막으로 판을 덮는 것이 가장 쉬웠지만 기각하고, 지도 세기는 굽는 단계에서 눌렀다. 시간대별(낮·황혼·밤) 배경이 한 장에 나란히 붙은 띠 그림은 CSS background-position으로 잘라 쓰지 않고 칸마다 잘라 JPG로 냈다(PNG 25MB 이상 → JPG 4.2MB). 한 장 잘라 쓰기는 칸 수가 원본마다 달라 같은 사실이 CSS와 코드 두 곳에 적히고, 밤 그림 하나를 띄우려 낮·황혼까지 받는다.

사례 · 정규화 기준 차이

무슨 일이 초상화는 정규화 없이(세로 채움 79~100%, 표준편차 3.6%), 액션 시트는 90%로 정규화해(91~99%, 표준편차 1.4%) 구웠다. 정지 그림을 움직이는 그림으로 바꾸자 「일부 캐릭터만 유독 작다」는 관찰이 나왔다. 잡은 방법 알파 경계상자로 채움 비율을 실측해, 코드 결함이 아니라 원본 기준 차이임을 확인했다. 따로, 기본 칩과 선택 칩(같은 600×398 캔버스·같은 자리에 그린 그림)은 도구가 각각 여백을 잘라 화면에서 크기가 달랐다. 첫 진단(선택 칩의 빛 번짐이 잘렸으니 문턱값을 올린다)은 틀렸다.

파라미터를 고치면 전체를 다시 굽고, 건너뛰기는 존재가 아니라 내용으로 판단한다

한 폴더에 서로 다른 규칙으로 만든 파일이 섞이면 눈으로 구분하지 못한다. 파라미터 변경과 전체 재생성을 한 단위 작업으로 묶고, 부분 재생성은 확인용으로만 쓴다. 「출력이 있으면 건너뛴다」는 같은 이름으로 고친 원본을 못 보므로, 증분 판단은 원본의 해시(또는 수정 시각)로 하고, 출력이 여러 벌이면 전부 있어야 건너뛴다. 늘 --force로만 돌리면 기본 경로의 버그가 숨으므로 기본 경로도 가끔 돌린다. 굽기 도구는 첫 입력 하나로 검증하지 말고, 작은 원본·큰 원본처럼 갈래가 다른 입력을 하나씩 넣어 본다. 「안 도는 갈래」는 새 그림이 와야 드러난다.

사례 · 부분 재생성

무슨 일이 초상화 배경 제거 규칙을 고친 뒤 7장만 다시 굽고 넘어갔다가 작업이 끊겨, 253장이 옛 규칙으로 남을 뻔했다. 잡은 방법 다음 작업에서 작업 이력을 보고 알아채 --force 전체 재생성으로 맞췄다.

사례 · 안 도는 갈래

무슨 일이 스프라이트 굽기 함수는 칸을 128px로 잡는데, 그 안의 리사이즈 함수는 줄이기만 했다. 그래서 칸이 56px인 작은 문양 그림이 128px 칸의 왼쪽 위 구석에서 깜빡였다. 앞서 쓰던 그림은 원본이 커서 이 갈래를 한 번도 지나지 않았다. 초상화 도구는 출력의 존재만 봐서 같은 이름으로 바로잡은 원본을 반영하지 못했다. 액자 굽기 도구는 결과가 이미 있으면 죽는 버그(파일 정보 조회 한 줄 누락)가 있었는데, 늘 --force로만 돌려서 아무도 못 봤다. 잡은 방법 칸 크기를 입력 크기에서 정하게 고쳤다. 나머지는 원본을 고쳤는데 결과가 안 바뀐 것, 기본 옵션으로 한 번 돌려 본 것이 드러냈다.

굽기 도구는 자기 이름만 지우고, 경고는 측정값으로 내고, 짝이 될 경고는 나란히 찍는다

같은 폴더를 여러 도구가 쓰면 「내 목록에 없으면 지운다」는 남의 산출물을 지운다. 각 도구는 자기가 만들 수 있는 이름 패턴만 지운다. 품질 경고는 파일 이름이 아니라 측정값(실제 폭)으로 낸다. 오탐이 섞이면 진짜 경고까지 무시된다. 「원본 없음」과 「매칭 실패」처럼 짝이 될 수 있는 경고는 한 화면에 나란히 출력하고, 에셋 이름의 표준은 하나(파일명)로 정한다. 폴백과 삭제는 말없이 하지 말고 이름을 찍어 알린다 → 3장 시스템 엔지니어.

사례 · 남의 파일을 지운 도구

무슨 일이 배경 굽기 명령이 공용 출력 폴더에서 UI 굽기 도구가 만든 배경 한 장을 「계획에 없으니 묵은 것」으로 쓸어 버려 404가 났다. 같은 배경 도구는 「저해상도」를 파일 이름의 접미사로 판단해서, 해상도가 같은 다른 그림을 저해상도로 찍었다. 왜 조용했나 배경 그림이 404면 화면이 바탕색으로 물러나 눈에 잘 띄지 않는다. 거짓 경고는 경고 전체를 안 읽게 만든다.

사례 · 짝이었던 두 경고

무슨 일이 액션 시트 도구가 몇 주째 「원본이 없는 캐릭터 8명」과 「대응 캐릭터가 없는 파일 8건」을 따로 찍었다. 나란히 놓자 한 글자씩 틀린 이름 짝이었다. 그동안 그 8명은 전투에서 초상화로 대신 섰다. 왜 조용했나 두 경고가 각자 「원본이 아직 안 왔다」로 읽혔다. 잡은 방법 두 목록을 나란히 놓았다. 수가 같은 두 경고는 서로의 짝인지부터 맞춰 본다.

6.5 자르기와 배경 제거 — 이미지 처리를 재는 법

대량 에셋을 다루면 이미지 처리 알고리즘을 직접 만들게 된다. 우리는 캐릭터 초상화 260장의 배경 제거, 그림 시트 자르기, 생성 영상의 배경 걷기를 직접 했다. 이 일은 예제 몇 장에서 좋은 점수가 나와도 전수에서 무너진다. 원칙은 「전수를 돌려 분포의 끝을 보고, 지표를 여럿 세우고, 정답조차 의심한다」로 모인다.

그림 시트는 등분하지 말고 픽셀로 경계를 찾고, 찾은 수를 단언한다

「넉 장을 넉 등분」처럼 당연해 보이는 분할도 실제 경계는 1~3px 어긋나 있다. 등분하면 옆 칸이 딸려 오고, 화면에는 「끝에 이상한 줄」로만 보인다. 등분 자리 근처에서 색이 가장 튀는 열이나 알파 합이 가장 작은 열을 경계로 찾고, 옮긴 값을 로그로 남기며, 찾은 경계 수가 기대값과 다르면 도구가 멈추게 한다. 칸의 순서도 관례를 믿지 말고 원본마다 열어서 확인한다.

사례 · 시트 자르기

무슨 일이 시간대별 배경 띠 그림의 진짜 칸 경계가 268·536이 아니라 266·535여서, 낮 그림 오른쪽에 황혼의 주황 띠가 2px 남았다. 다른 그림은 정확히 등분 자리라 「다 그렇겠지」로 넘어갈 뻔했다. 한 달 뒤 등급 배지 시트(1003px ÷ 6)는 알파 0인 틈조차 없었고, 상점 아이템 시트(681 ÷ 4 = 170.25)는 실제 경계와 최대 3px 어긋났다. 같은 자리를 두 번 밟았다. 왜 조용했나 도구는 몇 장을 만들었는지만 알려 주지, 잘 잘랐는지는 알려 주지 않는다. 잡은 방법 경계를 찾은 뒤 [268, 536] → [266, 535]처럼 보정량을 찍고, 찾은 경계 수가 기대값이 아니면 멈추게 했다.

사례 · 칸 순서

무슨 일이 기존 관례(시계방향)대로 2×2 연출 그림을 펴면 꽃이 피는 장면과 지는 장면이 뒤집혀 재생될 뻔했다. 실제로는 읽는 순서(좌상→우상→좌하→우하)로 그려져 있었다. 잡은 방법 그림 파일을 직접 열어 봤다.

표본은 대표값 하나로 접지 말고, 임계값은 정상값의 최댓값을 재고 정한다

여러 성분이 섞일 수 있는 표본을 중앙값 하나로 접으면, 혼합 표본에서는 어느 쪽도 아닌 값이 나온다. 분포(히스토그램)를 그대로 들고 판정한다. 임계값은 근거 없이 고르지 말고, 정상 사례가 어디까지 올라가는지와 이상 사례가 어디서 시작하는지를 재서 그 사이에 둔다. 연결성(플러드필, 같은 색 영역을 이웃 따라 채워 나가는 방식)만으로 안 잡히는 갇힌 영역에는 색 기준 같은 두 번째 판정을 둔다.

사례 · 배경 제거

무슨 일이 초상화 배경 제거의 첫 판은 그림 테두리 색의 중앙값 하나를 배경색으로 썼다. 예제에서는 IoU(정답 마스크와 겹치는 비율) 0.99였는데, 260장 중 46장이 배경을 절반도 못 지웠다(최악은 95.4% 잔존). 왜 조용했나 두 색 띠가 섞인 배경이 많았고, 혼합 표본의 중앙값은 어느 쪽도 아닌 색이라 두 색이 다 남았다. 예제 몇 장에는 그런 그림이 없었다. 잡은 방법 전수 결과의 「남은 넓이」 분포를 보고, 이상한 그림의 원본을 눈으로 확인했다. 히스토그램 방식으로 바꾸자 46장이 0장이 됐다.

사례 · 근거 없는 임계값

무슨 일이 단체 그림에서 「배경 띠」를 판정하는 채움 문턱 0.5를 근거 없이 골랐다. 그런데 발치에서는 캐릭터 5명만으로 폭의 65%가 차서 5명이 한 덩어리로 붙었다. 위아래 띠가 배경을 가둬 플러드필이 닿지 못해 그림 하나가 통째로 지워지기도 했다. 왜 조용했나 대부분의 입력에서는 0.5로도 정상 결과가 나왔다. 잡은 방법 실패한 파일을 하나씩 보고 정상 신호(진짜 띠는 폭의 100%)를 다시 쟀다.

한 축에서 상충이 풀리지 않으면 다른 축을 찾고, 틀림의 무늬를 본다

상충하는 목표는 각각 지표로 세워 나란히 놓고 훑는다. 같은 축(예: 색 허용치)에서 「느슨하면 A가, 조이면 B가 깨진다」가 보이면 그 축을 더 잘게 훑지 말고, 두 문제를 구별하는 다른 성질을 찾는다. 더 정교한 모델을 쫓다 막히면 「틀림이 어떤 주기·무늬로 나타나는가」를 보고 표적 필터를 생각한다. 알파와 색을 다른 정밀도로 처리하지 않고, 한 지표·한 배율만 보고 끝내지 않는다.

사례 · 축 추가

무슨 일이 히스토그램 방식에서 8장이 얼굴을 잃었다. 외곽선의 틈으로 플러드필이 얼굴 안까지 들어갔다. 색 허용치를 4×4로 훑었지만 느슨하면 얼굴이, 조이면 배경이 남았다. 잡은 방법 예제 IoU·최소 넓이(얼굴 보존)·최대 넓이(배경 제거) 세 지표를 나란히 놓아 색 축 안의 상충을 확인했다. 누수는 좁은 통로를 지난다는 점에 착안해 「폭」 축(반지름 3 열림 연산)을 더했다. 최소 넓이가 0.178에서 0.319로 올라 양쪽을 만족했다.

사례 · 무늬를 본 필터

무슨 일이 투명 배경을 뜻하는 체커보드 무늬가 아예 그림에 박혀 온 가챠 연출 그림의 배경 제거가 세 번 실패했다. 타일 평균은 1px짜리 광선에서 깨졌다. 위치마다 다른 분모(255 − 배경)를 쓴 방식은 가정이 깨지는 픽셀마다 체커를 물려받았다. 알파만 블러하자 색 복원식의 배경 항이 색에 새겨졌다. 왜 조용했나 구석의 알파만 보면 「배경은 깨끗」이었다. 무늬는 색 채널에 있었다. 잡은 방법 구석 알파·색 채널 픽셀 배열·실사용 크기 렌더 세 축을 따로 보다가, 틀림이 정확히 30px 주기로 난다는 것을 알아챘다. 그 주파수 성분만 복조·저역통과로 지웠다.

자기 출력을 다시 넣는 단계와 정답 표본은 둘 다 의심하고 잰다

1차 결과로 모델을 다시 추정하는 반복 정련은 1차의 오류를 다음 단계에 반영해 눈덩이로 키울 수 있다. 「더 정교해 보이는」 단계도 정답 대비 수치가 좋아질 때만 남긴다. 반대로 정답 표본도 완벽하다고 가정하지 않는다. 정답 대비 점수는 참고치로 쓰고, 점수가 낮은 건은 정답 쪽 결함부터 확인한다. 정답을 검수하지 않은 최적화는 정답의 결함까지 학습한다.

사례 · 정련 패스와 정답 표본

무슨 일이 1차 결과로 색 모델을 다시 잡아 2차 플러드필을 도는 정련 패스가 예제 IoU를 0.99에서 0.91로 떨어뜨리고 발밑 풀밭을 통째로 지웠다. 1차에 섞여 들어간 초록 기운이 모델에 반영됐다. 측정한 뒤 삭제했다. 같은 날, 점수가 낮던 예제 2건(IoU 0.907, 0.832)은 오히려 우리 결과가 더 깨끗했다. 예제 쪽에 등고선 조각·넝쿨 잔상이 남아 있었고, 서로 다른 도구로 만든 것으로 보였다. 왜 조용했나 IoU를 목표로 최적화했다면 예제의 잔상까지 따라 만들어 점수가 「올라갔을」 것이다.

자동 처리는 다수에 맞추고, 예외는 표시와 수동 통로로 처리한다

260개 중 1개를 위한 휴리스틱은 259개를 망칠 수 있다. 자동 처리는 다수에 맞추고, 정상 범위를 벗어난 결과를 「확인 필요」로 표시하는 검사와 수동 지정 통로로 예외를 처리한다. 수동 값은 원본이 바뀌면 틀어질 수 있음을 적어 둔다. 입력이 같은 생성기·같은 구도로 균질하면, 그 균질성을 쓰는 단순한 규칙이 범용 학습 모델보다 정확하고 의존성도 적다. 다만 그 파라미터는 그 입력 전용이라는 것을 적어 둔다.

사례 · 한 장의 예외

무슨 일이 초상화 한 장은 배경이 인물에 갇혀 있어 색 통계로 피부와 분리되지 않았다(배경의 밝기 편차 ±0~+7, 피부 +1~+38로 겹친다). 자동 판별 규칙을 더하는 대신, 배경 시작점 좌표를 손으로 넣는 옵션을 뒀다. 그리고 결과의 배경 비율이 정상 범위(8~55%)를 벗어나면 도구가 표시하게 했다. 배경 제거에 rembg 같은 학습 모델은 쓰지 않았다. 260장이 같은 생성기·같은 구도라 배경 성질을 직접 쓰는 쪽이 더 정확했고, 약 176MB짜리 모델 의존도 안 생겼다.

다른 바탕에 올릴 소재는 가장자리와 그림자를 다시 만든다

배경을 걷은 소재는 원래 바탕을 전제로 그려진 흔적을 안고 있다. 물체가 이미지 가장자리에 걸리면 모서리와 물체 사이의 배경이 바깥과 끊겨 「물체 안의 구멍」으로 보이고, 구멍 채우기가 그것을 정상적으로 채워 버린다. 구멍 채우기 전에 이미지 둘레에 배경색 테를 덧대 바깥을 하나로 이은 뒤 범람시킨다. 원본 그림자가 배경보다 밝으면 걷은 뒤 밝은 얼룩이 되므로, 검정 반투명으로 다시 만들어 어느 바탕에서도 바닥으로 읽히게 한다. 경계는 침식 대신 매팅(경계 픽셀의 알파와 색을 함께 추정하는 처리)으로 복원한다.

사례 · 생성 영상의 배경 걷기

무슨 일이 생성 AI로 만든 주사위 영상의 배경을 밝기 문턱 → 닫기 → 구멍 채우기로 걷었다. 그런데 첫 프레임에서 주사위가 화면 가장자리에 걸려, 모서리와 주사위 사이에 갇힌 배경이 검은 조각으로 붙었다. 원본 그림자는 짙은 회색 배경보다 밝은 회색이라, 걷고 나니 밝은 얼룩으로 남았다. 왜 조용했나 바깥과 이어지지 않은 배경은 알고리즘에게 「물체 안의 구멍」으로 보여 정상적으로 채워졌다. 잡은 방법 양피지·회색·먹색 세 바탕 위에 결과를 겹쳐 보는 미리보기 옵션으로 둘 다 찾았다. 화면 표식(워터마크)은 비우고, 물체가 들어오는 가장자리는 페이드로 스며 나오게 했다.

6.6 눈으로 확인하는 법

이 자리의 결함 상당수는 수치로 안 잡히고 눈으로만 보인다. 그런데 눈도 잘못된 조건에서 보면 속는다. 흰 미리보기, 작은 프레임, 기본 줌, 로딩이 덜 된 스크린샷이 모두 결함을 숨기거나 없는 결함을 만든다. 볼 때는 조건을 극단으로 잡고, 판정은 다시 숫자로 한다.

투명 이미지는 모든 바탕 위에서, 크게, 극단 표본으로 보고 판단은 픽셀 통계로 한다

투명 이미지는 실제로 쓰일 모든 배경색 위에 합성하고, 실제 표시 배율보다 크게 본다. 전수 확인이 어려우면 지표의 양 극단 + 무작위 표본을 한 장의 대조 시트로 본다. 수치는 정상이어도 그림이 깨질 수 있고, 반대로 눈에는 깨져 보여도 미리보기 탓일 수 있다. 「안 보인다」「노이즈가 있다」를 추출 실패로 단정하기 전에 미리보기 배경과 압축을 의심하고, 알파 히스토그램으로 판정한다.

사례 · 어두운 바탕에서만 보인 테

무슨 일이 초상화 이진 마스크가 흰 배경에서는 멀쩡했는데, 어두운 UI 위에서 실루엣 둘레에 황갈색 테 1px이 보였다(원본의 안티에일리어싱 혼합 픽셀). 기본 줌에서는 판의 칸이 30px대라 안 보였다. 왜 조용했나 넓이·IoU 같은 수치는 정상이었다. 잡은 방법 실제로 쓰일 판 색 셋(중립·아군 녹색·적군 적색) 위에 3배 확대 합성하고, 지표 양 극단 14장 + 무작위 86장을 어두운 배경 대조 시트로 봤다. 매팅 2px로 해결했다. 얼굴을 잃은 8장도 수치보다 대조 시트에서 먼저 보였다.

사례 · 미리보기의 착시

무슨 일이 불꽃 고리 연출 6장 중 흰색·은색 두 장이 흰 배경 미리보기에서 안 보였다. 가챠 그림은 미리보기에서 배경 노이즈가 보였다. 잡은 방법 둘 다 알파 0~255가 정상 분포임을 픽셀 통계로 확인했다. 앞은 미리보기 배경의 착시, 뒤는 미리보기의 압축 아티팩트였다.

꽉 채우는 그림은 가장 큰 프레임에서, 에셋이 다 온 뒤에 본다

작은 프레임에서는 늘린 저해상도 그림도 깨져 보이지 않는다. 해상도 품질 검사는 최대 표시 크기에서 한다(우리 경우 700px). 시각 확인용 캡처는 에셋 로드가 끝난 것을 확인한 뒤에 찍는다. 스크린샷이 그림 다운로드보다 빠르면 「판때기가 안 그려졌다」를 우선순위 문제로 오진한다.

사례 · 저해상도 배경

무슨 일이 처음 받은 화면 배경은 칸 하나가 225~300px짜리 저해상도였는데, 480px 스크린샷으로만 확인해 놓쳤다. 잡은 방법 기획자가 화면을 보자마자 지적했다. 이후 700px 눈검사를 기준으로 삼았다.

「안 보인다」「폰트가 다르다」는 굵기·색보다 좌표계를 먼저 본다

확대·축소가 있는 화면에서 월드 좌표 1px 선은 배율이 작아지면 1px 미만이 되어 사라진다. 굵기·색을 올리기 전에 그 선이 화면 좌표 기준인지 월드 좌표 기준인지 정하고, 항상 보여야 하는 선·글자는 배율 역수로 두께를 보정한다. 바탕 밝기 범위 전체에서 대비도 확인한다. SVG 안의 글자 크기가 화면마다 다르면 viewBox와 원본 해상도부터 본다. 포커스 가능한 SVG 요소에는 초점 스타일을 명시한다.

사례 · 사라진 줄눈

무슨 일이 판의 칸 줄눈을 굵고 진하게 해도 전체 보기 배율에서 안 보였다. 월드 좌표 1px은 0.19배에서 0.2px가 된다. 밝은 바탕에서는 검은 외곽선이 뒤집혀 글자는 날아가고 테만 남았다. 잡은 방법 이미 해결해 둔 좌표 눈금 글자의 방식(배율 역수)과 비교했다.

사례 · 다른 폰트처럼 보인 글자

무슨 일이 레벨이 오른 도시 그림의 원본이 482폭이라, 그 위의 SVG <text>가 viewBox 단위로 1.42배 커지면서 「다른 폰트」처럼 보였다. 클릭한 뒤 남던 검은 둥근 네모는 tabIndex를 단 <g>의 기본 초점 테두리였다. 잡은 방법 그림마다 자기 viewBox를 갖게 하고, 원본 해상도를 메인 화면 그림과 맞췄다.

장식 효과는 결정적으로 만들고, 불변 성질은 좌표로 검사한다

장식 애니메이션을 난수로 만들면 경계를 넘는 경우가 어쩌다 한 번 나와 재현이 안 된다. 정해진 순환으로 만들어(결정적, 같은 입력이면 늘 같은 결과) 모든 경우를 테스트로 훑을 수 있게 한다. 「글자가 안 움직인다」 같은 픽셀 단위의 불변 성질은 스크린샷 두 장을 눈으로 비교해서는 알 수 없으므로 좌표로 검사한다. DOM 구조를 바꾸면 그 구조를 읽던 스모크 테스트도 함께 고친다. 「있는가」「제자리에 있는가」「몇 줄인가」를 따로 재는 일반 원칙은 → 5장 클라이언트 엔지니어를 본다.

사례 · 움직이는 배경

무슨 일이 메뉴 화면 배경의 미세한 움직임을 2.6초 간격·최대 1.5%·여덟 자세 순환으로 만들었다. 최대 10px 이동이라 글자가 1~2px 따라 움직여도 눈으로는 모른다. 그림을 별도 층으로 옮기자, 배경 그림을 제목 요소에서 읽던 스모크 테스트가 첫 항목에서 막혔다. 잡은 방법 「그림의 transform은 달라지고 제목의 getBoundingClientRect()는 같다」를 한 검사로 묶었다. 확대로 만든 여백이 이동 거리보다 큰지는 계산(회귀 테스트)과 실제 배치(브라우저에서 21초를 0.4초마다 훑어 최악의 틈 −12.043px)로 따로 확인했다.

목업은 결함을 찾는 데 쓰고, 느낌은 실제 화면에서 판단한다

인증 같은 외부 의존 때문에 화면에 못 들어가면 「스타일만 얹은 정적 목업」과 「진짜 컴포넌트를 가짜 데이터로 마운트한 임시 엔트리」를 쓰고, 검증 뒤에는 지운다. 목업은 잘림·깜빡임 같은 결함 판단의 근거로만 쓴다. 목업에는 실제 화면의 조상 요소가 없어 구조에 의존하는 버그가 재현되지 않고, 밀도·답답함 같은 감각은 실제 크기 화면에서만 판단할 수 있다. 고치기 전에는 요청받은 화면을 스크린샷으로 확인해, 실제로 렌더하는 컴포넌트를 특정한다.

사례 · 로그인이 막힌 화면

무슨 일이 외부 인증 서비스(Supabase)의 이메일 확인 설정 때문에 자동화 세션이 시험 계정을 만들 수 없었다. 대신 스타일시트를 정적 파일 폴더에 잠깐 복사하고(그래야 그 안의 상대 경로 그림이 풀린다) 마크업만 흉내 낸 HTML을 Playwright로 찍었다. 이것으로 효과 글 잘림·음절 중간에서 끊긴 한글·스프라이트의 구석 깜빡임·그림 사라짐 넷을 잡았다. 반면 340px 목업에서 답답해 보여 줄을 두 줄로 눕혔다가, 기획자가 실제 화면에서 「안 답답하다」고 해서 되돌렸다. 잡은 방법 결함은 목업으로 잡고, 느낌은 실제 화면 스크린샷으로 기획자에게 확인받았다.

사례 · 엉뚱한 컴포넌트

무슨 일이 「캐릭터 카드를 고쳐 달라」는 요청에 이름이 비슷한 상세 화면 컴포넌트를 고쳤는데, 실제로 뜨는 것은 카드 팝업 컴포넌트였다. 잡은 방법 고친 뒤 스크린샷을 보니 바뀐 것이 없었다. 화면 이름으로 파일을 짐작하지 않는다.
