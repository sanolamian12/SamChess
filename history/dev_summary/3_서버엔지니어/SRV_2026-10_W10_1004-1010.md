# 서버 엔지니어 — W10 · 2026-10-04 ~ 10-10

> **이번 주 요지** — 서버 코드는 거의 안 바뀐 주다. 다만 전투 UI 개편이 **온라인 경로의 두 구멍**을 드러냈다 — 상대 차례의 [턴 넘기기]가
> **한 번도 서버에 안 닿고 있었고**(재생기가 버렸다), 온라인에서 먼저 준비를 마치면 전선의 `waiting`이 **「상대 차례」로 옮겨져** 배치 판이 통째로
> 비었다(H2a부터 두 달 가까이). 온라인을 화면으로 보는 통로가 H3a 이후 없었다는 것도 드러나 **`npm run look:online`**(계정 둘 · 진짜 대기열)을 새로 냈다.
> 6단계 마무리 때는 Supabase Transaction Pooler 연결이 **3.6~14.6초**로 느려져 `smoke:meta`가 세 번 떨어졌다.

## 대전 서버·네트워크

### 상대 차례의 [턴 가져오기] — 서버에 닿게 (10-06, 3단계)

`forceSkipTurn`(상대가 20초를 넘기면 켜지고 3번이면 승리)은 서버 규칙이 이미 받는데, 클라이언트의 `Playback.submit()`이 **`awaitingInput`이 아니면 전부 버려서**
— 상대 차례의 단계 이름이 바로 `aiThinking`이다 — 커맨드 패널의 「턴 넘기기」는 켜져도 서버에 닿지 않았다. 켜지려면 온라인에서 실제로 20초를 기다려야 하고
AI 대전엔 마감이 없어 아무 검사도 지나지 않았다. `forceSkipTurn`만 `aiThinking`에서 통과시켰다(게임 정보의 [턴 가져오기]). `Playback.submit()`을 바꿨으므로
`smoke:online`을 돌려 통과를 봤다. → 결정·교훈 참조

### 배치 대기(`waiting`)는 재생기에서 `deploying`이다 (10-07, 8단계)

전선의 `phase`는 「받는 사람의 걸음」이고 `waiting`(「나는 준비를 마쳤고 상대를 기다린다」)은 서버가 `toWire(state, side)`로 떼면서 넣는 관점이다.
그런데 받는 쪽 `playback.ts`의 `settle()`이 그것을 **`aiThinking`**(상대 차례)으로 옮기고 있었다(H2a, 2026-08-19). 5단계의 배치 판은 「대기는 배치 단계 안의 걸음 —
`deploying` + `state.ready`로 가른다」고 그렸으니, **온라인에서 먼저 준비하면 배치 판이 비고 순서 판 · 명령 판이 상대 차례를 그렸다.**

- `deploying`으로 고쳤다(5단계 설계대로라 묻지 않았다). `aiThinking`의 `waitMs`(상대 걸음 350ms마다 청하기)는 대기에는 필요 없었다 — 온라인의 `ready()`는 로컬만 듣는다.
- `smoke_online`은 「준비를 마친 쪽은 `aiThinking`」을 **단언**하고 있었다 — 검사가 틀린 가정을 굳히고 있었다. 단언을 `deploying` + `state.ready`로 고쳤다.
- 흉내 통로 `?late=1`(로컬)이 첫 실행에 잡았다. 상세 → QA · 결정·교훈.

### `npm run look:online` — 계정 둘 · 브라우저 둘로 진짜 대기열 (10-07)

과제 문에 「온라인 두 탭(`?seat=1`/`?seat=2`)」이 적혀 있었는데 클라이언트 어디에도 `seat`가 없었다 — H3a(로그인, 2026-08-20)가 지웠고, 같은 브라우저의 탭 둘은
`localStorage` 세션을 함께 써 **같은 계정**이 된다. **CLAUDE.md 머리와 HANDOFF §5 「화면 확인용 통로」**는 두 달 가까이 없는 통로를 안내하고 있었다.

`tools/online_look.ts`:

- Supabase Admin API로 계정 둘 · `createProfile(이름, 7)` + `addSquad`(King · Queen · Rock)를 `saveProfileTrusted`로 심는다 — **같은 시드 = 같은 장수 = 전투력 644 대 644 → 서로 매칭.**
- Playwright 컨텍스트 둘(700px 판 = 1000×1400)로 간판부터 들어가, 진짜 대기열에서 붙어 매칭 · 배치 · **대기** · 정찰 · **상대 차례 팝업**(400ms · 3초 · 7초) ·
  상대가 넘긴 뒤 · 결과를 OS 임시 폴더에 찍는다.
- 판 전체가 `try/finally` 안 — 예외로 끝난 첫 실행이 계정을 안 지웠다(남은 두 계정 `눈확인-A/B-…`은 DB에서 찾아 지웠다).
- 생각하는 쪽에 `meditate`를 보냈는데 MP가 가득이라 서버가 거절했다 — **거절은 화면에 안 돌아온다**(온라인은 `submit()`이 `true`를 돌려준다). 늘 받는 `endTurn`으로 바꿨다.
- `smoke:online`의 `[grain] items 실패 … status=404` 줄은 그 스모크의 계정이 프로필 없이 대기열만 쓰기 때문이다(판은 그대로 돈다 — §5-61).

### 매칭의 [AI 대전하기] (10-08)

온라인 검색 중 바닥에 [AI 대전하기 (5)] — 5초 뒤 켜지고(`aiReadyMs()`, `?match=fast`는 1초), 누르면 대기열을 닫고(`search.close()`) 30초 시간 초과 뒤와 같은 화면으로.

### Supabase Pooler 연결이 수 초씩 걸렸다 (10-06, 6단계 마무리)

`smoke:meta`가 「로그인했는데 계정 API를 부르지 않는다」(두 번) · 「개발용 지급이 서버에서 돌아오지 않는다」(한 번)로 떨어졌다. 계정 API 로그의 `/profile` 응답이
**7~15초**였고, DB에 직접 붙어 재 보니 **연결만 3.6~14.6초**, 질의는 0.3초였다 — Transaction Pooler까지의 연결이 느린 것이다. 이번 변경은 전투 화면(클라이언트)뿐이라
그 경로를 지나지 않고, 같은 코드로 세션 시작 때는 완주했다. 연결이 회복된 뒤 다시 돌려 **완주를 보고 나서** main에 합쳤다.
