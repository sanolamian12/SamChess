## 관리자 API

### 1단계 — 구조 · 조회 · 지급 · 회수 · 감사 로그 (10-20)

운영용 관리자 페이지를 시작했다. **화면은 별도 저장소 `../SamChessAdmin`**(React + Vite, 5174), **API는 이 저장소 `packages/server-api/src/admin/`**(따로 도는 프로세스, 8788).
처음 파악한 대상 — 유저 데이터는 `profiles(uid, data jsonb)` 한 행에 통째로 들어 있고(이메일 · 가입일 · 마지막 로그인은 `auth.users`), 게임 데이터는 엑셀 → JSON으로 코드에
묶여 있어 실행 중에 못 바꾸며(서버가 AI 대전을 같은 데이터로 재생 검증하므로 서버 값만 바꾸면 화면과 어긋난다), 계정을 바꾸는 쓰기는 전부 `mutateProfile()`을 지나야 한다.
관리자 페이지 원칙은 9월 결제 검토 문서 §5.6에 이미 있었다(서버가 권한 확인 · 모든 조작 감사 로그 · 사유 필수 · 금화는 결제로만).

| 자리 | 내용 |
|---|---|
| `admin/auth.ts` | `verifyAdmin()` — `/auth/v1/user` 응답의 `app_metadata.role === 'admin'`. 매 요청 DB 값을 보므로 역할을 거두면 바로 막힌다 |
| `admin/store.ts` | 검색(`auth.users` 기준 — 도시 없는 계정도) · 상세(**저장하지 않는** 정산) · `mutateWithAudit` · 감사 로그 · 집계 |
| `admin/routes.ts` | `/admin/me` · `stats` · `users` · `users/:uid` · `users/:uid/adjust`(사유 필수) · `audit` · `gamedata` |
| `meta/src/admin.ts` | 지급 · 회수 규칙(순수 — 시스템 엔지니어 문서) |
| `profileStore.ts` | 정산 순서를 **`syncAtServer()`** 한 함수로 뺐다 · `mutateProfile`에 `onWrite` 훅(쓴 직후 · 커밋 전 · 같은 연결) |
| `sql/schema.sql` | `profiles` RLS · `admin_audit_log`(+RLS) |
| 도구 | `npm run admin-api` · `admin:role -- <이메일>` · `smoke:admin` |

- **관리자 API를 별도 프로세스로** — 운영에서 이 포트만 사내망 뒤로 숨길 수 있고 CORS 허용 주소가 다르다. 같은 행을 같은 `for update`로 고치므로 게임 API와 서로 덮어쓰지 않는다. HOST 기본값 127.0.0.1.
- **감사 로그는 같은 트랜잭션** — 처음엔 `mutateProfile` 사본을 admin에 뒀다(본체에서 다른 세션이 디버깅 중이라 기존 파일을 못 고쳤다). 본체가 비자 `onWrite` 훅으로 합치고
  사본을 지웠다. 거절된 조정은 쓰기도 로그도 없다.
- **들여다보기는 저장하지 않는다** — 게임의 `getProfile()`은 읽으며 정산을 되쓰지만, 관리자가 본 것만으로 계정이 바뀌면 안 된다. 같은 `syncAtServer`를 메모리에서만 돌린다(도적떼는 출몰시키지 않는다).
- **역할은 화면에서 안 준다** — 관리자 하나가 털리면 관리자를 늘릴 수 있게 된다. 서비스 키를 쥔 도구(`admin:role`)만.
- **`before`/`after`는 바뀐 최상단 필드만** — 행이 커지지 않게. 정산으로 바뀐 몫(군량 충전)도 섞여 들어간다.
- 게임 데이터는 **(a) 읽기 전용으로 시작**(기획자 결정) — 실행 중 수정((b))은 서버 · 클라이언트가 같은 값을 읽는 구조가 먼저 필요하다.

### 2단계 — 계정 정지 · 해제 (10-20 ~ 10-21)

**실측**(관리자 쪽) — 정지하면 Supabase가 **정지 전에 받은 토큰도 바로** `/auth/v1/user` → `403 user_banned`, refresh · 로그인 → `400 user_banned`. SQL로 `auth.users.banned_until`을 써도 똑같다.

본체 사전 검토에서 짚은 것(전부 반영):

1. 대전 서버는 같은 함수가 아니라 **사본**(`server/src/auth.ts`) — 응답을 읽는 판정을 하나로(`@samchess/meta`의 `readAuthUser()`, 세 곳이 함께 쓴다).
2. **이미 시작된 판은 못 막는다** — 재접속 · `reserveSeatFor`가 `onAuth`를 안 다시 부르고, 끝나면 서버 간 비밀로 `/internal/battle-result`에 온다 → `settleOutcome()` 맨 앞에서
   정지면 거절(판은 끝까지 두되 보상 없음).
3. 401이 아니라 **403 `account_banned`** — 401이면 게임 화면이 오프라인으로 물러난다.

**계약(게임 화면이 받는 모양)** — 게임 API `403 { error: 'account_banned', until: ISO|null, reason: string|null }`(오류 처리기 하나 `server-api/src/ban.ts`) · 대전 서버
`ServerError(403, 'account_banned')` · Supabase 로그인 `400 error_code: user_banned` · 상수 `ACCOUNT_BANNED`. 관리자의 「영구」는 100년이다.

관리자 API — `POST /admin/users/:uid/ban { days(1~36500), reason }` · `/unban { reason }`. `banned_until`과 `app_metadata.ban.reason`을 **감사 로그와 같은 트랜잭션**에서 쓴다.
자기 계정 · 관리자 계정은 거절. 게임 화면의 「정지된 계정입니다」 안내는 본체가 넣었다(`ac845f8` — 클라이언트 엔지니어 몫).

### 관리자 MFA (TOTP) — `b7544ce` (10-21)

- **실측** — 비밀번호 로그인 = `aal1`, TOTP verify 뒤 = `aal2`, refresh해도 `aal2`. aal1로는 인증된 factor를 지우거나 새로 더하지 못한다(`insufficient_aal`). 등록하다 만 factor는
  aal1로 지워진다. **factor를 지워도 받아 둔 aal2 토큰은 만료까지 aal2** — 그래서 서버는 토큰의 `aal`과 `/auth/v1/user`의 `factors`(verified totp)를 둘 다 본다(왕복은 그대로 하나).
- `verifyAdmin` → `unauthorized | forbidden | mfa_required`. **역할을 먼저** 본다(관리자 아닌 계정에 등록을 시키지 않는다). `403 { error: 'mfa_required' }`.
- 복구는 `npm run admin:role -- <이메일> --reset-mfa`(등록하다 만 것까지, 역할은 그대로) · `--list`에 MFA 여부. 화면에는 지우는 길이 없다.
- 화면 쪽에서 걸린 것 — REST의 `qr_code`는 **SVG 원문**(supabase-js가 data URI로 감싸 준다) · StrictMode가 effect를 두 번 불러 등록이 겹쳐 `Factor not found`.

### 우편 — 게임 쪽 경로와 관리자 보내기 · 회수 (10-21)

**보내는 것은 DB `mail` 표에 한 줄 적기로 끝난다.** 바로 지급(수천 계정을 하나씩 고치기)을 안 고른 이유: 끊기면 어디까지 줬는지 따로 세야 하고, 판 도중의 계정을 건드리고,
「나중에 가입한 사람」을 가를 수 없다.

- **게임 쪽**(`44b6bf3`) — `GET /mail` · `POST /mail/:id/read` · `/claim`. 받기는 `mutateProfile`이 행을 잠근 채 「이미 받았나 → 보상 → 적기」를 한 트랜잭션에서 한다.
- **「이 사람에게 보이는가」는 쿼리 하나**(`server-api/src/mail.ts`의 `visibleMail`) — 회수 안 됨 · 기한 전 · 나에게 또는 전체(보낸 시각 ≥ `auth.users.created_at`). 목록과 읽음 · 받기가
  같은 쿼리를 지나 번호로 남의 우편을 받지 못한다. **안 보이는 것은 이유를 가르지 않고 모두 404**(번호를 넣어 보며 남의 우편이 있는지 알아내지 못하게).
- 받으면 서버가 고친 계정이 함께 와서 화면이 갈아 끼운다.
- `mail` 표는 `npm run db:migrate`로 개발 DB에 적용, RLS 켬.
- **관리자 쪽**(`03fd7dc`) — `POST /admin/mail`(MailDraft + reason → `parseMailDraft`의 말 그대로 400, 한 사람이면 없는 계정 404) · `POST /admin/mail/:id/revoke`(사유 필수, 이미 회수 ·
  기한 지남 400) · `GET /admin/mail?status=live|expired|revoked&target=&before=` · `GET /admin/mail/audience`.
- **보내는 시각 · 기한은 DB `now()`** — 보이는 우편을 고르는 쿼리가 DB 시각(`auth.users.created_at`)과 비교하므로 같은 시계여야 한다(관리자 쪽 제안, 동의).
- 우편 한 줄과 감사 로그(`mail.send` · `mail.revoke`)가 같은 트랜잭션 · **회수는 `revoked_at`만 찍고 계정을 안 고친다** · **받은 수는 기한 전까지만 맞다**(`mailbox` 줄이 기한 뒤 걷힌다).
- ⚠ `smoke:admin`은 **전체 공지**를 실제로 보냈다가 곧 회수 · 삭제한다 — 개발 DB 실계정에도 몇 초 보인다(보상 없음). 운영에서는 안 돌리기로 10-22에 정했다(아래).

### 역할 나누기 (관리자 / CS) — 판정 · 하루 합계 · 정지 줄이기 구멍 (10-21)

권한 표와 CS 상한(관리자의 1/10, 하루 합계 × 5)은 게임 디자이너 문서, 순수 규칙은 시스템 엔지니어 문서. 서버의 판정 자리는 그대로 하나다.

- `verifyAdmin()`이 `role`을 함께 돌려준다 — `app_metadata.role`이 `ADMIN_ROLES`에 없으면 `forbidden`. MFA는 CS도 똑같이 요구한다.
- `requireAdmin(req, reply, perm)` — 경로마다 필요한 권한을 적는다. 권한이 없으면 **403 `{ error: 'role_forbidden', need }`**(역할 자체가 없는 `forbidden`과 가른다 — 화면이 「이 일은 관리자에게」를 말할 수 있게).
- **조정 경로는 본문을 보고 나서 권한을 정한다** — 같은 `/adjust`가 지급이면 `grant`, 회수면 `revoke`. 정지도 일수를 본다.
- **하루 합계는 감사 로그에서 센다** — 따로 세는 표를 두지 않는다(감사 로그가 이미 정본). 세기 전에 `pg_advisory_xact_lock(hashtext('admin-cs:' || uid))`로 그 CS의 요청을 줄 세운다
  (앞말을 붙여 다른 잠금과 섞이지 않게, 순서는 늘 「계정 행 → 이 잠금」). 넘으면 **403 `cs_limit { kind, scope: once|daily, limit, used, amount, message }`**.
- 감사 로그에 `admin_role` 칸 — `alter table admin_audit_log add column if not exists admin_role text not null default 'admin'`(옛 줄은 전부 관리자였다). 관리자 쪽이 개발 DB에 적용.
- `npm run admin:role -- <이메일> --role cs | --role admin | --revoke`, `--list`는 역할 · MFA를 함께. `/admin/me`가 역할 · 권한 · CS 오늘 양을 준다 — **막는 것은 언제나 서버다**.

**본체 검토에서 잡은 것 — 정지를 짧게 덮어쓰면 사실상 해제다** — `banTx`가 이미 정지된 계정에 다시 정지를 걸면 끝나는 시각을 `now() + days`로 **덮어써**, CS가 관리자의 영구 정지를
1일로 줄일 수 있었다 — `unban` 권한 없이 해제가 된다. 고친 것(`79b6dc7`): 잠근 행에서 DB 시계로 「정지 중이고 `now() + days`가 지금 끝나는 시각보다 이른가」(`shortens`)를 읽어,
그러면 `unban`도 요구한다(403 `role_forbidden`, need `unban`). 같은 길이 · 더 긴 정지는 그대로 된다. → 결정·교훈 참조

### 손으로 맞춘 값을 계약으로 — 리터럴 타입 + `satisfies`, 안 되면 응답에 시각 (10-22)

관리자 화면은 서버 응답 타입을 `import type`으로 읽어 모양이 바뀌면 `npm run typecheck:admin`이 깨지는데, 인수인계서 §3-2의 값들은 화면이 숫자 · 문자열을 **다시 적고** 있어서
본체가 바꿔도 아무 오류가 없었다. 화면은 `import type`만 쓴다(값을 import하면 SamChess 코드가 번들에 들어간다). 그래서 두 갈래로 나눴다.

| 갈래 | 언제 | 어떻게 |
|---|---|---|
| **리터럴 타입 + `satisfies`** | 값이 코드에 리터럴로 적힌 상수 | 계약이 `typeof X`(리터럴 타입)를 내보내고 화면이 같은 값을 적어 `satisfies`로 묶는다 — `MAIL_LANGS`가 이미 하던 방식 |
| **응답에 싣기** | 엑셀에서 오는 값 · 계정마다 다른 값 | 서버가 정산과 같은 함수로 계산한 **시각**을 응답에 싣는다 |

| 값 | 전 | 후 |
|---|---|---|
| 정지 「영구」 36500 | `store.ts`의 `BAN_DAYS_MAX`, 화면 두 곳 | meta로 옮김 → `BanDaysMax`. 화면 `BAN_FOREVER_DAYS = 36_500 satisfies BanDaysMax` 하나 |
| CS 정지 상한 7 | 화면 `SHORT_MAX_FALLBACK = 7`(§3-2에 없던 것) | `7 satisfies CsBanDaysMax` — `AdminMe.cs.banDaysMax`도 이 타입 |
| 감사 로그 `action` 이름 | 서버는 `string`, 화면 `Record<string, string>` | **`AdminAuditAction`** 유니언(`adjust.${…}` · `resolve.${…}` · `ban` · `unban` · `mail.send` · `mail.revoke`)과 묶음 `AdminAuditActionGroup`. 서버 `insertAudit()` · `mutateWithAudit()`이 이 타입만 받는다 |
| 우편 기한 30일 | meta 곱셈(`number`), 화면 `30` | `MAIL_TTL_DAYS = 30` 리터럴 → `MailTtlDays` |
| 시간 규칙 경고(AI 60분 · 도적떼 대기 10분 / 전투 60분) | `ResolvePanel.tsx`의 문장 | `UserDetail.autoResolveAt { aiBattle, raid }` — meta의 `aiAbandonAt()` · `raidAutoSurrenderAt()` |
| 판 종류 | 화면 세 벌 | 계약이 `CarriedBattle`을 내보내고 화면 `Record<CarriedBattle, string>` 하나 |
| 한 쪽 50줄 | 화면 안의 중복 | `PAGE_SIZE` 하나(화면이 정해 보내는 값, 서버는 200까지) |

시각을 실은 이유 — 분(AI 60분은 곱셈, 도적떼 10분 · 60분은 `RAID.*Minutes` — 엑셀)은 타입이 `number`라 묶이지 않고, **도적떼 응전 시간은 컬렉션(`raidResp`)으로 계정마다 늘어난다** —
화면의 「대기 10분」은 그 계정에서 이미 틀린 문장일 수 있었다. 분을 실어 화면이 더하게 하면 규칙을 화면이 다시 짓는 것이다. 경고는 이제 「그냥 두면 10/22 15:40(응전 마감)에 같은
처리가 된다」처럼 그 계정의 실제 시각을 말한다.

**올리지 못한 것**(인수인계서 §3-2에 이유와 함께) — 감사 로그 `params`의 모양(`jsonb`에 옛 줄이 남는다 — 지금 모양으로 박으면 옛 줄에 거짓말을 한다) · 정리의 뜻을 적은 문장 ·
대장간 「Lv × 1분이라 정리 대상이 아니다」 · `syncAtServer()`의 범위 · 게임 데이터 표시 문구 · 새 재화를 넣을지.

| 자리 | 내용 |
|---|---|

### DB 연결 끊김에 게임 API가 죽던 것 — `withCheckout()` (10-21)

관리자 세션이 실측한 버그. `db.ts`의 `pool.on('error')`는 **쉬는** 연결만 받고, `pool.connect()`로 꺼낸 연결이 트랜잭션 중 끊기면 리스너가 없어 **프로세스가 통째로 내려간다.**
`server-api/src/checkout.ts`의 `withCheckout(connect, label, fn)`(리스너 달기 · 떼기 · 끊긴 연결은 `release(err)`로 버림)을 `mutateProfile()`이 지난다. 관리자 `setBan`도 이것으로
옮겼다(리스너를 떼지 않고 끊긴 연결을 풀에 돌려주고 있었다). **새 트랜잭션은 반드시 `withCheckout`.** 회귀 `server-api/test/checkout.test.ts`는 이 패키지의 **첫 테스트**다.
`profileStore.ts`의 연결 리스너는 관리자가 찾았지만 본체가 고쳤고(공용이라도 본체 소유 파일), 관리자 파일(`admin/store.ts`의 `setBan`)은 그쪽에 맡겼다.

### 개발 / 운영 Supabase 분리 준비 (10-22)

결정(기획자) — **지금 프로젝트 = 개발, 운영은 새로 만든다**(저장소의 `.env`가 그대로라 다른 세션 · 스모크 · 도구에 영향이 없고, 운영은 시험 흔적 없이 시작한다). **운영 프로젝트는 배포 직전에**.
「프로젝트가 둘이면 과금되나」 — **무료 플랜은 활성 2개까지 $0**(3개째는 청구가 아니라 생성이 막힌다), TOTP MFA는 모든 플랜 무료. 대신 **무료 프로젝트는 1주일 활동이 없으면 잠든다** —
출시 전에 만들어 두면 잠들어서 「배포 직전」이 맞다. 실제 서비스는 Pro($25/월) 검토. **운영에서는 `smoke:admin`을 돌리지 않는다** — 운영 확인은 `db:check:prod`와 실제 플레이로.

| 자리 | 내용 |
|---|---|
| `server-api/src/environment.ts` (새) | `SAMCHESS_ENV`(`development` · 비움 · `production`, **오타는 개발로 물러나지 않는다**). 운영이면 게임 API가 **개발용 지급 켜짐 · `SAMCHESS_WEB_ORIGIN` 없음(CORS 전부 열림) · 내부 비밀 32자 미만**을 하나하나 적고 뜨지 않는다. 순수 함수 + 회귀 3건 |
| `server-api/src/main.ts` | 부팅 때 그 검사. CORS `?? true` → `\|\| true` — `.env.example`을 그대로 복사한 빈 칸이 CORS 주소(빈 글자)가 되어 모든 요청이 막히는 것을 막았다 |
| `tools/db_check.ts` (새) · `db:check` / `:prod` | **읽기만** — 프로젝트 ref · `SAMCHESS_ENV`, `schema.sql`이 만드는 표 · 인덱스(목록을 그 파일에서 읽어 스키마가 늘면 검사도 는다), public 표 **전부**의 RLS, Auth 설정(이메일 가입 · 익명 로그인 · 확인 메일), 서비스 키로 Admin API, 계정 · 관리자 수. 운영이면 관리자 0명 · 시험 계정이 ✗ |
| `tools/devOnly.ts` (새) | `refuseProduction()` — `smoke:admin`이 운영 표시에서 시작하지 않는다 |
| `package.json` | `db:migrate:prod` · `db:check` · `db:check:prod` · `admin:role:prod` — 운영은 **이름으로 골라야만** 간다(`--env-file=.env.production`) |
| `docs/운영_Supabase.md` (새) | 운영 프로젝트를 만드는 순서 · 키 목록 · 값이 사는 파일 · 운영에서 하지 않는 것. 공개 저장소라 실제 ref · 키는 안 적었다 |
| `SamChessAdmin/.gitignore` | `.env.*` + `!.env.example` — 전에는 `.env` · `.env.local`만 막아 Vite의 `.env.production`이 커밋에 섞일 수 있었다 |

알게 된 것 — **코드에 프로젝트 주소가 하나도 박혀 있지 않았다**(전부 환경 변수). 표도 넷뿐이고 전부 `schema.sql`에 있어 `db:migrate` 한 번이면 선다. 손으로 맞출 것은 **대시보드 설정**
(확인 메일 · Site URL · 리디렉트 · SMTP)과 관리자 역할뿐이다. 개발 프로젝트는 「확인 메일」이 켜져 있다(`mailer_autoconfirm: false`) — 운영도 같게 둔다. **`vite build`는
`.env.production`을 `.env`보다 앞세운다** — 운영 파일이 생기면 로컬 빌드도 운영으로 로그인한다(개발 서버는 그대로). 스모크 · `*_ux` 도구 20여 개에는 운영 거절을 넣지 않았다 — 전부
`--env-file=.env`만 읽어 구조로 이미 개발에 묶여 있다. `smoke:admin`(전체 공지를 보내는 유일한 것)에만 두 번째 문을 달았다.
