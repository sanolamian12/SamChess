## 대전 서버·네트워크

### H1 — 전송 층을 가른다, 서버 코드 0줄 (08-19)
**동작은 한 글자도 안 바뀌었다** — 스모크 둘이 갱신 없이 통과한 것이 증거다. 바뀐 것은 「누가 상태를 만드는가」다. 합 10개 파일 · +1,042 / −166, 저장 형식 무변경.
```
예전   [Playback] ──apply()/advanceTime()/takeTurn()──▶ [룰 엔진]
지금   [Playback] ──의도──▶ [BattleTransport] ──▶ 판정 주체 (로컬: 룰 엔진 · 온라인: 서버)
            ◀──「이렇게 됐다」(ServerMsg)──
```
**계약 — 메서드 넷과 통 하나** (`client/src/battle/transport.ts` 신규)
```ts
interface BattleTransport {
  readonly initial: BattleState; readonly humanSide: Side | null;
  open(inbox: (msg: ServerMsg) => void): void;   // 첫 통이 여기서 온다
  send(intent: Intent): void;                    // 결과는 inbox로 돌아온다
  ready(): void;                                 // 「나는 밀리지 않았다」 — 로컬만 듣는다
  close(): void;
}
interface ServerMsg { t: 'sync'; state: Omit<BattleState,'log'>; events: BattleEvent[]; deadlineInMs: number | null; }
```
- 떼고 붙이는 자리는 각각 하나 — `toWire()` · `applyWire()`. 갈래를 `sync` 하나로 둔 것은 일부러다.
- **이음매가 하나여야 했던 이유** — `Playback`이 네 자리(내 의도 · 상대의 수 · 시간 진행 · 마감)에서 직접 상태를 만들고 있었고 넷 다 온라인에서 「도착한다」로 바뀐다. 각각 갈아 끼우면 갈래가 여덟이 된다. 하나로 모으니 「바뀌는 것은 상대가 사람인지뿐」이 코드에서 성립한다.
- **`LocalTransport`는 흉내가 아니라 정말 판정한다** — 주소가 여기일 뿐이라 서버가 꺼져 있어도 AI 대전이 돈다. `open()`은 첫 통을 보내고 배치 단계면 상대 대신 `ready`를 낸다. `send()`는 `validate()` → `apply()`, 거부는 우리 UI의 버그라 던진다. `ready()`는 상태를 보고 `control`이면 상대의 `takeTurn`, `running`/`scout`면 `advanceTime`. 온라인과 다른 것은 **즉시 답한다** · **기다려 준다** 둘뿐.
- **로그를 떼어 보낸다 — 실측**

| | 스냅샷(로그 제외) | 로그 포함 | 턴 |
|---|---:|---:|---:|
| 3v3 | **2,408 B** | 27,743 B | 48 |
| 5v5 | **3,705 B** | 55,089 B | 104 |

  로그를 실으면 매 턴 보내는 통이 판 길이에 비례해 전선에서 `O(턴²)`다(`cloneState()` 로그 지뢰가 네트워크에 다시 나타나는 것). 받는 쪽이 이벤트를 이어 붙여 되만들고, 엔진의 `commit()`이 `이전 로그 ++ events === 다음 로그`를 보장한다. **이벤트만 보내는 길은 안 골랐다** — 리듀서가 없고 만들면 `apply()`의 두 번째 구현이다. 스냅샷을 보내면 어긋남이 구조적으로 불가능하고 **재접속이 덤으로 풀린다**(돌아온 사람에게 스냅샷 한 통).
- **마감은 「남은 ms」로 싣는다** — 서버와 사람의 시계가 몇 초씩 어긋나 있어서. 받는 쪽이 제 시계로 `지금 + 남은 ms`를 만든다. 단계가 **바뀔 때만** 다시 잰다(통마다 재면 배치 중 30초가 되살아난다).
- **Colyseus 상태 동기화(`@colyseus/schema`)를 안 쓴다** — `BattleState`를 다시 적으면 상태가 두 벌이 되어 「룰 엔진을 서버와 클라가 같은 코드로 돌린다」(HANDOFF §3)를 정면으로 어긴다. Colyseus는 **방 · 전송 · 재접속**으로만 쓴다. Schema의 데코레이터는 Node 타입 스트리핑이 못 넘기므로 이것이 물리적 제약이기도 했다. → 결정·교훈 참조

### H2a — 대전 서버와 방, 사람 둘이 처음으로 붙었다 (08-19)
H1의 계약(`BattleTransport` · `ServerMsg`)은 한 글자도 안 바꿨다.
```
H2a  [Playback] ──▶ [BattleTransport] ──▶ OnlineTransport ──ws──▶ [BattleRoom] ──▶ room-logic
                                                                   (얇은 껍데기)   (순수)
```
| 파일 | 줄 | 무엇 |
|---|---:|---|
| `packages/server/src/room-logic.ts` 신규 | +380 | 방의 규칙 전부 — 순수, 시각을 인자로 |
| `packages/server/src/BattleRoom.ts` 신규 | +145 | Colyseus 껍데기, 판정 0줄 |
| `packages/server/src/{protocol,clock,index,main}.ts` 신규 | +120 | 메시지 모양 · 서버 시계 · 배럴 · 부팅 |
| `packages/rules/src/wire.ts` 신규 | +130 | **전선 계약이 rules로 올라왔다**(양쪽이 본다) |
| `packages/client/src/battle/online.ts` 신규 | +140 | `OnlineTransport` · `connectBattle` |
| `tools/smoke_online.ts` 신규 | +200 | 진짜 서버로 한 판(브라우저 없이) |

- **순수 층과 껍데기를 갈랐다.** 굳는 규칙(배치 30초 · 정찰 30초 · 제어 20초 · 넘기기 3번 · 재접속 유예 60초 · 유휴 2분 · 이탈 표 네 줄)은 전부 기다려야 일어난다 — 손으로 확인하려면 탭 둘을 띄우고 분 단위로 세야 하고 그러면 아무도 다시 안 본다. `step(room, event, nowMs)`가 시각을 받아 가짜 시계로 한 판을 통째로 민다. 껍데기(`BattleRoom`)는 자리 배정 · `step()`으로 넘기기 · `out`을 진영별로 뿌리기 · 250ms마다 시계 보기 넷뿐이다.
- **굳은 계약 다섯**
  1. 전선의 `phase`는 **받는 사람의 걸음** — `toWire(state, side)`가 `ready[side] && phase === 'deploy'`면 `waiting`을 넣는다. `waiting`은 한쪽만의 사실이라 공유 상태에 못 넣는다(넣으면 아직 배치 중인 상대가 판을 못 만진다). 마감도 갈린다(배치 중이면 `DEPLOY_MS`, 준비 끝이면 `WAITING_MS` 잔여).
  2. 제어 20초를 화면이 따로 재던 자리(`controlModal.ts`의 `FORCE_SKIP_AFTER_MS` + `performance.now()`)를 없앴다 — 제어 단계에도 `deadlineInMs`를 싣고 화면은 그것만 읽는다. `ServerMsg`에 필드를 더하지 않았다.
  3. **성립하지 않은 판은 엔진의 결말이 아니다** — 배치 중 이탈 · 양쪽 이탈 · 양쪽 유휴는 서버가 마지막 통에 `close: RoomClose`를 싣고 받는 쪽은 `applyBattleResult`를 아예 안 부른다(환불만). 정찰 이후 이탈은 서버가 사라진 쪽 대신 `{t:'surrender'}`를 적용 — 평범한 결말이다.
  4. **배치 프리셋은 서버가 깐다** — `BattleScreen`이 깔면 북군(P2) 프리셋이 「내가 언제나 남군」인 오프라인에서 한 번도 안 돈다. 이제 두 사람의 프리셋이 각각 깔리고, 어긋나면 여전히 아무 말 없이 안 깐다.
  5. 시간 셋의 **관계**가 규칙이다(`TIMING_INVARIANTS`, 시스템엔지니어 문서).
- **의존성 고정** — `@colyseus/core@0.16.22` + `@colyseus/ws-transport@0.16.5` + `colyseus.js@0.16.22`. `colyseus` 메타 패키지는 안 쓴다. → 결정·교훈 참조(버전 짝 지뢰)
- 배럴(`index.ts`)과 부팅(`main.ts`)을 갈랐다 — 스모크가 `BattleRoom`만 빌리려다 포트를 잡던 문제.
- `OnlineTransport`는 `opened`로 받은 첫 스냅샷을 큐에 넣어 두었다가 `open()`에서 흘린다(`LocalTransport`와 같게).
- 개발용 통로 `?match=room`(방 이름 고정, 탭 둘이 만난다) · `?seat=N`(저장 키와 **재접속용 `deviceId`를 함께** 가른다).
- **알고 둔 공백**: 서버는 아직 참가비·거절 군량을 검증하지 않는다(§5-61 · H3) — `room-logic.ts` 머리에 적었다.

### H2b — 대기열과 거절 (08-20)
```
QueueRoom ──search──▶ queue-logic.enqueue() ──matched──▶ 둘 다 confirm
                                     │ matchMaker.createRoom('battle') + reserveSeatFor() × 2
클라 ──consumeSeatReservation()──▶ BattleRoom (여기서부터 H2a와 완전히 같다)
```
`BattleRoom.ts` · `room-logic.ts`는 한 글자도 안 바뀌었다. 방을 여는 자리는 `@colyseus/core`가 이미 가진 `matchMaker.createRoom` + `reserveSeatFor` — 메타 패키지가 필요 없다.
- **대기열을 두 번째 방으로** 만든 이유: 매칭된 뒤에도 둘 다 [전투준비]를 눌러야 방이 열리므로(§5-60) 「찾음 → 확인 대기」는 아직 전투가 아니다. 판정 층에 전투 아닌 상태를 섞으면 나중에 걷어 낼 일이 생긴다.
- `queue-logic.ts`(순수, 시각을 인자로)는 넷뿐이다 — `enqueue(state, entry, priority?)`(같은 모드 · 서로 안 피함 · `isAdjacentPower`인 상대가 있으면 즉시 매칭, 매칭 폭은 안 넓힌다) · `confirm(state, matchId, playerId)` · `decline(state, matchId, deciderId, nowMs)`(거절한 쪽은 `avoid` 기억 + 재대기, 거절당한 쪽은 패널티 없이 재대기) · `gone(state, playerId, nowMs)`(대기 중이면 즉시 빼고, 확인 대기 중이었으면 상대만 되돌린다 — 진짜 거절이 아니므로 기억 안 남김).
- **굳은 계약**: 거절당한 쪽만 대기열 앞으로, 거절한 쪽은 맨 뒤 · 검색 시간 제한(`ONLINE_SEARCH_MS`)은 「찾을 때까지만」(매칭 뒤 확인 대기·재매칭엔 상한 없음) · 대기열엔 재접속 유예가 없다(끊기면 즉시 정리) · `?match=room` · `?match=online` 삭제, `?match=fast`만 남음.
- 클라이언트 `matchmaking.ts`: `send('search')`보다 먼저 `onMessage(...)`를 건다 · 나가는 자리는 `left` 플래그로 감싼 `leaveQueue()` 하나(타임아웃 · `close()` · 방이 열린 뒤 셋이 전부 그것만 부른다). → 지뢰는 결정·교훈 참조

tools/migrate_db.ts    npm run db:migrate — schema.sql 적용(멱등)

- **토큰 검증은 매 요청 `${SUPABASE_URL}/auth/v1/user` 호출** — JWKS 로컬 검증은 트래픽이 커지면(지금은 0이라 잴 수도 없다).

- Supabase 자격 증명에서 세 번 넘어졌다(IPv6 전용 Direct connection → Transaction Pooler, 자리표시자 대괄호, 비밀 키 두 형식). → 결정·교훈 참조

### H3a 클라이언트 절반 — 로그인과 서버 정본 (08-20)
이걸로 H3a가 끝났다.
```
client/src/meta/auth.ts      (신규) Supabase Auth REST 직접 fetch — signUp·signIn·signOut·getAccessToken(자동 갱신)
client/src/meta/storage.ts   (재작성) 동기 localStorage → 비동기 GET/PUT /profile. 로컬은 읽기 전용 캐시(samchess.profile.cache)
server/src/auth.ts           (신규) server-api/src/auth.ts와 같은 검증, 별도 사본
server/src/{QueueRoom,BattleRoom}.ts  static onAuth. Enlist.playerId를 서버가 덮어쓴다
server-api/src/main.ts       @fastify/cors(GET,PUT 명시)
server-api/src/profileStore.ts  getProfile()이 되접힌 값을 그 자리에서 되쓴다
```
- **`@supabase/supabase-js`를 안 쓴다** — Auth REST는 엔드포인트 셋(로그인 · 회원가입 · 리프레시)뿐이고 최소 의존성 우선.
- **세션은 `client.auth.token`(colyseus.js)이 실어 나른다** — 설정하면 `joinOrCreate`가 `_authToken` 쿼리로 보내고, 서버의 `static onAuth(token, options, context)`가 `context.token`으로 받는다. Colyseus 자체 인증 모듈은 안 쓴다(인증은 Supabase, Colyseus는 검증만). `onAuth`는 **계정 데이터를 안 읽고 신원 확인만** 해서 §5-54를 안 깬다.
- **`BattleRoom.onAuth`는 대기열이 예약한 좌석에는 안 걸린다** — `matchMaker.reserveSeatFor(room, options, authData)`의 셋째 인자로 `QueueRoom`이 검증한 uid를 실으면 `BattleRoom.onJoin(client, options, auth)`가 `client.auth`로 받는다. `reserveSeatFor` 직접 호출은 HTTP 매치메이크가 아니라 `callOnAuth`를 안 지난다. `BattleRoom.onAuth`는 개발용 고정 방(`smoke_online.ts` 전용) 직접 접속에만 걸린다 — 이중 검증 없이 신원 확인이 이어진다.
- `Enlist.playerId`가 `deviceId` 문자열에서 **서버가 검증한 Supabase uid**로. `?seat=N` 개발용 통로를 지웠다.
- **쓰기 큐** — 앞 저장의 응답을 기다린 뒤 다음 요청을 시작한다(겹친 `PUT`이 늦게 도착해 최신 값을 덮던 문제). **CORS `methods`를 명시**(기본값이 `PUT`을 빠뜨렸다). → 결정·교훈 참조
- `getProfile()`이 되접은 결과가 저장된 것과 다르면 그 자리에서 되쓴다.

### H3b — 참가비 · 거절 군량 · 환불 서버 재검증 (08-21)
H3a는 신원만 검증했고, 참가비 · 거절 페널티 · 환불은 클라이언트 계산 그대로 `PUT`되어 API를 직접 부르면 군량을 공짜로 채울 수 있었다.
```
server-api/src/internalAuth.ts   (신규) /internal/*의 인증 — 서버 간 공유 비밀(INTERNAL_API_SECRET)
server-api/src/profileStore.ts   applyGrainAction() — spendGrain·declineMatch·refundGrain(@samchess/meta)을 서버 프로필에 재적용
server-api/src/routes.ts         POST /internal/grain
server/src/economy.ts            (신규) chargeGrain(uid, mode, action) — server-api를 fetch로. 실패해도 로그만
server/src/QueueRoom.ts          openBattle()이 좌석 예약 전에 참가비를 기다림 · doDecline()이 거절 군량을 void로
server/src/BattleRoom.ts         dispatch()가 RoomClose.refund를 재계산시킴
.env / .env.example              SERVER_API_URL · INTERNAL_API_SECRET
```
- **사용자 액션 엔드포인트(`POST /match/spend` 같은)가 아니라 Colyseus 셸이 `server-api`를 직접 부르는 내부 API**를 골랐다 — 참가비 · 거절 · 환불은 `QueueRoom`/`BattleRoom`이 이미 권위 있게 결정해 둔 사건이라, 그 순간 직접 반영하면 「같은 방을 두 번 정산」 같은 멱등성 문제를 새로 안 만든다.
- **순수 판정과 부수효과를 갈랐다** — `room-logic.ts` · `queue-logic.ts`는 한 글자도 안 바꿨다. 네트워크 I/O는 판정이 끝난 뒤의 부수효과로 셸에 둔다(`out` 통을 뿌리는 자리와 같다).
- **참가비는 좌석 예약 전에 기다리고**(`Promise.all` 뒤 `createRoom`) — 「참가비는 방이 열린 순간에」(§5-84)가 서버에서도 지켜지게. **거절 · 환불은 `void`로 안 기다린다** — 이미 큐 재배치·방 종료가 끝난 뒤의 정산이라 흐름을 막을 이유가 없다.
- **실패해도 판을 막지 않는다** — 「`server-api`가 꺼져 있어도 게임은 돈다」(§5-61). 재시도 큐 같은 내구성 장치는 범위 밖.
- **알고 남긴 공백**: `PUT /profile`은 여전히 `grain`을 통째로 신뢰 — 정상 클라이언트 흐름만 막았다(H3d가 닫음).
- AI 대전 서버 이관은 이 세션에서 **갈라 미뤘다**(§5-96) — Colyseus 방이 없어 이 패턴이 적용될 자리가 없고 훨씬 큰 일이 된다.

### H3c — AI 대전: 로컬 재생 + 서버 검증 (08-21)
첫 안(봇이 앉은 `BattleRoom` — `drive()`의 `control` 단계에 「봇 자리면 `takeTurn()`」만 얹고 `QueueRoom`에 `wantAi` 메시지)을 사장님 지적으로 뒤집었다. → 결정·교훈 참조
```
client/src/battle/transport.ts  LocalTransport.getIntentLog() — 사람이 낸 의도를 순서대로 쌓는다
client/src/meta/aiBattle.ts     (신규) settleAiBattle() — POST /battle/ai-result, 실패하면 null(로컬 폴백 신호)
client/src/meta/storage.ts      authedFetch export
client/src/screens/BattleScreen.tsx  AI 승/패를 settleAiBattle()에 먼저 맡기고, 실패할 때만 로컬 applyBattleResult
server-api/src/aiBattle.ts      (신규) settleAiBattle(uid, body) — 계정에서 로스터·배치를 다시 만들고 replayLocalMatch()로 검증한 뒤 applyBattleResult()
server-api/src/routes.ts        POST /battle/ai-result (사용자 토큰)
server-api/src/main.ts          CORS methods에 POST 추가
```
- 사람 쪽 로스터 · 배치 프리셋은 **서버가 가진 계정에서 직접 다시 만든다** — 클라이언트가 능력치·레벨을 자칭할 수 없다.
- 판마다 살아 있는 상태가 필요 없는 **한 번 계산하고 끝나는 요청**이라 부하가 판 길이·동시 접속자 수에 얽매이지 않는다(`npm run balance`가 초당 수천 판을 돌리는 것과 같은 종류).
- `packages/server`(Colyseus)는 한 글자도 안 건드렸다 — 이 설계는 Colyseus를 지나지 않는다.
- 무승부(실측 0.02%)는 택1 규칙 때문에 이 경로를 안 쓰고 클라이언트가 로컬 반영(낮은 심각도 공백). 서버 다운이면 예전 방식(로컬 계산 + `PUT`)으로 물러난다.
- `/battle/ai-result`는 **브라우저가 직접** 부르는 POST라 CORS에 `POST`를 미리 더했다(`/internal/grain`은 서버 간이라 문제가 없었다) — 실제로 막히기 전에 잡은 몇 안 되는 자리.

### H3d — `PUT /profile`의 grain 신뢰 마감 (08-21)
H3b · H3c가 같은 문장으로 남긴 공백 둘 — **온라인 대전의 보상 반영**과 **시간 기반 군량 충전** — 을 닫았다. 사장님께 두 질문을 물어 「`BattleRoom` → server-api 직접 호출 + `'settled'` + 실패 시 로컬 폴백」 설계대로, 그리고 「PUT도 같이 막는다」로 정했다.

**재생(H3c)이 아니라 직접 호출(H3b 패턴)인 이유** — 온라인은 `BattleRoom`이 `step()`으로 이미 실시간 판정을 해 왔다. `room.battle.phase === 'finished'`가 되는 순간의 `room.battle` 자체가 권위 있는 최종 상태라 다시 계산할 이유가 없다.

서버(Colyseus)
- `BattleRoom.dispatch()`에 `settled` 플래그. `res.closed`가 아니라 `phase === 'finished' && winner !== null`이 되는 순간(한 판에 한 번) `settleFinished()` — 자연 종료(king down · wipe out · time limit)와 정찰 이후 이탈의 강제 항복 둘 다 덮는다.
- `settleFinished()`는 양쪽 진영 각각 `economy.ts`의 새 `settleBattleResult()`를 부른다 — `Enlist.entries`에서 `picks`, `countKills()`로 `kills`, `battlePower()`로 `power`. 응답 `rewards`를 그 좌석에게만 새 메시지 **`'settled'`**로 돌려준다.
- `protocol.ts`에 `Settled` 타입 — `ServerMsg`(rules의 `wire.ts`)에는 안 얹었다. rules가 meta(계정 보상)를 알면 계층이 깨진다.
- `settleFinished()`는 `room.battle`을 **읽기만** 한다 — 그래서 「Colyseus는 방·전송·재접속만」 경계가 안 깨진다(H3b와 같은 잣대: 부수효과, 판정이 끝난 뒤).

server-api
- `battleResult.ts`(신규) — `settleOutcome(uid, outcome, seed)` 하나로 「읽고 `applyBattleResult()` 불러 저장」을 모았다. `aiBattle.ts`도 이걸로 리팩터 — AI · 온라인 · 무승부가 같은 마지막 한 걸음을 쓴다.
- `POST /internal/battle-result`(공유 비밀) — 온라인 승/패, `BattleRoom`만 부른다.
- `POST /battle/draw-result`(사용자 토큰) — 무승부 택1, AI · 온라인 공통. 이 경로가 없으면 `PUT`이 grain을 안 믿는 순간 **무승부 군량 보상이 조용히 사라진다.**
- `profileStore.getProfile()`이 되접기와 같은 자리에서 **`syncGrain(profile, Date.now())`을 서버 시계로** 매번 계산하고 바뀌면 되쓴다. `applyGrainAction` · `settleOutcome` 등 전부 `getProfile()`을 거쳐 공짜로 최신값 위에서 계산된다.
- `saveProfile(uid, raw)`(클라이언트 `PUT` 전용)는 기존 행이 있으면 들어온 `grain` · `grainAt`을 **조용히 버리고** 서버 값으로 덮는다(최초 1회 이전만 예외 — 지킬 정본이 아직 없다). `saveProfileTrusted(uid, profile)`(신규)는 서버가 방금 계산한 값 저장 전용이라 grain을 안 지킨다. **이름을 갈라 둔 것 자체가 안전장치**다.

클라이언트 쪽 연결
- `BattleTransport`에 선택적 `waitForSettled?(timeoutMs)` — `LocalTransport`는 안 채운다. `OnlineTransport`는 **리스너를 생성자에서 건다**(H2b의 리스너 경주를 반복하지 않으려고) — 방에 붙는 즉시 거는 `Promise`를 타임아웃과 경주시킨다.
- `BattleScreen`: 온라인이고 무승부가 아니면 `waitForSettled(3000)` → 받으면 `rewards`를 화면에 쓰고 `loadProfile()`로 **다시 읽는다**(로컬 계산을 정본으로 안 쓴다). 못 받으면 로컬 `applyBattleResult` + `PUT`.
- `meta/battleResult.ts`(신규) — `/battle/draw-result` 래퍼(`authedFetch` 재사용, 실패 시 `null`). `ResultScreen.pick()`이 먼저 부르고, 실패하면 로컬 반영 — 그 경우 카드·재료는 `PUT`이 받지만 **grain만 놓칠 수 있다**(§5-61과 같은 결의 대가로 받아들였다).
- `exactOptionalPropertyTypes: true`가 `kills?:`에 `undefined`를 명시적으로 넣는 걸 막아, 스프레드(`...(b.kills ? { kills: b.kills } : {})`)로 세 군데를 맞췄다.

**알고 남긴 공백**
- `/battle/draw-result`의 `picks` · `kills` · `power`는 클라이언트 값 — 판정 주체가 사라진 뒤에 오므로 재검증할 대상이 없다(낮은 심각도).
- **온라인 대전의 `enlist.entries`(로스터 — 능력치·레벨)는 여전히 클라이언트가 대는 값**이다. `BattleRoom.openRoom()`이 그대로 믿고 전투를 만든다. 범위 밖이었고 §5-103 이후 결정 이력이 없어, 건드리려면 기획자에게 먼저 물어야 한다.
