# 이상 징후 감시 — 설계 · 구현 (2026-11-12)

관리자가 하지 않았는데 장수 카드 · 금화 등이 늘어나는 것 같은 **이상상태를 1시간마다 찾아 관리자 화면 목록에 올린다.**
기획자 결정(2026-11-12):

- 방식 **B — 변화 장부 + 1시간마다 점검** (스냅샷 비교만 하는 A는 「왜 늘었나」를 몰라 버린다)
- 잡으면 **「이상 징후」 목록에 올리고 관리자가 보고 처리한다** — 자동 정지 · 자동 회수는 없다
- 알림은 **나중에** — 관리자가 등록한 메일로 받는다(이번 범위 밖)
- 정의는 **① 출처 없는 변화 · ② 불변식 위반 · ④ 수상한 시도**부터. ③ 속도 이상 · ⑤ 전투 통계는 기획 수치가 정해진 뒤

## 0. 전제 — 감시할 값은 이미 서버만 바꾼다

금화 · 장수 카드 · 보유 장수 · 군량 · 자재 · 건물 · 건설 기회 · 시장 아이템 · 컬렉션은 `SERVER_OWNED_FIELDS`(`meta/authority.ts`)이고
`PUT /profile`은 그 값을 버린다. 그래서 이 감시가 잡는 것은 **클라이언트 조작이 아니라 서버의 버그 · 악용 경로 · DB 직접 수정**이다.

그리고 **계정을 쓰는 길은 전부 `profileStore.ts`의 `transact()` 하나를 지난다** — 게임 API · 관리자 API · 읽기(`getProfile`)까지.
장부는 그 한 자리에 붙인다. 예외는 `saveProfileTrusted()`(스모크 · 도구 전용)와 DB를 직접 고치는 것 둘이고, 둘 다 아래 ①-b가 잡는다.

## 1. 장부 — `account_ledger` (새 표)

`transact()`가 **실제로 쓸 때만**(지금도 같은 값이면 안 쓴다) 같은 트랜잭션 안에서 한 줄을 남긴다. 감시하는 값이 하나도 안 바뀐 쓰기
(AI 대전의 수 덧붙이기 등 — 가장 잦은 쓰기)는 **줄을 안 남긴다.**

| 칸 | 뜻 |
|---|---|
| `id` · `at` · `uid` | 줄 번호 · 시각 · 계정 |
| `source` | **어느 길로** — 요청의 라우트(`POST /battle/ai-result`, `POST /admin/users/:uid/adjust` …). 요청 밖이면 `tool` |
| `phase` | `sync`(읽는 순간의 서버 시계 정산 — 군량 충전 · 60분 방치 정산 등) / `action`(그 요청이 한 일) |
| `delta` | 감시하는 값의 **바뀐 만큼** (JSON — `{gold:+300, cards:{"jo-un":+2}, roster:+1 …}`) |
| `after` | 감시하는 값의 **쓴 뒤 값** — ①-b(장부 밖에서 바뀐 것)를 찾는 기준 |
| `audit_id` | 관리자 조치면 그 감사 로그 줄 |

- **라우트 이름은 요청마다 저절로 붙는다** — Fastify 훅이 `AsyncLocalStorage`에 라우트를 넣고 `transact()`가 읽는다.
  호출하는 함수 수십 곳에 인자를 더하지 않는다(빠뜨린 곳이 「출처 없음」으로 보이는 일이 없게).
- `sync`와 `action`을 **가른다** — 지금 `transact()`는 「읽고 정산(`syncAtServer`) → 고치기(`fn`)」를 한 번에 쓰는데, 정산이 한 변화
  (예: `GET /profile`이 60분 지난 AI 대전을 패배로 정산해 보상 카드가 들어옴)를 그 요청의 라우트 탓으로 적으면 「조회했는데 카드가 늘었다」가 된다.
  장부는 두 단계의 차이를 따로 적는다.
- 감시하는 값: 금화 · 군량 · 자재 · 건설 기회 · 장수 카드(장수마다) · 보유 장수(수 · 레벨) · 건물(레벨) · 시장 아이템 · 병기 · 컬렉션.
  군량은 시간으로 늘 차므로 `sync` 줄이 잦다 — **군량 충전만으로 생긴 `sync` 줄은 안 남긴다**(줄 수를 지킨다. 군량의 이상은 ②가 본다).
- 보관: **90일**(점검이 지운다). 장부는 덤으로 **금화 입출금 내역**이 된다 — 관리자 계정 상세에 「변화 내역」 탭(같은 범위에 넣는다).
- RLS를 켠다(CLAUDE.md 규칙).

## 2. 이상의 정의

### ① 출처 없는 변화 — 있으면 버그

- **①-a 허락되지 않은 길로 늘었다.** 값마다 「늘릴 수 있는 길」 표를 meta에 둔다(`ledgerSources.ts`, 예: 금화를 늘리는 길 = 전투 정산 ·
  우편 받기 · 카드 정리 · 관리자 지급 · 개발용 지급). 표 밖의 길로 늘면 징후. 줄어드는 쪽은 안 본다(쓰는 길이 많고 해가 없다).
  - **표는 손으로 적지 않고 회귀가 지킨다** — 라우트마다 그 길의 meta 함수를 시험 계정에 돌려 「실제로 늘리는 값」과 표가 맞는지 본다.
    새 라우트가 금화를 늘리는데 표에 없으면 회귀가 떨어진다(운영에서 오탐으로 처음 아는 일이 없게).
  - `sync` 단계는 길이 아니라 **무엇이 정산됐나**로 본다 — 카드가 늘었으면 그 쓰기에서 AI 대전 · 도적떼 · 연구가 정산됐어야 한다.
  - **운영에서 `/dev/grant`로 바뀐 것**은 언제나 징후다(운영은 그 길이 막혀 있어야 한다).
- **①-b 장부 밖에서 바뀌었다.** 점검이 계정마다 지금 값과 장부의 마지막 `after`를 비교한다. 다르면 DB를 직접 고쳤거나
  `saveProfileTrusted()` 같은 장부 밖의 길이 쓴 것이다. 장부가 생기기 전 계정은 첫 점검에서 기준만 잡는다(징후 아님).

### ② 불변식 위반 — 있을 수 없는 상태

meta의 순수 함수 `profileInvariants(profile)` 하나가 판정하고 점검이 전 계정에 돌린다(관리자 계정 상세도 같은 함수로 띄울 수 있다).

- 금화 · 군량 · 자재 · 건설 기회 · 카드 · 아이템 개수가 음수이거나 정수가 아니다
- 장수 레벨이 1 미만 · 최대 초과, **`growth.length !== level − 1`**(CLAUDE.md의 「언제나 참」)
- 건물 레벨이 그 도시 레벨이 허락하는 것보다 높다, 도시 레벨이 범위 밖
- 보유 장수가 전체 장수 수보다 많다, 없는 장수 id · 없는 아이템 id
- 가챠 뽑은 수가 풀 크기보다 크다
- 군량이 상한을 넘는다(시장 구매로 넘을 수 있으면 그 상한으로 — 구현 때 규칙에서 낸다)

숫자를 새로 적지 않는다 — 상한은 전부 데이터(`growth.json` · `buildings.json` · `economy.json`)와 기존 함수에서 낸다.

### ④ 수상한 시도 — 서버가 거절한 것

정상 클라이언트로는 거의 안 나오는 거절을 **같은 계정에서 1시간 안에 센다.**

| 거절 | 문턱 | 왜 |
|---|---|---|
| `ai.revealByServer`(대결 공개를 사람이 적음) | 1번 | 정상 클라이언트는 절대 안 보낸다 |
| `ai.replayFailed` · `raid.replayFailed`(재생 불일치) | 2번 | 버전이 엇갈린 판 하나는 있을 수 있다 |
| `ai.intentsRejected` · `ai.intentsGap` 등 수 덧붙이기 거절 | 5번 | 네트워크 재전송으로 가끔 난다 |
| 온라인 방이 손에서 온 판정 의도(`REFEREE_INTENTS`)를 버림 | 1번 | 대전 서버(Colyseus)가 게임 API에 알려야 해서 **2차** |

거절은 장부 옆 `account_rejects`(uid · 시각 · 코드 · 라우트)에 한 줄씩 남긴다. 문턱 값은 운영하며 바꿀 수 있게 한곳에 둔다.

## 3. 점검과 목록

- **점검(`scanAnomalies`)**: 1시간마다. 게임 API 프로세스의 타이머가 돌리고(관리자 API는 늘 떠 있지 않다), 여러 대가 떠도 한 번만 돌게
  DB 잠금(`pg_try_advisory_lock`)을 쓴다. 손으로도 돌린다: `npm run anomaly:scan`. 지난 점검 뒤의 장부 · 거절만 보고(①-a · ④),
  ①-b · ②는 전 계정을 본다(지금 규모에서는 몇 초. 커지면 「지난 점검 뒤 쓴 계정」으로 좁힌다 — ①-b는 장부 밖 쓰기라 `profiles.updated_at`으로).
- **징후 표 `anomalies`**: 계정 · 종류(①-a · ①-b · ② · ④) · 무엇이(값 · 길 · 코드) · 근거(장부 줄 id들) · 처음 본 때 · 마지막 본 때 · 상태.
  **같은 계정 · 같은 종류 · 같은 값이 열려 있으면 새 줄을 안 만들고 「마지막 본 때」만 민다** — 목록이 같은 일로 넘치지 않게.
- **상태**: `open`(새로) → `ok`(정상으로 판정 — 사유 필수) / `fixed`(조치함 — 사유 필수, 회수 · 정지는 기존 패널로 하고 그 감사 로그를 잇는다).
  처리는 감사 로그에 `anomaly.resolve` 한 줄(같은 트랜잭션). 권한은 새 권한 `anomaly`(관리자 · CS 둘 다 — 보고 판정하는 일이다).
- **관리자 화면**: 메뉴 「이상 징후」 — 열린 것 먼저, 종류 · 상태로 거르기, 줄을 누르면 계정 상세로. 대시보드에 「열린 징후 n」.
  계정 상세에 「변화 내역」 탭(장부)과 그 계정의 징후.

## 6. 구현 결과 (같은 날 — 단계 1 · 2 · 3 끝, 브랜치 `anomaly`)

### 설계에서 바뀐 것

- **①은 쓰는 순간 판정한다** — 장부 줄에 `unexpected`(그 길로는 늘 수 없는 묶음)를 적고, 점검은 그 줄만 모은다. 점검이 나중에 다시 내려면
  쓰기 전 · 후의 계정이 통째로 있어야 하는데(「읽는 순간 AI 대전이 정산됐나」) 그것은 쓰는 순간에만 있다.
- **①-b(장부 밖 변화)도 쓰는 순간 본다** — 설계대로 점검만 보면, DB를 직접 고친 뒤 **평범한 요청이 그 계정을 한 번 쓰면** 새 `after`가 그 변화를
  삼켜 점검이 못 본다. 그래서 줄을 얹기 전에 읽은 값을 장부의 마지막 `after`와 견주어, 다르면 `baseline` 줄에 판정 `outside`를 단다(감시 값이 바뀐
  쓰기만 — 색인 한 번). 점검의 전 계정 비교는 그 뒤로 아무도 안 쓴 계정을 맡는다.
- **②는 저장된 값 그대로에 본다** — `migrateProfile()`이 읽을 때마다 깨진 것을 조용히 고친다(레벨은 성장 스택에서 다시 내고 도시 · 건물은 범위로 자른다).
  고친 뒤에 보면 아무것도 안 걸려 `ledger_ux`의 첫 실행이 떨어졌다. 저장 형식이 지금 버전이 아닌 옛 줄만 되접은 값으로 본다.
- **레벨은 「Lv1 위로 올린 수」로 적는다** — 새로 든 Lv1 장수가 「레벨이 올랐다」로 잡혀 가챠 · 전투 정산이 회귀에서 떨어졌다(풀에 드는 것과 레벨업을 가른다).
- 「늘릴 수 있는 길」 표의 회귀는 **두 겹**이다 — 게임 API · 관리자 API의 **쓰기 라우트 목록과 표가 같은가**(`server-api/test/ledgerSources.test.ts`,
  새 라우트를 표에 안 적으면 떨어진다 — 단계 3에서 실제로 잡았다) + **대표 meta 함수가 표 밖으로 늘리지 않는가**(가챠 · 군량 · 레벨업 · 전투 정산,
  `meta/test/ledger.test.ts`). 라우트마다 meta 함수를 다 돌리는 것은 안 했다 — 라우트가 50개를 넘는다.
- 불변식에 **「도시 상한을 넘은 장수 레벨」**(`officerLevelCap`)을 더했고, **군량 상한은 안 본다**(시장 구매 · 보상 · 환불 · 지급이 넘겨 줄 수 있다).
- 감사 로그 이름 `anomaly.resolve` · 권한 `anomaly`(관리자 · CS) · 불변식 종류 `InvariantCode`(관리자 화면이 `Record`로 묶는다).

### 찾은 것 — 새 계정은 클라이언트를 믿는다

첫 `PUT /profile`(도시 만들기)은 **지킬 기존 행이 없어** 클라이언트가 만든 계정을 그대로 받는다(`saveProfile` — H3d가 「최초 1회 이전」으로 남긴 예외).
조작한 클라이언트는 금화 · 카드를 얹은 도시로 시작할 수 있다. 이번에는 **잡기만** 한다 — 장부의 `create` 줄을 `creationViolations()`(시작 꾸러미 =
`createProfile()`과 견줌)로 판정해 징후 `create`로 올린다. **구멍 자체는 남았다** — 막으려면 서버가 시작 꾸러미를 직접 만든다(장수 다섯은 시드에서).

### 확인한 것

- `npm test` · `typecheck` · `typecheck:admin` · 관리자 `npm run build`
- `tools/ledger_ux.ts`(진짜 게임 API · 개발 DB) — 새 계정 `create` 줄 · 장부 밖 쓰기 → 다음 쓰기의 `outside` 기준 줄 · 가챠 `action` 줄 · 조회는 줄 없음 ·
  요청 밖으로 금화 +500 → 판정 `gold` · 수 덧붙이기 틈 5번 → 거절 5줄 · 장부 밖 레벨 깨기 → 점검이 `outside` · `source` · `invariant` · `reject`를 올리고
  `create`는 없다 · 다시 점검해도 새 줄이 안 열린다
- `smoke:admin` 완주 — 관리자 지급이 장부에 출처와 함께(판정 없음) · 징후 목록 거르기 · 시험 계정 · 사유 필수 · 두 번 400 · 평범한 사용자 403 ·
  감사 로그 `anomaly.resolve`. 감사 로그 수(6 → 7) · CS 권한 목록(`anomaly` 더함)을 고쳤다 — 의도한 변경이다
- 관리자 화면(Edge, 1280 · 400px) — 대시보드 「열린 이상 징후」 · 목록 · 처리(검토 → 실행, 감사 로그 #) · 계정 상세 「변화 내역」. 첫 판은 시험 계정의 긴
  주소에 밀려 **처리 단추가 표 밖으로** 나갔다 — 계정 칸을 줄이고 「무엇이 · 근거」를 한 칸으로 합쳤다. 400px의 가로 넘침(37px)은 대시보드 · 유저 목록과 같다(골격의 것)
- 개발 DB 첫 점검: 계정 21 — 시험 도구가 도시 Lv1에 궁궐을 직접 올린 시험 계정 셋이 `invariant`로 걸렸다(실제 플레이로는 못 만든다 — 맞게 잡은 것)

### 운영에 올리기 전

- ⚠ `npm run db:migrate:prod` — 새 표 넷(`account_ledger` · `account_rejects` · `anomalies` · `anomaly_scans`). **표가 없으면 계정 쓰기가 전부 실패한다**
  (장부가 같은 트랜잭션이라서 — 수비군 `defenses`와 같은 결)
- 게임 API가 1시간마다 점검한다(뜬 지 1분 뒤 처음). 시험용 서버는 `SAMCHESS_ANOMALY_SCAN=off`. 손으로는 `npm run anomaly:scan`(운영 `:prod`)
- 남은 것: 메일 알림(관리자 메일 등록 뒤) · ③ 속도 이상 · ⑤ 전투 통계(기획 수치 뒤) · ④의 온라인 방 거절(대전 서버가 게임 API에 알려야 한다) ·
  새 계정 구멍 막기
