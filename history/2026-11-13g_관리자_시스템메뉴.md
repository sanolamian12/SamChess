# 관리자 「시스템」 — 서버 상태 · 트래픽 · 인프라 점검 (2026-11-13)

기획자 요청: 관리자 홈페이지에서 **구현된 인프라 점검**과 **서버 트래픽 안정성**을 본다. 설계 검토를 먼저 하고 정한 것:

- 메뉴 **하나**(「시스템」) + 탭 셋(**상태 · 트래픽 · 점검**), 순서도 제안대로(상태 → 점검 → 트래픽 → 배포 때 알림)
- 트래픽 기록은 **메모리만** — 며칠치 추이는 운영이 가까워지면 DB에
- **관리자만** 본다(새 권한 `system`, CS 없음)

(같은 시각 다른 세션이 튜토리얼 화면을 고치고 있어 브랜치를 바꾸지 않고 main에서 작업했다 — 그쪽 파일은 건드리지 않았다.)

## 1. 설계 — 숫자는 각 서버가 세고, 관리자 API는 모은다

이 작업 전에는 **트래픽을 세는 곳이 아예 없었다** — 서버 로그가 터미널에 찍힐 뿐, 요청 수 · 오류율 · 지연을 모으는 자리도, 상태 확인 길도 없었다.
그래서 화면보다 「세는 장치」가 먼저였다.

| 무엇 | 어디서 세나 | 관리자 API가 읽는 길 |
|---|---|---|
| 게임 API의 요청(경로 틀 · 상태 · 걸린 시간) | Fastify `onResponse` 훅(`server-api/src/health.ts`의 `attachTraffic`) | `GET /internal/health`(서버 간 비밀) |
| 대전 서버의 사건(대기열 입장 · 나감 · 방 열림 · 끊김 · 돌아옴 · 못 돌아옴 · 스스로 나감) | `BattleRoom` · `QueueRoom` 껍데기가 `countEvent()`(`server/src/traffic.ts`) — 순수한 방 규칙은 모른다 | 대전 서버의 내부 HTTP에 `GET /internal/health`(「전투」가 연 그 자리) |
| 관리자 API 자신 | 같은 `attachTraffic` | 직접 |
| 메모리 · 이벤트 루프 · DB 풀 · 방 · 대기열 | 각 프로세스 | 위 둘 |
| DB · Auth | — | 관리자 API가 한 번씩 두드려 왕복을 잰다(`select` 한 번 · `/auth/v1/health`) |

모양(`ProcessHealth` · `TrafficWindow` …)과 1분 칸에 쌓는 규칙은 **meta `system.ts`** — 두 서버 프로세스가 서로 import하지 않으므로(`LiveRoomSummary`와 같은 까닭).
순수하고 시각을 인자로 받는다. 최근 60분, 1분 칸, 응답 시간은 칸 셈(5 · 10 · 25 … 5000ms)으로 p95를 어림한다(칸의 위 끝 — 조금 크게 틀린다).
경로는 **틀**(`GET /mail/:id/claim`)로 센다 — 틀이 없는 요청은 「(없는 경로)」 한 줄. 실제 URL을 넣으면 두드리는 것만으로 줄이 끝없이 는다.
관리자 화면이 10초마다 묻는 상태 요청 자신과 `OPTIONS`는 안 센다(안 그러면 조용한 서버에도 늘 분당 6건이 찍힌다).

알림은 이 화면이 하지 않는다 — 관리자 API는 늘 떠 있지 않고, 꺼진 서버는 제가 꺼졌다고 말하지 못한다. 배포 때 외부 감시(공개 `/health`)가 맡는다.

## 2. 고친 것

**계약** — meta `system.ts`(`ProcessHealth` · `TrafficWindow` · `TrafficMinute` · `TrafficRoute` · `TrafficRecent` · `BattleEvent` · `ServiceId`,
`createTraffic` · `recordRequest` · `recordEvent` · `trafficWindow` · `trafficRecent` · `p95Of`), 권한 `system`(`ADMIN_PERMISSIONS` · `PERMISSION_LABELS`, CS 표에는 없음),
관리자 `AdminSystemStatus` · `SystemServiceRow` · `AdminSystemTraffic` · `AdminSystemChecks` · `InfraCheck` · `InfraGroup`.

**게임 API** — `health.ts`(트래픽 훅 · `processHealth` · `GET /internal/health`), `main.ts`가 건다.
**대전 서버** — `traffic.ts`(사건 셈) · `health.ts`(방 · 자리 · 대기열 — 자리는 방의 요약에서 세어 재접속 유예 중인 자리도 든다) · `internalHttp.ts`가 `/internal/health`도 받는다
(비밀을 본 **뒤에** 읽도록 값이 아니라 읽는 함수를 고른다). `QueueRoom.size()`.
**관리자 API** — `admin/system.ts`, `GET /admin/system/status` · `/traffic` · `/checks`(권한 `system`). 못 닿은 서버는 그 줄만 붉다 — 404면 「새 코드로 다시 띄웠는가」.
**인프라 점검** — `tools/db_check.ts`의 내용을 `server-api/src/infraCheck.ts`로 옮겼다. `npm run db:check`와 「점검」 탭이 **같은 함수**를 부른다(두 벌이면 한쪽만 낡는다).
보는 것이 늘었다 — 내부 비밀 길이(값은 안 보인다), **이상 징후 점검이 최근에 돌았나 · 실패했나**, 보관 정리가 도는가.
**관리자 화면** — `SystemPage.tsx`(메뉴 「시스템」, 권한이 있을 때만 · `#/system?tab=…`), 대시보드 카드(관리자만). 눈 확인 `npm run look:system`.

## 3. ★ 새 점검이 첫 실행에 잡은 것 — 이상 징후 감시가 하루 종일 죽어 있었다

`npm run db:check`를 처음 돌리자 「이상 징후 점검 — 마지막 실행이 실패했다」. `anomaly_scans`를 보니 **오늘 12번 연속 실패**였다(01:22 ~ 08:04 UTC):
`insert … violates foreign key constraint "anomalies_uid_fkey"`.

- 관리자 지급의 감사 줄은 계정을 지워도 `target_uid`가 남는다(외래 키 없음 — 기록이라서). 그 계정의 장부는 cascade로 지워진다.
- 점검의 지급 대조(`grantsInWindow`, 11-12)가 그 줄을 읽어 「안 들어감」으로 보고 **없는 계정에** 징후를 넣다가 외래 키에 걸려 **점검 트랜잭션 전체가 굴렀다.**
- 점검의 커서(`audit_to`)는 **성공한 점검에서만** 나아간다 → 다음 점검이 같은 줄을 다시 읽고 또 실패 → **영원히.**
- 시험 계정에 지급하고 지우는 도구(look · smoke)가 한 번 돌면 감시 전체가 멈췄다. 화면에는 「열린 이상 징후 0」으로만 보였다.

고침 — 지급 대조가 **지워진 계정의 감사 줄을 뺀다**(`exists (select 1 from auth.users …)`). 없는 계정에는 징후를 걸 데도 고칠 것도 없다.
손으로 점검을 돌려(#44) 성공 · 밀린 징후 5건이 열렸다. 커서가 그 줄을 지나 옛 코드로 떠 있던 게임 API의 다음 점검도 안 걸린다.
**교훈 — 커서가 성공에서만 나아가는 배치 작업은 한 줄의 실패가 그 뒤 전부를 막는다.** 이번 것은 「안 도는 갈래」의 사촌인데 **돌다가 굴러서** 안 돌았다 —
그래서 「점검」 탭에 「마지막 실행 · 실패」를 두었다.

## 4. ★ Windows의 이벤트 루프 지연은 타이머 눈금이다

첫 `/internal/health`가 **쉬는 프로세스에서 p50 31ms**를 냈다. `monitorEventLoopDelay({ resolution: 20 })`이 Windows의 타이머 눈금(약 15.6ms)의 배수를
지연으로 재고 있었다(resolution 10 → 15ms, setImmediate로 잰 실제 지연 0.1ms). 그대로 실었으면 「볼 것」 문턱(100ms)에는 안 닿아도 늘 30ms가 찍혀 아무도 안 믿게 된다.
**측정 바닥(히스토그램의 `min`)을 빼고, 사용률(`eventLoopUtilization`)을 함께** 싣는다 — 쉴 때 약 2ms, 200ms 막힘은 215ms로 그대로 잡힌다(실측). Linux는 바닥이 0에 가깝다.

## 5. 화면에서 보인 것 — 고치지 않고 적어 둔다

- **게임 API가 느리다** — `POST /presence` 평균 1.9초, `GET /profile` 0.9초, 최근 5분 p95 2.5 ~ 5초(개발 Supabase, 도쿄 pooler). 요청마다 `/auth/v1/user`로 토큰을
  검증하고 DB에 붙는다. 「볼 것」 문턱(p95 1초)에 늘 걸려 상태 탭이 노랗다 — 운영 리전 · 토큰 검증 캐시를 정할 때 다시 본다.
- **DB 왕복은 첫 번이 1.4 ~ 1.6초** — 관리자 API의 풀이 비어 있으면 TLS 연결부터 맺는다. 두 번째부터 약 180ms.
