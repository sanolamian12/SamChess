## 왜 이 작업인가

기획자가 `assets/Audio/`에 배경음악 3곡(상점·전투 비김·전투 패배), 효과음
13개, 고유기술 성우 대사 90개(18종 × 5개 언어)를 새로 넣어 두고 "이번
세션에서는 연결만 하자"고 요청하며 시작됐다. 연결이 끝난 뒤 실제로 눌러 보며
"환경설정 확인 버튼에서 소리가 안 난다" → "전투 중 소리가 그림보다 먼저
들린다" → "고유기술 연출이 너무 짧다, 도시 이름에 Q·E가 안 써진다"로 요청이
이어진, 전형적인 "붙이고 나서 눌러 보며 어긋난 것을 잡는" 세션이다. 마지막
버그(Q·E)의 원인을 설명하자 사용자가 "이참에 키보드 단축키를 전부 없애자,
모바일에서 키보드를 띄워 놓고 게임할 사람은 없다"고 방향을 정했다 — 호버
전용 효과를 이미 배제했던 것과 같은 논리다.

### 2. 효과음이 팝업 안에서 안 나던 버그

환경설정 [확인] 등 **팝업 8곳 전부**에서 확인 버튼을 눌러도 `select_confirm`이
안 울렸다. 원인: 모든 팝업이 `<div className="modal" onClick={(e) =>
e.stopPropagation()}>`로 안쪽 클릭을 감싸고 있다 — 바깥(`.modal-back`)까지
버블링되면 팝업이 닫히기 때문이다. `buttonSfx.ts`의 위임 리스너는 **버블
단계**의 `window`에 걸려 있었는데, `stopPropagation()`이 그 버블을 팝업
경계에서 막아 버려 리스너까지 아예 안 왔다.

고친 방법은 리스너를 **캡처 단계**(`{ capture: true }`)로 옮긴 것 — 캡처는
`window`에서 타깃으로 **내려가는** 길이라 안쪽에서 나중에 걸리는
`stopPropagation()`보다 항상 먼저 지나간다. 한 줄 수정으로 8개 팝업 전부가
한꺼번에 고쳐졌다.

### 3. 전투 중 소리·연출 타이밍 어긋남 세 건

**증상 세 가지** (사용자 보고)
1. 적이 공격할 때 피격 소리가 그림보다 먼저 들린다. 내 공격은 괜찮다.
2. 적이 책략을 쓸 때 대상이 먼저 아파하고 그 다음에야 카메라가 시전자로
   포커싱되는 것처럼 보인다. 책략 소리는 성공/실패와 무관하게 먼저 나야 하고,
   성공했을 때만 0.5~1초 뒤 디버프 띠·포커싱·피격 액션이 같이 나야 한다.
3. 처치할 때 사망 사운드 → 피격 사운드 → 액션 순으로 들린다. 액션과 피격
   사운드는 같이 나고, 사망 사운드는 점멸 시작에 맞아야 한다.

**공통 원인**: `BattleScene.playBurstFor()`가 이벤트가 도착한 **즉시**(연출
시간표 `t=0`) 효과음을 틀었다. 그런데 실제 타격·피격 자세는 카메라가 대상
자리에 도착한 **뒤**(`poses.ts`의 `CAM_LEAD_MS=600ms`)에야 뜬다 — 그래서 소리가
그림보다 먼저 났다. 내 턴에서 안 보이던 이유는, 카메라가 대개 이미 그 자리를
보고 있어 `look()`이 「같은 자리면 안 기다린다」 최적화로 `CAM_LEAD_MS`를 안
붙였기 때문이다.

**고침**: `poses.ts`의 `PoseDirector`에 카메라 큐·HP 큐와 같은 결의
**소리 시각표**(`SoundCue`)를 추가했다. `plan()`이 각 이벤트를 훑을 때 「실제로
그림이 뜨는 시각」(`hitAt`, 카메라 도착 이후)에 소리 큐를 심고,
`drainSounds()`가 지금 시각(`t`)에 닿은 큐만 한 번씩 꺼내 준다.
`BattleScene.update()`가 매 프레임 이걸 불러 `playSoundCue()`로 실제 재생을
맡는다 — `playBurstFor()`는 이제 화면 전체를 덮는 배너(`SkillFx`)와 판 안
오버레이(`BurstFx`)만 즉시 튼다(카메라 도착과 안 엮이는 것들이라 그대로 둬도
된다).

책략(2번)에는 **진짜 시각적 순서 버그**도 있었다 — `tacticCast`의 "성공" 갈래가
대상의 피격 자세(`show()`)를 카메라를 대상으로 옮기는 `look()`보다 **먼저**
스케줄링하고 있었다(다른 모든 갈래는 `look()` → `show()` 순인데 이 갈래만
거꾸로였다). 그래서 피격 자세가 카메라가 도착하기도 전에 이미 떠 있었다 —
`look()`을 먼저 부르고 그 뒤 커서(카메라가 실제로 도착한 시각)에 `show()`를
놓는 것으로 다른 갈래와 같은 순서로 맞췄다.

디버프 띠(지속형 시각 효과 링)도 같은 문제였다 — `state`는 판정이 이미 끝난
값이라 `ringsOn()`이 그 자리에서 곧바로 새 링을 보여 준다. `HideCue`(`{unit,
vfx, until}`)를 새로 둬서, 책략이 성공해 새로 걸린 상태의 링을 카메라가
도착하는 시각(피격 자세가 뜨는 바로 그 시각)까지 `BattleScene.syncRing()`에서
걸러내게 했다.

`roar2`(§1에서 추가한, 배치/정찰→전투 전환 함성)도 이 참에 정확한 전환
시점(`lastPhase`가 `prep`에서 `battle`로 바뀌는 그 프레임)에 걸리도록
다시 확인했다.

**회귀 테스트**: `poses.test.ts`에 6개를 새로 추가했다 — `attackHit`/
`moveStart`/`dieBlink`/`castStart` 소리 큐 타이밍 4개, 책략 성공 시 카메라
지연을 재현하는 `positionedState()` 픽스처 기반 테스트 2개(피격 자세 지연 +
`HideCue` 노출 시각). **기존 `fakeState()` 픽스처가 유닛 `pos`를 안 채워
넣었던 것이 이 버그를 테스트에서 완전히 가리고 있었다** — 셀이 항상 `null`이라
두 번째 `look()`이 "같은 자리"로 오판해 `CAM_LEAD_MS`를 절대 안 붙였다.
새 테스트는 실제 좌표를 채운 상태를 써서 카메라가 **진짜로 이동해야 하는**
경우를 재현한다.

### 4. 고유기술 연출 길이 · 키보드 단축키 조사와 전면 제거

**고유기술 배너**: `ui/skillFx.ts`의 1단(시전자 얼굴) `FACE_MS`를 1초→2초,
2단(배너+이름) `HOLD_MS`를 2초→4초로 늘렸다(총 6초) — 성우 대사(4~6.5초)가
배너 구간 안에서 다 나오도록. `BattleScene.update()`가 이미 `this.fx.active`인
동안 `playback.update()`를 통째로 건너뛰므로, 상수만 바꿔도 "6초 동안 판이
멈췄다가 상대가 이어간다"가 그대로 성립했다.

**Q·E 안 먹힘 / M이 배경음악을 끄는 버그 조사**: 도시 이름 짓기 화면(순수
React, Phaser 없음)에서 왜 전투 단축키(Q·E)가 영향을 주는지가 핵심 의문이었다.
원인은 **`ControlModal`이 `window.addEventListener('keydown', …)`를 걸어 두고
한 번도 해제하지 않은 것**이었다 — `Phaser.Game.destroy()`는 자기가 모르는
(직접 `window`에 건) 리스너를 안 치운다. 전투를 한 번이라도 치른 뒤에는 그
판의 죽은 `ControlModal`이 Q·E(당시 활성 상태였던 「이동」·「공격」 버튼)를
영원히 가로채고 있었다 — 같은 패턴이 `BattleScene`의 F키(판 전체 보기)와
`InspectPanel`의 Esc(정보 팝업 닫기)에도 있었다. `M`이 음악을 끈 것은 별개
버그로, `bgm.ts`의 전역 M 단축키가 지금 포커스가 입력창인지 확인 안 하고
무조건 발동했기 때문이다.

**1차 수정** (누수만 막는 안): `ui/keyboardGuard.ts`(`isTypingInField()`)로
입력창 포커스 가드를 추가하고, `BattleScene`에 `AbortController`를 두어
`ControlModal`·`InspectPanel`·F키 리스너를 전부 그 신호에 묶은 뒤
`bootBattle`의 `destroy()`가 `scene.dispose()`로 확실히 끊게 했다.

**2차 — 사용자가 범위를 넓혔다**: "이참에 키보드 단축키를 전부 없애자, 모바일
환경과 동등하게 맞추고 싶다(호버 전용 효과를 배제했던 것과 같은 이유)"는
요청을 받고, 1차에서 고친 누수 자체의 원인(전역 키보드 리스너들)을 통째로
들어냈다.

- `ControlModal`: Q(이동)·E(공격)·R(책략)·M(명상)·Space(대기)·Esc(취소/뒤로)
  단축키와 `dataset.key` 매칭 로직, 버튼 툴팁의 "(Q)" 같은 표기를 전부 제거 —
  버튼을 누르는 것만 남았다.
- `InspectPanel`: Esc로 닫는 전역 리스너와 닫기 버튼 툴팁의 "(Esc)" 제거 — `×`
  버튼과 바깥 클릭만 남았다.
- `BattleScene`: F키(판 전체 보기) 제거 — 좌상단 `FocusToggle` 버튼이 이미 같은
  일을 한다.
- `bgm.ts`: M 음소거 단축키 제거 — 환경설정 팝업의 켬/끔 버튼이 이미 있어
  대체할 필요도 없었다.
- 1차에서 넣었던 `AbortController`/`dispose()`/`isTypingInField()` 정리
  장치는 **전역 키보드 리스너가 하나도 안 남으니 전부 걷어냈다** —
  `keyboardGuard.ts`는 호출부가 사라져 파일째 삭제했다.

  머리말 참조), 사용자가 직접 플레이하며 보고한 증상 → 코드 추론 → 수정 →
  사용자 재확인의 순환으로 진행했다.

## 이번 범위 밖 (다시 볼 자리)

- **고유기술 초상화 연출 자체의 시각 효과**(판 전체를 덮는 방식을 더 화려하게)는
  사용자가 "이건 내가 나중에 진행하겠다"고 명시적으로 미뤘다 — 이번엔 재생
  타이밍(§4)과 길이 조정만 했다.
- **고유기술 성우 22종**(40종 중 아직 녹음 안 된 것)은 자동으로 조용히
  건너뛰도록만 해 뒀다 — 채워지는 대로 `npm run audio`만 다시 돌리면 된다,
  코드 변경 불필요.
- **더빙 언어 매핑**(`DUB_FOR`, `CA`가 중국어권이라는 것 등)은 이미
  `i18n/index.ts`에 2026-08-25에 확정돼 있던 것을 그대로 가져다 썼다 — 이번
  세션에서 새로 정한 것은 아니다.
- **`select_confirm`/`select_option`이 정말 모든 버튼에 자연스러운지**는 화면
  하나하나 다 눌러 보지 않았다 — `.btn.primary` vs 나머지라는 이분법이 8개
  팝업·전체 화면의 모든 버튼에 맞는지는 실제 플레이에서 계속 확인이 필요하다.
- **`enter_barraks`/`enter_palace`가 장터(`market`) 진입에는 없다** — 사용자가
  이 세 자리 중 둘만 지정했고, 장터는 bgm 분기(`shop`)만 받았다. 의도된
  비대칭이지만 나중에 "장터도 효과음이 있어야 하나"로 다시 물을 수 있다.

## 새 대화로 이어갈 때

- 이 세션에서 **키보드 단축키는 완전히 사라졌다** — 앞으로 새 화면·기능을
  만들 때 `window.addEventListener('keydown', …)`로 단축키를 추가하지 않는다
  (모바일 우선 방침, 2026-08-26 확정). 꼭 필요하면 먼저 사용자에게 확인한다.
- 전투 사운드를 더 추가하거나 타이밍을 바꿀 일이 생기면 `BattleScene`에
  직접 `playSfx()`를 흩어 넣지 말고 `poses.ts`의 `SoundCue`/`HideCue` 시각표에
  큐를 심는 방식을 따른다 — 이번 세션이 겪은 "이벤트 도착 즉시 재생" 버그의
  재발을 막는 자리다.
- 다음 걸음 후보: ① 남은 22종 고유기술 성우가 들어오면 `npm run audio`로
  연결(코드 변경 없음), ② 고유기술 발동 화면 이펙트 리디자인(사용자가 직접
  진행 예정이라고 밝힘), ③ 전투 화면을 실제로 켜서 이번 세션에서 고친 소리
  타이밍·단축키 제거를 브라우저로 최종 확인.
