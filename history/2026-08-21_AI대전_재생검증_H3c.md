# 2026-08-21 — AI 대전 서버 이관 H3c: 로컬 재생 + 서버 검증

H3b(참가비·거절 군량·환불 서버 재검증)에 이어지는 세션. H3b는 온라인 매칭 경로만
서버 권위로 옮겼고, AI 대전은 §5-96으로 갈라 미뤄 뒀다 — 지금은 클라이언트 프로세스
안의 `LocalTransport`가 사람 쪽은 물론 **AI의 수까지** 판정하고, 이긴/진 것도 클라이언트가
계산해 `applyBattleResult()` 뒤 `PUT /profile`한다. 이번 세션이 그 자리를 다뤘다.

## 1. 설계 — 두 번 거쳤다

### 처음 안 — 봇이 앉은 `BattleRoom`

HANDOFF가 남긴 물음("새 방 종류? server-api가 룰 엔진을 직접 돌리는가?")을 따라
처음 짠 안은 H2a의 `BattleRoom`을 확장해 **한 자리가 사람이 아니라 서버 자신인
경우**를 처리하는 것이었다. `room-logic.ts`의 `drive()`가 `control` 단계에서
"서버는 재되 먼저 움직이지 않는다"고 멈추는 그 자리에 "봇 자리면 `takeTurn()`을
그 자리에서 부른다"만 얹으면 됐다 — 이미 250ms마다 도는 tick 루프가 봇의 수를
자동으로 밀어 주므로 새 이벤트 타입도, `BattleRoom`의 새 호출 자리도 필요 없었다.
대기열(`QueueRoom`)에도 `wantAi` 메시지 하나만 더해 온라인과 같은 `reservation`
파이프라인을 태우면 됐다.

**설계안을 보여 주자 사용자가 짚었다** — "서비스가 커지면 AI 대전을 이용하는
사람이 많아질수록 서버 부하가 심하지 않냐? 로컬에서 돌리고 결과만 서버로
올려서 검증하는 건 어떠냐?" 맞는 지적이었다: AI 대전은 [출정하기]의 기본 대체
경로(30초 안에 온라인 상대를 못 찾으면 자동으로 떨어지는 곳)라 온라인 대전보다
훨씬 자주 열리는데, 봇 자리가 있는 방은 **판마다 살아 있는 Colyseus 방 + 250ms
시계 하나를 그 판이 끝날 때까지 붙든다** — 동시 접속자가 늘면 그대로 서버 부하로
쌓인다.

### 뒤집은 안 — "로컬에서 그대로 두고, 결과만 서버가 재현해서 검증한다"

룰 엔진은 원래 결정적이다(`Date.now()`/`Math.random()` 금지). GDD §10이 "시드
기반 PRNG를 서버가 소유하고, 전투 로그에 시드와 소비 순서를 남겨 **리플레이·분쟁
처리를 가능하게 한다**"고 예고해 둔 자리가 바로 여기였다. AI 대전은 지금처럼
브라우저에서 실시간으로 돌리고(화면·속도·자원 소모 전부 그대로), 판이 끝난 뒤에만
서버가 개입한다 — 사람이 낸 의도의 **순서만** 서버로 보내면, AI의 수·시간 진행·
자동 준비는 전부 결정적이라 서버가 처음부터 다시 계산해 낸다.

이 방식은 판마다 살아 있는 상태를 요구하지 않는다 — `npm run balance`가 이미
초당 수천 판을 돌리는 것과 같은 종류의, **한 번 계산하고 끝나는 요청**이다.

`packages/server`(Colyseus)는 **한 글자도 안 건드렸다** — 이번 설계는 아예
Colyseus를 지나지 않는다.

## 3. 밟은 지뢰 하나 — CORS `methods`

CLAUDE.md에 이미 적혀 있던 교훈("`@fastify/cors`의 기본 `methods`를 믿지 않는다")을
또 만날 뻔했다. `main.ts`의 CORS 등록이 `['GET', 'PUT']`으로 고정돼 있었는데,
`/internal/grain`(H3b, POST)은 서버 간 호출이라 브라우저 CORS를 안 지나 문제가
없었지만 `/battle/ai-result`는 **브라우저가 직접** 부르는 POST다. 코드를 작성하며
발견해 미리 `POST`를 추가했다 — 실제로 막히는 걸 겪지 않고 넘어간 몇 안 되는
자리다.

## 4. 검증

`replay.test.ts`에서 처음 쓴 참조 시뮬레이션(사람은 항상 `endTurn`, AI는 실제
`takeTurn()`)의 로그가 `replayLocalMatch()`의 결과와 **이벤트 순서까지** 어긋났다
— 원인은 배치 단계에서 준비 순서였다: 실제 `LocalTransport.open()`은 **AI(비사람
쪽)가 먼저 자동으로 준비**하고 사람은 나중에 `ready`를 보낸다. 테스트의 참조
시뮬레이션이 반대 순서(사람 먼저)로 짜여 있어 로그 순서가 어긋났다 — `replay.ts`가
아니라 테스트 쪽 버그였다. 참조 시뮬레이션의 준비 순서를 고치자 통과했다.

```
npm run extract       → 검증 통과
npm run typecheck     → exit 0
npm test               → 429/429 (신규 replay.test.ts 4건 포함, room-logic 등 기존 것 전부 그대로)
npm run smoke:online  → 통과 (온라인 경로 무변경 확인)
npm run smoke:account → 통과 (무관한 변경 없음 재확인)
npm run smoke:meta    → 통과 — 새 assertion 포함, AI 대전 결과가 실제로
                         /battle/ai-result를 지나 DB에 반영되는 것을 서버 GET으로 확인
```

**서버 다운 시 로컬 폴백은 코드 검토로만 확인했다** — `settleAiBattle()`의
`try/catch`가 실패를 전부 삼켜 `null`을 주고, `BattleScreen.tsx`가 그러면 기존
`applyBattleResult()` 경로(H3c 이전과 완전히 같은 코드, 손 안 댔다)로 떨어지는
구조라 실측을 안 해도 확신이 크지만, 실제로 `server-api`를 끄고 AI 대전을 끝까지
확인해 보지는 않았다 — 검사가 안 잡는 것은 주장하지 말고 적어 둔다.

## 5. 다음 세션

**Colyseus 트랙에서 다음으로 정해진 것이 없다.** HANDOFF §7 맨 위 참조.

- `PUT /profile`의 grain 신뢰 문제(나머지) — 온라인 대전의 보상 반영과 시간 기반
  군량 충전(`syncGrain`)이 여전히 클라이언트를 믿는다. `settleAiBattle()`의 패턴

  설계 질문이다 — 다만 온라인은 이미 실시간 서버 판정이 있어 "결과를 지어낼" 여지가
  AI보다 작으므로, 급한 정도는 다시 볼 것
