# 회원가입 확인 메일 버그 수정 (2026-08-24)

트랙 9(상점/가챠)와는 무관한 별도 세션. 실사용자가 간판 화면에서 "계정 생성"을
눌렀다가 화면이 죽는 것을 그대로 스크린샷과 함께 보고했다.

## 증상 — 두 단계로 나타났다

**1단계.** 이메일·비밀번호 칸이 **비어 있는 채로** "계정 생성"을 눌렀더니
`Anonymous sign-ins are disabled`라는 알림만 뜨고 아무 일도 없었다.

**2단계.** 실제 이메일·비밀번호를 채워 넣고 다시 눌렀더니
`Cannot read properties of undefined (reading 'id')`로 화면이 죽었다.

## 1단계 — 버그가 아니었다

`signUp(email, password)`는 입력값을 그대로 Supabase의 `POST /auth/v1/signup`에
보낸다. 빈 문자열 `{email:"", password:""}`을 받으면 Supabase Auth는 이것을
**익명 로그인 시도**로 해석하는데, 이 프로젝트는 익명 로그인이 꺼져 있어(정상
설정) 그 에러를 그대로 돌려준다. 코드가 에러 메시지를 있는 그대로
화면에 띄우다 보니(`title.error`) Supabase 내부 사정이 사용자에게 그대로
노출된 것 — 실제 결함은 아니고, 입력을 채우고 다시 누르면 되는 상황이었다.

## 2단계 — 진짜 버그

`packages/client/src/meta/auth.ts`의 `toSession(t)`이 `t.user.id`를 읽는데
`t.user`가 `undefined`였다.

`signUp()`은 애초에 "확인 메일은 꺼져 있다"(개발 단계 결정, `auth.ts` 머리말
주석)는 전제로 짜여 있었다 — 회원가입이 성공하면 로그인과 똑같은 모양
(`{access_token, refresh_token, expires_in, user: {id, email}}`)이 곧바로
온다고 가정했다.

그런데 Supabase 프로젝트의 실제 Auth 대시보드 설정은 **"Confirm email"이
켜져 있었다** — 코드 주석의 가정과 실제 프로젝트 설정이 따로 놀고 있었던 것.
확인 메일이 켜진 프로젝트에서 `/auth/v1/signup`은 응답 모양이 완전히
다르다 — 세션 토큰 없이, 유저 필드를 `user`로 감싸지 않고 **응답 최상위에
바로** 돌려준다(`{id, email, email_confirmed_at: null, ...}`, `access_token`
자체가 없음). 그래서 `t.user`가 `undefined`였고, `.id`를 읽으려다 죽었다.

## 고친 것

두 갈래 해결책을 사용자에게 물었다 — (A) Supabase 대시보드에서 "Confirm
email"을 끈다(코드 변경 없음, 원래 의도한 설정으로 되돌리는 것뿐) vs (B) 코드가
확인 메일이 켜진 경우도 정상 처리하게 만든다. 사용자가 "이 세션에서 로그인 및
계정생성을 구현하자"고 답해 **(B)**로 진행했다 — 대시보드 설정에 의존하지
않고 코드가 두 경우 다 견디게 만드는 쪽이 더 견고하다는 판단.

- **`meta/auth.ts`** — `authFetch`(세션 응답을 요구하는 `signIn`/토큰 갱신 전용)와
  `rawAuthFetch`(원본 응답을 그대로 돌려주는 저수준 함수)를 갈랐다. `signUp()`은
  `rawAuthFetch`로 받은 뒤 `access_token`·`user`가 있는지 직접 확인해
  `{confirmed: true, session}` 또는 `{confirmed: false}`를 돌려준다 — 크래시
  대신 타입으로 두 경우를 구분한다.
- **`screens/TitleScreen.tsx`** — `run()` 하나로 로그인·회원가입을 같이 처리하던
  것을 `runSignIn()`/`runSignUp()`으로 갈랐다. `runSignUp()`은 `confirmed: false`를
  받으면 `onSignedIn()`을 부르지 않고 `confirmSent` 상태만 켠다.
- **`i18n/index.ts`** — `title.confirmEmail`("{email}로 확인 메일을 보냈다 —
  메일함을 확인한 뒤 입장한다.") 문구 추가.

## 확인

`npm run typecheck` · `npm test`(444/444) 전부 통과. 그 뒤 사용자가 실제
이메일로 직접 회원가입 → Supabase가 보낸 확인 메일 수신 → 메일의 확인 링크
클릭 → "입장"으로 정상 로그인되는 것까지 실사용으로 확인했다.

## 남는 것 (범위 밖으로 남겼다)

- 확인 메일이 **실제로 안정적으로 발송되는지**는 Supabase의 내장 SMTP 설정에
  달려 있다 — 기본 제공 메일 서비스는 시간당 발송 제한이 있다. 계정 생성이
  잦아지면 별도 SMTP 연동이 필요할 수 있는데, 이번 세션 범위 밖이라 손대지
  않았다.
- 확인 메일을 안 켜기로(A안) 되돌릴지, 계속 켜 둔 채로 갈지는 기획 결정이
  아니라 운영 결정이라 이번에 확정하지 않았다 — 지금 코드는 **어느 쪽 설정이든**
  안전하게 동작한다.

## 교훈 — CLAUDE.md·HANDOFF.md에 옮겨 적었다

**코드 주석에 "이 외부 서비스는 이렇게 설정돼 있다"고 적어 두는 것과, 실제로
그 설정인 것은 다른 문제다.** 대시보드 토글 하나가 코드의 전제를 조용히
깨뜨릴 수 있고, 그 어긋남은 타입 검사도 테스트도 못 잡는다(실제 네트워크
응답의 모양이 바뀌는 것이라 로컬 회귀로는 재현되지 않는다) — 오직 실사용에서만
드러난다. 외부 서비스 설정에 기대는 분기점은 "그 설정일 것이다"로 한 가지
응답 모양만 가정하지 말고, 실제 응답을 보고 갈라야 한다.
