# 트랙 9 — 상점 가챠 경제/로직 선작업 (2026-08-24)

> 사양은 [`Design/GDD.md`](../Design/GDD.md) §6.2, 결정 로그는
> [`docs/작업계획.md`](../docs/작업계획.md) §5-109~114, 진행 상태는
> [`HANDOFF.md`](../HANDOFF.md) §2·§7.

## 왜 이 작업인가

Colyseus 트랙(H1~H3d)이 2026-08-21에 전부 끝난 뒤, 다음 트랙(9. 메타 나머지 /
G. 별도 트랙) 중 무엇을 먼저 할지 안 정해진 상태였다. **상점 UI는 기획자가
직접 만들어 주기로 했고 이 세션 시점엔 아직 없었다** — 그래서 상점(트랙 9)
전체를 시작할 수는 없었지만, 가격 정책은 이미 `history/2026-08-21_트랙9_가격정책_초안.md`에서
사전 논의가 끝나 있어서 **"상점 UI 없이도 할 수 있는 절반"**만 먼저 밟기로
사용자와 합의했다. G1(인물 서사)·다국어도 후보였지만 둘 다 원본 자료가 이
저장소에 아직 없어서(검색 결과 0건) 제외했다 — `docs/2026-08-24_개발_인프라_보고서.md`가
"코드 밖 콘텐츠 자산 대량 확보 — 아직 파이프라인에 미연결"이라고 이미 적어 둔
상태였다.

## 한 일

1. **`tools/extract_data.py`의 `ECONOMY`** — `gachaGrades`를 `["S","A","B","C"]`에서
   `["S","A","B","E"]`로, `cardPacks`(고정 카드 수 팩)를 `gachaPull`(단발/10연
   골드 가격)로, `gachaRates: null`(TODO로 남아 있던 것)을 아예 없애고 왜
   없는지 주석으로 남겼다. `gachaSlotMultiplier: 2`를 새로 더했다.
2. **`packages/rules/src/types.ts`의 `EconomyConfig`** — 실제 아무도 참조하지
   않는 타입이었지만(`ECONOMY`는 JSON import의 구조적 타입을 그대로 쓴다),
   문서 역할을 하고 있어서 같이 갱신했다.
3. **`packages/meta/src/gacha.ts`(신설)** — `gachaSlotsPerOfficer()`·
   `gachaDeckBase()`·`shuffledGachaDeck()`·`drawGacha()`.
4. **`PlayerProfile.gachaPool?: {seed, drawn}`** — 저장 형식 버전은 안 올렸다
   (필드 추가일 뿐 기존 필드의 뜻이 안 바뀜 — `squads`·`grainAt`과 같은 자리).
5. **회귀 `packages/meta/test/gacha.test.ts` 12건** — 슬롯 총합·등급 확률·
   재현성·소진 근처 동작·`gachaPool` 최초 생성/유지를 고정했다.
6. **GDD §6.2·§12, 작업계획 §5, HANDOFF §2·§7** 갱신.

## 설계에서 확정한 것 (사용자 확인 완료)

- **가챠 등급 풀 `S·A·B·E`** — 전투 보상 풀(`B·C·D`, §5-22 불변식)과 B만 겹친다.
- **모델은 계정별 유한 랜덤 어레이** — 고정 확률표가 아니라, 계정마다 등급
  장수 카드를 섞은 유한 배열에서 복원 없이 하나씩 뺀다.
- **`gachaRates` 필드를 없앤다** — 이 모델엔 고정 rate가 없고, 등급별 확률은
  "그 등급에 속한 장수 수"가 정한다(계산값이지 데이터가 아니다).

## 구현하며 새로 정한 것 (이번 세션에서 처음 나온 판단)

- **슬롯 수를 표로 옮겨 적지 않는다.** `history/2026-08-21_...md`의 계산
  (200장 = 레벨9 누적 100장 × 2)을 GDD에 숫자로만 박아 두면, 이 저장소가
  이미 두 번 겪은 사고(§4.3 레벨업 카드 표·§5 증축 자재 표가 GDD와 실제
  JSON에서 갈렸던 것 — CLAUDE.md 「기획 수치의 정본은 엑셀이다」)를 가챠에서
  또 반복하게 된다. 그래서 `gachaSlotsPerOfficer()`가 `cardsSpentOn(GROWTH.maxLevel)`
  (이미 있는 함수, growth.json이 정본)에 `economy.json`의 `gachaSlotMultiplier`
  하나만 곱해 **매번 계산**한다 — growth.json이 바뀌면 슬롯 수도 따라간다.

- **배열 자체를 저장하지 않는다.** 25,200장을 계정마다 그대로 저장하는 건
  낭비이기도 하고, "유한하다"는 전제를 지키려면 재접속마다 다시 섞이면 안
  되는데 배열을 통째로 저장·복원하는 코드는 그 실수(재섞기)를 저지르기
  쉽다. 대신 전투 리플레이가 로그 대신 `seed`·`rngCursor`만 들고 다니는
  것과 정확히 같은 패턴을 가져다 썼다 — `{seed, drawn}` 정수 둘만 저장하고,
  필요할 때마다 `shuffle({seed, rngCursor: 0}, deck)`으로 **같은 순서를
  다시 셔플**해서 `drawn`개를 건너뛴다. 같은 시드 → 같은 순서가 회귀
  (`gacha.test.ts`의 「셔플 재현성」)로 고정돼 있다.

- **밟을 뻔한 지뢰 — `drawGacha`가 처음엔 `Date.now()`/`Math.random()`으로
  시드를 자체 생성했다.** `packages/meta/src/index.ts`의 머리말이 "I/O·
  `Date.now()`·`Math.random()`을 쓰지 않는다"고 이미 적어 놨는데도 처음
  구현에서 그대로 어겼다 — 코드를 다 쓰고 나서야(`freshSeed()` 함수를
  보다가) 알아차려 바로 고쳤다. 고친 방식은 `applyBattleResult(profile,
  outcome, seed)`가 보상 카드 추첨에 이미 쓰던 것과 같은 자리다 —
  `drawGacha(profile, count, newSeed)`로 시드를 **호출자가 준다.** 계정에
  이미 `gachaPool`이 있으면 `newSeed`는 무시된다(재접속마다 안 섞이는 것과
  같은 이유). **이 프로젝트에서 "meta는 순수 함수, 시계는 밖에서 넣는다"는
  원칙이 코드를 다 쓴 뒤에도 한 번 더 스스로 어기기 쉬운 자리라는 뜻이다** —
  다음에 meta에 새 모듈을 추가할 때 같은 실수를 반복하지 않도록 여기 남긴다.

- **소진은 예외가 아니라 값으로 알린다.** `drawGacha`가 요청한 수보다 적게
  나오면(배열 소진) `RangeError`를 던지는 대신 `exhausted: true`와 함께
  있는 만큼만 돌려준다 — 확정안 §4.4가 "이 유한성은 정상 상한이 아니라
  매크로 남용을 막는 안전장치"라고 명시했으므로, 도달해도 게임(뽑기 자체)이
  멈추면 안 된다는 판단이다.

## 이번 범위 밖

- **상점 화면·골드 차감·뽑기 연출** — 상점 UI가 아직 없다. UI가 오면
  `drawGacha()` 위에 골드 검증(`gachaPull`의 가격)과 카드 지급(`addCard`,

  미정(§7 참조).
- **G1 인물 서사·다국어 번역** — 원본 자료 미도착으로 보류.

## 이어서 — 상점 가챠 그림 16장 + 등급 배지 색 (같은 날, 이어진 세션)

로직을 굳힌 뒤, 이미지 생성 AI에게 요청할 프롬프트 목록을 만들어 줬고
(재화 아이콘 3종·구매 상품 아이콘 6종·가챠 배너·등급별 개봉 연출 4종·장터 소품),
사용자가 그걸로 그림을 받아 `assets/market/`에 넣어 왔다. 컬러 가이드(S 보라·
A 빨강·B 파랑·E 황금)도 함께 확정했다.

### 한 일

1. **`tools/build_market.py`(신설) + `npm run market`** — 다른 `assets/X` 폴더와
   같은 관례(전용 굽기 도구, 원본은 리포 밖)를 그대로 따랐다. 아이콘 10종은
   `terrain`·`vfx`와 같은 "알파 경계상자 → 정사각 → 리사이즈"를, 배너·소품
   2종은 비율 유지 리사이즈를, 개봉 연출 4종은 `vfx`의 "2×2를 4칸으로 편다"
   패턴을 재사용했다.
2. **`style.css`의 `--grade-{S,A,B,E}` 갱신** — 2026-08-12에 기획자가 이미
   "단일 출처"로 지정해 게임 전체(상태 팝업·카드 스트립·커맨드 패널·메타 화면)가
   쓰고 있던 값이다. 그래서 이번 갱신은 상점 하나가 아니라 **게임 전체의 등급
   색**이 바뀌는 변경이다.
3. **HANDOFF §2·§5·§7, 작업계획 §5(결정 115~117)** 갱신.

### 코드를 쓰며 새로 알아차린 것

- **개봉 연출(`reveal-*.png`)의 2×2 칸 순서가 기존 관례와 다르다.** `SpecialStatus`의
  알파벳 파일(`build_status_fx.py`)은 시계방향(좌상→우상→우하→좌하)으로 편다는
  게 이미 정해진 관례였다. 이번 `reveal-s.png`도 처음엔 같은 순서로 펼 생각이었는데,
  **`Read` 도구로 그림을 직접 열어 보니** 프롬프트가 요청한 "옅은 빛(1) → 터짐(2) →
  빛줄기 만개(3) → 흩날리며 소멸(4)"이 실제로는 좌상→우상→**좌하**→**우하**
  (reading order)로 그려져 있었다 — 시계방향으로 읽었으면 3·4번째 칸이 뒤바뀌어
  "만개"와 "소멸"이 뒤집힌 채로 재생될 뻔했다. **"2×2를 N칸으로 편다"는 조작 자체는
  재사용 가능한 패턴이지만, 실제 칸 순서는 소스마다 확인해야 한다** — 표로 굳어진
  관례(시계방향)를 새 원본에 무비판적으로 적용하면 안 된다는 것을 여기서 확인했다.
- **등급 배지 색을 "고급진 보라/빨강/파랑/황금" 같은 서술형 가이드로 받았을 때,
  추상적인 이름 대신 실제로 받은 그림에서 색을 뽑아 왔다.** `reveal-*.png`에서
  채도가 가장 높은 픽셀의 색상(hue)을 계산해 배지 색의 기준으로 삼았다 — 사람이
  "고급진 빨강"이라고 말한 색과 이미지 생성 AI가 실제로 그린 빨강이 미묘하게
  다를 수 있는데, 뽑기 화면에서 터지는 색과 등급 배지 색이 갈리면 "왜 여기선
  색이 다르지"가 생긴다. 그래서 임의로 손으로 고른 hex가 아니라 **실제 자산에서
  역산**했다 — CLAUDE.md의 "밸런스·경제 상수를 GDD에 옮겨 적지 않고 이미 있는
  계산에서 파생시킨다"와 같은 태도를 색상에도 적용한 셈이다.
- **처음 `Read`로 이미지를 열었을 때 배경에 심한 노이즈가 보여 "배경 제거가
  덜 됐나" 의심했다.** 실제로는 파일의 알파 채널이 0~255 전 구간에 걸쳐 정상
  분포하고 있었고(파이썬으로 직접 확인), 노이즈처럼 보인 것은 반투명 영역을
  미리보기가 렌더링하는 과정의 압축 아티팩트였다 — `tools/build_market.py`로
  실제 처리(경계상자 크롭 + 리사이즈)를 거친 결과물을 다시 열어 보니 완전히
  깨끗했다. **미리보기에서 이상해 보여도, 실제 파이프라인을 태운 뒤에 판단한다.**
- **`tools/strip_reveal_bg.py`라는, 이번 세션에서 내가 만들지 않은 파일이 이미
  `assets/market/reveal-{s,a,b,e}`를 대상으로 정확히 존재했다.** 배경이 체커보드로
  플래튼된 경우까지 다루는 정교한 알파 복원 스크립트였는데, 커밋되지 않은 채로
  남아 있었다 — 사용자가 이미지를 준비하며 (아마 다른 세션에서) 이미 한 차례
  전처리를 거쳤다는 뜻이다. **폴더에 낯선 파일이 있으면 지우거나 무시하지 말고
  먼저 읽어서 왜 있는지 파악한다** — 이번엔 지금 하려는 작업의 전처리 단계가
  이미 끝났다는 유용한 증거였다.

### 이번 범위 밖

- **상점 화면 자체** — 여전히 없다. `public/market/`의 그림은 화면이 붙을 때
  `<img>`/CSS 배경으로 참조하면 된다.
- **골드 차감·구매 흐름** — `gachaPull`(가격)·`drawGacha()`(뽑기)는 있지만
  실제로 골드를 빼고 카드를 지급하는 화면 로직은 UI와 함께 만든다.
