# 2026-08-24 — 상점 뽑기 연출 배경 제거 (`reveal-{s,a,b,e}.jpg` → `.png`)

> 이 문서는 **한 대화 세션의 기록**이다. 프로젝트의 현재 상태와 규칙은
> [`HANDOFF.md`](../HANDOFF.md)와 [`Design/GDD.md`](../Design/GDD.md)가 정본이며,
> 여기는 "무엇을 왜 그렇게 정했는가"와 "어디서 넘어졌는가"를 남긴다.

세션 시작 시점: `assets/market/reveal-s.jpg` · `reveal-a.jpg` · `reveal-b.jpg` · `reveal-e.jpg`
(가챠 등급별 연출 이펙트, 각각 2048×2048에 2×2로 배치된 변형 4장씩)만 사용자가 가진 도구로
투명 배경 처리가 안 됐다. 폴더의 나머지 파일은 이미 처리되어 있었다.

세션 종료 시점: **4장 전부 알파가 들어간 `.png`로 변환됐고, 다시 만드는 도구가 있다.**
`.jpg` 원본은 지우지 않고 그대로 남겨 뒀다(백업 겸 재처리용 입력).

이 폴더 배경 제거는 처음이 아니다 — [`2026-08-07_장수_이미지_배경제거.md`](2026-08-07_장수_이미지_배경제거.md)가
장수 초상 260장을 다뤘다. 그때는 **양피지 배경 + 색상 히스토그램 + 연결성**으로 풀었는데,
이번 소재(검은 바탕에 그려진 발광 이펙트)는 성질이 완전히 달라 **그 도구를 그대로 못 쓴다** —
아래에 왜 다른 접근이 필요했는지 적는다.

## 2. 원본의 성질 — 두 갈래로 갈린다

`is_checker_bg()`가 좌상단 20×20 코너 밝기로 자동 분기한다.

- **검은 캔버스 (`reveal-s` · `reveal-a` · `reveal-e`)**: 순수 검은 배경 위에 그려진
  발광 구름/폭발 그림. "additive glow" 소재의 표준 추출법 — `alpha = max(R,G,B)`,
  그 다음 그 알파로 색을 **역-예비곱셈**(unpremultiply, `fg = arr/alpha*255`)해서
  합성했을 때 색이 탁해지지 않게 한다. 검은 배경이라 배경값이 0이므로 이 계산에
  왜곡이 없다 — 나눗셈 분모가 언제나 같은 기준(255)이다.

- **체크보드가 박제된 파일 (`reveal-b`)**: 픽셀을 직접 찍어 보니 코너가 순수 검정이
  아니라 **회색 72와 108이 30px 격자로 번갈아 있는 진짜 체커보드 무늬**였다(§3-1).
  JPG는 알파 채널이 없으므로, 이건 **예전에 어떤 도구가 이미 배경 제거를 했고
  그 투명도 미리보기(체커보드)를 통째로 JPG로 납작하게 저장**한 결과로 추정된다 —
  진짜 알파는 사라지고 미리보기 무늬만 픽셀에 남은 것. 사용자가 "이 파일만 도구로
  안 된다"고 한 이유도 이것과 맞아떨어진다 (진짜 알파가 없으니 도구가 뭘 지워야
  할지 알 수 없다).

두 갈래는 **완전히 다른 수식**이 필요하다 — 검은 배경은 배경값이 균일(0)해서 단순
나눗셈으로 끝나지만, 체커보드는 배경값이 **픽셀 위치마다 두 값 중 하나**라 그 위치
의존성을 식에서 지워야 한다. 아래 §3~4가 그 과정이고, 이번 세션 시간의 대부분이
`reveal-b` 하나에 들어갔다.

## 3. 검은 배경 셋 (`reveal-s` / `-a` / `-e`)

`strip_black_bg()`:

```python
alpha = arr.max(axis=2)                       # 0-255
fg = arr / alpha * 255                        # 역-예비곱셈
```

배경이 순수 0이라 이게 전부다. 미리보기(체커/단색 캔버스에 합성)로 확인했을 때
가장자리가 완전히 투명하고, 밝은 중심부는 원래 색 그대로 유지됐다 — 한 번에 통과.

## 4. 체커보드 파일 (`reveal-b`) — 세 번 실패하고서야 맞았다

### 4-1. 체커보드 실측

```
corner (x=0)  ≈ (72.2, 72.4, 72.3)
corner (x=30) ≈ (107.5, 107.6, 107.5)
tile 크기 = 30px, (0,0)에 정렬
```

값이 정확히 회색(R=G=B)이고 30px마다 정확히 번갈아 → **알고리즘이 생성한 체커보드
미리보기**임을 확인. 이 정보(타일 크기, 두 회색 값)가 이후 전체 복원의 기반이다.

### 4-2. 1차 시도 — 30px 타일 평균으로 두 배경 매팅 (실패)

전통적인 "두 배경 매팅"(같은 전경을 서로 다른 배경 두 장에 합성한 걸 알면 알파와
전경색을 대수적으로 풀 수 있다)을 응용해, 인접한 두 타입 타일의 **평균색**을 두
샘플로 놓고 풀었다.

**결과: 실패.** 가는 광선(폭 1~3px)이 30px 타일 하나를 가로지르므로 "타일 안에서는
전경이 거의 같다"는 전제가 깨졌고, 결과물에 누런 얼룩과 강한 노이즈가 났다.

> 타일 평균처럼 **공간적으로 뭉개는** 방법은, 전경이 타일보다 고주파(가는 선·뾰족한
> 꽃잎 윤곽)를 가지면 그 즉시 깨진다. 30px 타일에 1px 광선이 지나가면 평균은
> 그 어느 쪽도 아닌 값이 된다.

### 4-3. 2차 시도 — 픽셀별 정확한 배경값 빼기 (배경은 깨끗, 내용물은 여전히 체커)

타일 평균 대신, **위치로 배경값이 정확히 결정되므로** 픽셀마다 정확한 배경값(72
또는 108)을 그 자리에서 바로 뺐다:

```python
bg = 72 if 체커타입==A else 108   # 픽셀 위치로 결정, 근사가 아니라 정확한 값
effective = arr - bg
alpha = clip(effective.max(2) / (255 - bg), 0, 1)   # 타입별로 다른 분모(!)
```

배경(빈 공간)은 완전히 깨끗해졌다 — 코너 알파가 0으로 완벽히 떨어짐. 그런데
이펙트 **내용물 안**(소용돌이 획 등)에 여전히 체커보드가 비쳤다.

원인: `255 - bg`가 타입마다 다르다(183 대 147). **진짜 색이 항상 채널 최댓값
255로 포화한다는 가정 아래서만** 이 분모가 정확하다 — 그 가정이 안 맞는(즉 채도가
낮거나 어두운) 픽셀에서는 두 타입이 **같은 진짜 알파에 대해 ~20% 다른 알파값**을
내놓는다. 그 20% 차이가 그대로 체커보드 무늬로 보였다.

> **정규화 분모가 위치에 의존하면, 그 의존성이 성립하지 않는 곳마다 그 위치의
> 무늬가 그대로 결과에 새겨진다.** 여기선 "채널 최댓값=255 포화" 가정이 깨지는
> 모든 픽셀이 체커보드를 물려받았다.

### 4-4. 3차 시도 — 알파만 블러 (알파는 깨끗해졌지만 색이 깨졌다)

타입별 분모 문제를 알파 채널에 가우시안 블러(반경 = 타일×1.5)로 눌러 봤다.
**알파 채널 자체는 깨끗해졌다**(코너 확인, 실제 배열 값도 완만하게 변함). 그런데
합성 미리보기에는 **여전히 체커보드가 보였다** — 이번엔 알파가 아니라 **색(fg)에서**.

디버깅으로 원인을 찾았다: 색 복원식이 `fg = bg + effective/alpha`인데, 여기서
**블러된(뭉개진) 알파**로 나누면서 **뭉개지지 않은 원본 `effective`**와 짝이
안 맞게 됐다. 특히 R 채널처럼 원래 배경값과 비슷한(파란 이펙트라 R 성분이 거의
없는) 채널에서는 `effective_R ≈ 0`이라 `fg_R ≈ bg`가 그대로 남는데, **그 `bg`
자체가 체커보드값(72/108)이라 무늬가 색에 직접 박제됐다.**

```
실측: R 채널이 알파와 무관하게 그냥 72 또는 108 그 자체로 찍혀 나옴
```

> **알파와 색을 다른 정밀도로 처리하면(하나는 블러, 하나는 원본) 서로 짝이
> 안 맞아 어느 한쪽에 무늬가 다시 나타난다.** 색 복원식에 배경값을 더하는 항이
> 있으면, 그 배경값 자체가 위치 의존적일 때 나누는 알파가 부정확한 만큼
> **그 부정확함이 고스란히 배경값 무늬로 드러난다.**

### 4-5. 최종 — 색은 원본 알파로 복원 + 주파수 노치 필터로 마무리

색 복원은 **뭉개지지 않은(raw) 알파**로 되돌렸다 — `effective`와 같은 픽셀에서
나온 값이라 최소한 서로 앞뒤가 맞는다. 그런 다음, **남은 체커보드 편향만 표적으로
제거**하는 신호처리 기법을 색 채널에 얹었다:

```python
checker_sign = 1 또는 -1   # 타입 A/B에 따라
signal = fg_channel * checker_sign          # 복조 (demodulate)
bias = gaussian_filter(signal, sigma=tile)  # 저역통과 — 30px 주기 성분만 남는다
fg_channel -= checker_sign * bias           # 재변조 후 빼기
```

이건 통신에서 쓰는 **AM 복조 → 저역통과 → 재변조** 그대로다. 정확히 체커보드
주기(30px)로 번갈아 뒤집히는 성분만 골라내 제거하고, 대각선 광선이나 둥근 꽃잎처럼
그 격자에 정렬되지 않은 진짜 그림 내용은 건드리지 않는다. 알파 채널은 그대로
가우시안 블러 + 임계값(35/255 미만은 0으로 눌러 JPEG 링잉 잔여물 제거)으로 마무리.

**검증**: 픽셀 배열을 직접 찍어 R 채널이 더 이상 72/108을 따르지 않고 완만하게
변하는 것을 확인했고, 실제 사용 크기(256px·400px 썸네일)로 렌더링해 무늬가 전혀
안 보이는 것도 확인했다. 2048px 원본에서 4배로 확대해야만 아주 미세한(~7% 진폭)
잔물결이 남는데, 실사용 조건이 아니라 받아들였다.

> **완벽한 알파 모델을 못 찾겠으면, "무엇이 틀렸는가"가 아니라 "그 틀림이 정확히
> 어떤 주파수/무늬로 나타나는가"를 보고 그 무늬만 표적으로 지우는 필터를 생각할 것.**
> 세 번의 시도 모두 "더 정교한 알파 추정"을 쫓다 실패했고, 마지막에야 "알파는
> 대충 맞고, 남는 편향은 신호처리로 걸러내자"로 방향을 바꿔 풀렸다.

## 6. 새 대화로 이어갈 때

### 이 도구를 다시 쓸 상황

- `assets/market/` 등에 **검은 배경에 그려진 발광 이펙트**(gacha 연출, 스킬
  이펙트 등)가 새로 추가되고 투명 처리가 안 돼 있으면: `strip_black_bg()`
  경로를 그대로 탄다. 파일명이 `reveal-*`가 아니어도 되도록 `MARKET_DIR`
  경로와 `main()`의 파일 목록만 바꿔 쓰면 된다.
- 어떤 파일이 **이미 열어보면 체커보드가 씌워진 채로 보이는 JPG**라면(=예전
  도구가 알파를 만들고 미리보기를 그대로 구워버린 흔적), `is_checker_bg()`가
  자동으로 잡아 `strip_checker_bg()`로 보낸다. 단, **타일 크기(30px)와 두 배경
  회색값(72/108)은 이 파일들 전용으로 실측한 상수**다 — 새 파일의 체커보드가
  다른 크기/색이면 `strip_checker_bg()` 호출부의 `tile=` · `bg_low=` · `bg_high=`를
  다시 재야 한다 (§4-1 방식대로 코너 픽셀을 직접 찍어보면 된다).

### 남겨둔 것

| 항목 | 비고 |
|---|---|
| `reveal-*.jpg` 원본 | 지우지 않고 남겨 뒀다. `.png`로 화면에서 잘 쓰이는 게 확인되면 지워도 된다 |
| 체커 타일 상수(30px, 72/108) | `strip_checker_bg()` 시그니처의 기본값. 다른 체커보드 소재가 생기면 실측부터 다시 |
| `reveal-b`의 4배 확대 시 미세 잔물결(~7%) | 실사용 크기에서는 안 보여서 더 안 팠다. 만약 이 이펙트를 아주 크게(전체화면급) 띄우는 화면이 생기면 재검토 |

### 작업 방식에서 확인된 것

- **한 이미지 폴더 안에서도 소재 성질이 다르면 알고리즘을 나눠야 한다.** 이번엔
  `is_checker_bg()`로 자동 분기했다 — 파일마다 사람이 골라주지 않아도 되게.
- **"검증 배경/크기를 바꿔 볼 것"이 §4-4(장수 배경제거 세션)에서도 나온 교훈인데
  여기서도 그대로 반복됐다** — 코너만 보고 배경은 깨끗하다고 결론 내렸다가
  (§4-3) 내용물 안의 무늬를 놓쳤고, 원본 해상도로 확대해서 보고서야(§4-4→4-5)
  실사용 크기에서는 안 보이는 잔여 문제라는 것도 확인했다. **한 지표·한 배율만
  보고 끝내지 말 것.**
- **모델이 안 맞을 때, "더 정교한 모델"과 "표적 필터"는 다른 해법이다.** 이번엔
  알파 모델을 아무리 정교하게 다듬어도(블러 반경을 늘리고 줄이고) 안 풀렸고,
  "이 편향은 정확히 이 주파수에서만 나타난다"는 걸 알아챈 뒤 노치 필터로
  바로 풀렸다.
