# 현금결제 연동 1차 검토 (2026-09-25)

금화 충전 화면을 만들려고 시작한 세션이다. 결제 연동에 필요한 요건과 구현 방향, 법·세무를 조사했고,
그 과정에서 **경제 규칙 둘을 확정**했다(하나는 구현까지 끝냈다). **실제 결제 연동은 보류했다** —
UI를 손볼 곳이 아직 많아서, 다른 작업을 마친 뒤 이 문서에서 다시 시작한다.

> ⚠ 법·세무 항목은 **방향을 잡기 위한 조사**다. 실제로 진행할 때 세무사·변호사 확인이 필요한 곳은
> 「확인 필요」로 표시했다. 앱스토어 규정은 2025~2026년에 크게 바뀌었고 **지금도 소송 중**이라
> 다시 시작할 때 최신 상태를 다시 확인한다.

## 1. 이번 세션에서 확정한 것

### 1.1 금화는 오직 결제로만 생긴다 (기획자 확정)

- 보상·이벤트·출석·장애 보상은 **금화가 아니라** 군량·아이템·카드로 준다.
- 그래서 금화를 **유료/무료로 나누지 않는다.** 나누면 환불(청약철회)·차지백 계산과 「금화를 되돌려
  주는」 모든 길이 「어느 쪽에서 냈던 금화인가」를 따라가야 한다.
- 예외는 **관리자 지급** 하나(고객 문의 대응·테스트 계정). 원장에 사유와 함께 따로 적어 환불
  계산에서 뺀다.
- GDD §6.1에 기록했다.

**운영에서 무료 금화가 필요해지는 흔한 경우와 대체 수단**

| 경우 | 대체 |
|---|---|
| 점검·장애 보상 | 군량·아이템 |
| 출석·이벤트·쿠폰 | 금화 대신 다른 재화 (지금은 없음) |
| 신규 가입 보너스 | 지금은 금화 0으로 시작 |
| 결제는 됐는데 금화가 안 들어온 경우의 수동 지급 | **무료가 아니다** — 주문에 연결된 유료 금화. 관리자 페이지에서 「무료 지급」이 아니라 **「주문 수동 확정」으로 따로** |
| 스토어 심사·QA 계정 | 계정에 테스트 표시. 환불·정산 대상에서 뺀다 |

### 1.2 대장간은 확정이 곧 결제이고 취소·환불이 없다 (기획자 확정, 구현 완료)

금화가 늘어나는 곳을 코드에서 훑었더니 결제 외에는 **두 군데**뿐이었다 — 개발용 지급(`devGrant`)과
**대장간 주문 취소의 전액 환불**. 금화를 되돌려 주는 규칙을 없애기로 했다.

- 논의 과정: 「제작 시간 + 1분, 마지막 1분 진입 때 결제하고 그 뒤로 취소 불가」 안이 먼저 나왔다.
  **기각** — 돈을 늦게 떼려면 그동안 금화를 **잡아 두는(예치)** 상태가 필요하고, 그 예치액을 금화를
  쓰는 자리 전부(가챠·장터·군량·자재·재설계·태학·도시 이름, 7곳 이상)가 빼고 봐야 한다. 한 곳만
  빠뜨려도 「확정 순간에 낼 금화가 없다」가 된다. 게다가 제작 시간이 1~5분이라 +1분이면 Lv1은 두 배가 된다.
- 최종: **[제작 확정] 순간 금화가 나가고, 취소·환불은 없고, 제작 기간이 지나면 병기가 들어온다.**
  확정 전에 한 번 묻고 「취소·환불되지 않는다」를 알린다.

## 2. 지금 코드의 출발점

- `gold` · `gachaPool`은 **이미 서버 소유 필드**다(`SERVER_OWNED_FIELDS`, `meta/src/authority.ts`).
  `PUT /profile`로 금화를 올릴 수 없다 → 결제 구현의 중심은 **금화를 지급하는 서버 경로 하나를 새로 만드는 것**.
- 금화 팩 표가 이미 엑셀 → `packages/data/generated/economy.json`에 있다:
  **10냥 1,000원 / 60냥 5,000원 / 120냥 10,000원** (`goldPacks`).
- 계정 쓰기는 전부 `mutateProfile()`(`server-api/src/profileStore.ts`)의 **행 잠금 트랜잭션**을 지난다.
  다만 `fn`이 순수 함수라 **같은 트랜잭션 안에서 다른 테이블(결제 원장)에 쓸 수 없다** — 결제
  확정은 「주문 상태 변경 + 금화 증가」가 한 트랜잭션이어야 하므로 여기를 넓히거나 전용
  `grantPurchase()`를 둬야 한다.
- 개발용 지급 `POST /dev/grant`는 `SAMCHESS_DEV_GRANTS=1`일 때만 열린다. 감사 로그가 없다.
- 장터 홈에 [금화 충전] 자리가 이미 있다(pptx 75~88쪽 재구성 때). GDD의 「환경설정 → 결제 내역」 자리도 있다.

## 3. 결제 경로 (2026-09 기준)

| 경로 | 판매 주체(MoR) | 수수료 | 세금·환불·통화 | 쓰임 |
|---|---|---|---|---|
| ① 앱스토어 인앱결제 (StoreKit / Play Billing) | 스토어 | 연매출 100만 달러까지 대체로 15%, 넘으면 30%. Google은 2026-06-30부터 미국·EEA·영국에서 서비스 수수료와 결제 수수료를 분리 | **스토어가 거의 다 처리** | Android·iOS 앱 안 |
| ② 웹 결제 + 국내 PG (토스페이먼츠·KG이니시스·포트원 등) | 본인 | 2~4% 안팎 | **본인이 직접** (부가세·환불·청약철회) | PC 웹, 한국 |
| ③ 웹 결제 + 게임 전문 MoR (Xsolla·Coda·Neon 등) | MoR 업체 | 5% 이상, 사기 방지·분쟁까지 실질 8~10% | **업체가 대신** (각국 VAT·차지백) | PC 웹, 해외 |

MoR(Merchant of Record) = 법적으로 「판매자」가 되어 세금·분쟁을 책임지는 주체.

**2025~2026년에 바뀐 것**
- **Apple(미국)**: 2025-05부터 미국 스토어 앱은 외부 웹 결제 링크를 **수수료 0%**로 넣을 수 있다.
  하지만 Apple이 2026-08-13에 15%/10%/5% 수수료안을 법원에 냈고, 대법원도 상고를 받아들였다
  (본안 판결은 2027년 예상). **여기에 사업 모델을 걸지 않는다.**
- **Google Play**: 대체 결제·외부 링크 프로그램 확대. 외부 링크는 게임 설치 1건당 3.65달러라 소규모엔 불리.
  대체 결제 프로그램 가입자는 2026-10-01부터 거래 보고 의무.
- **Stripe**: 한국 사업자는 직접 가입이 안 되는 것으로 안다(확인 필요) → 해외 웹 결제는 ③ MoR가 현실적.
- 한국(전기통신사업법)·EU(DMA)·일본(스마트폰법, 2025-12 전면 시행)에 스토어 대체 결제가 열려 있으나
  수수료 차이가 작아 초기엔 인앱결제 하나로 충분하다.

## 4. 배포 플랫폼 — 스토어 앱도 낼 수 있다

사용자는 웹에서만 테스트해 와서 스토어 배포를 생각하지 않고 있었다. **가능하고, 처음부터 그렇게
짜여 있다** — HANDOFF 기술 스택 표에 「패키징: Capacitor — 웹 빌드 하나로 PC·Android·iOS」가 있다.
Capacitor는 `vite build` 결과를 네이티브 앱 안 WebView에 넣어 그대로 돌린다(React + Phaser 그대로).
**다만 아직 설치되어 있지 않다.** 사용자 결정: **Android 배포는 그 시점에 다시 묻는다.**

| 항목 | 상태 |
|---|---|
| 서버 주소 | ✅ `VITE_SAMCHESS_API` · `VITE_SAMCHESS_SERVER` · `VITE_SUPABASE_URL`로 바꿀 수 있다 |
| 운영 서버 | ⚠ 앱은 `localhost`에 못 닿는다. `https`/`wss` 공개 서버가 먼저. Android는 평문 `http`/`ws`를 막는다 |
| 에셋 크기 | ⚠ `client/public` 139.5MB · 1,705개 — Google Play 기본 모듈 200MB 안이지만 크다 |
| 재접속 | ✅ 백그라운드 전환 끊김은 기존 재접속 유예 60초가 받는다 |
| 이메일 인증 링크 | ⚠ 웹 주소로 열린다 — 딥링크 설정 또는 「웹에서 인증 후 앱에서 로그인」 |
| 입력·화면 | ⚠ hover 의존 UI · 노치(safe-area) · 화면 방향 · Android 뒤로 가기 — 실기기 확인 |
| 스토어 필수 | ⚠ 앱 안 계정 삭제(Apple·Google 의무) · 개인정보처리방침 URL. 이메일 로그인만이라 Apple 로그인 의무는 없음 |

준비물: Android는 Windows에서 전부 된다(개발자 계정 25달러 1회, 개인 계정은 출시 전 **테스터 12명 ×
14일 비공개 테스트**). iOS는 **macOS + Xcode 필요**(또는 클라우드 빌드), 연 99달러.

| | 웹만 | 웹 + 스토어 앱 |
|---|---|---|
| 결제 | PG·MoR 직접, 수수료 낮음, 세금·환불 직접 | 앱 안은 IAP 15~30%, 세금·환불은 스토어 |
| 등급분류 | **게임물관리위원회에 직접** | 스토어 IARC로 대체 (웹도 내면 웹은 따로) |

## 5. 구현 설계 제안

### 5.1 이 저장소 규약을 결제에 옮기면

| 기존 규약 | 결제에서 |
|---|---|
| 클라이언트는 의도만 보낸다 | 「이 상품을 사겠다」와 결제사가 준 증표만 보낸다. **금액·수량·성공 여부는 절대 안 보낸다** |
| 서버 소유 필드 | 금화가 늘어나는 곳은 **결제 확정 경로 하나**뿐 |
| 기획 수치의 정본은 엑셀 | 금화 팩 표는 엑셀 → `extract` → JSON (이미 그렇다). 화면이 다시 적지 않는다 |
| 조용히 무시하는 경로는 없는 것처럼 보인다 | 결제에서는 「돈은 나갔는데 금화가 없다」. 모든 실패는 기록하고 다시 처리할 수 있어야 한다 |
| 폴백이 늘 안전하지 않다 | **결제에는 로컬 폴백이 없다.** 서버에 못 닿으면 결제 단추를 막는다 |

### 5.2 구조 — 결제사 어댑터 + 주문 하나의 흐름

```
[화면] 금화 팩 고름
   │ POST /purchase/order {packId}
   ▼
[server-api] 주문 생성 ─ payment_orders: status=created, 금액은 서버 표에서
   │ orderId, 금액
   ▼
[결제사 창] 토스페이먼츠 / Xsolla / (나중) Google Play / Apple
   │ 성공 → 증표(paymentKey · purchaseToken 등)
   ▼
[server-api] POST /purchase/confirm {orderId, 증표}
   ① 결제사 API에 직접 승인·조회 — 금액이 주문과 같은지 대조
   ② 한 트랜잭션: 주문 paid→granted + 계정 금화 증가 + 원장 한 줄
   ③ (인앱결제면) 스토어에 consume / finishTransaction
   ▼
[웹훅] 결제사 → server-api: 승인 누락 보정 · 환불 · 차지백
```

- **`PaymentProvider` 인터페이스 하나** — `confirm(order, 증표)` · `lookup(id)` · `parseWebhook(req)`.
  토스·Xsolla·Google·Apple이 각각 구현한다. 주문 → 지급 → 환불 흐름은 한 벌. Android를 붙일 때 바뀌는 것은
  어댑터 하나와 결제창 호출부뿐이다.
- 순수 부분(`grantGoldPack(profile, pack)`)은 meta에, I/O는 store에 둔다.

### 5.3 데이터 모델 초안

- **`payment_orders`**: `order_id`(PK) · `uid` · `pack_id` · `amount` · `currency` · `provider` ·
  `provider_tx_id` · `status`(created/paid/granted/refunded/failed) · 시각들 · `test` 표시.
  **`unique(provider, provider_tx_id)`** — 중복 지급을 DB가 막는다(도시 이름의 23505 처리와 같은 방식).
- **`gold_ledger`** (추가만 하는 기록): `uid` · `delta` · `kind`(purchase/spend/refund/admin_grant) · `ref` · 사유.
  「결제 내역」 화면과 고객 문의·환불 계산의 근거. 계정의 `gold`와 원장 합계를 정기 대조한다.
- 금액은 **정수 최소 단위**(원·센트). 부동소수 금지.

### 5.4 대비해야 할 실패 시나리오

| # | 상황 | 대비 |
|---|---|---|
| 1 | 금액 위조 (1,000원 결제하고 5만 원 팩 주장) | 금액은 주문 생성 때 서버 표에서. 승인 뒤 결제사 조회 금액과 대조 |
| 2 | 중복 지급 (확정 두 번, 웹훅과 확정이 동시에) | 고유 인덱스 + 상태 전이 `paid→granted`는 한 번만. 같은 요청엔 같은 응답(멱등) |
| 3 | 결제 직후 브라우저 종료·서버 다운 | 웹훅이 보정 + 「결제됐는데 미지급」 주문 재처리 작업 + 앱을 열 때 확인 |
| 4 | 웹훅 위조 | 서명 검증. 가능하면 내용을 믿지 말고 결제사 API로 다시 조회 |
| 5 | 웹훅 순서 뒤바뀜 (환불이 승인보다 먼저) | 상태 전이 표. 불가능한 전이는 기록만 하고 보류 |
| 6 | 환불·차지백 뒤 금화가 이미 가챠에 쓰였다 | **정책 결정 필요** — 보통 잔액 음수 허용 + 결제 제한 |
| 7 | 청약철회 (7일, 쓰지 않은 유료 금화) | 환불 가능액 = 그 주문에서 아직 안 쓴 금화 |
| 8 | 부분 환불 · 여러 팩 섞여 쓰임 | 처음엔 팩 단위 전액 환불만 지원해도 된다 |
| 9 | 테스트 키가 운영에 섞임 | 환경별 키 + 주문의 `test` 표시 |
| 10 | `SAMCHESS_DEV_GRANTS=1`이 운영에서 켜짐 | 운영 설정에서 켜져 있으면 **부팅 거부** |
| 11 | 통화·반올림 | 정수 최소 단위. 해외 가격은 결제사 가격표를 따른다 |
| 12 | 미성년자 결제 취소 요청 | 약관 조항 · 연령 확인 · #6과 같은 회수 경로 |
| 13 | 결제사 장애 | 「지금 결제할 수 없습니다」. 로컬 폴백 없음 |

### 5.5 검사 전략

- **`FakeProvider`로 회귀** — 승인 성공·실패, 금액 불일치, 웹훅 중복, 환불 먼저 도착을 스크립트로
  밀어 넣는다. `npm test`에서 진짜 결제사 없이 돈다(「회귀 안에 가짜 판정 주체」와 같은 방식).
- **각 방어를 깨 본다** — 고유 인덱스를 지우면 중복 지급 검사가, 금액 대조를 지우면 위조 검사가
  실패해야 한다. 안 깨지면 그 검사는 아무것도 확인하지 않는 것이다.
- **샌드박스 스모크** — 토스페이먼츠는 가입만으로 테스트 키를 주는 것으로 안다(확인 필요).
  「결제 → 금화 증가 → 결제 내역 표시」를 끝까지.

### 5.6 관리자 페이지

지금은 테스트 금화를 개발용 지급으로 넣고 있다. 관리자 페이지를 만들면 좋지만 **그것만으로 무료 금화가
없어지지는 않는다** — 결제 없이 생긴 금화는 어느 화면에서 넣든 무료 금화다. 관리자 페이지가 주는 것은
**「누가, 언제, 왜 넣었는지가 남는다」**는 점이다. 개발 금화가 운영에 섞이는 것을 실제로 막는 것은
**개발용과 운영용 Supabase 프로젝트를 나누는 것**이다.

- 게임 클라이언트 번들과 **분리**(예: `packages/admin` 작은 웹앱 → `server-api`의 `/admin/*`).
- 권한은 **서버가 확인**(Supabase `app_metadata.role = 'admin'` 등). 화면에서 단추를 숨기는 것으로는 못 막는다.
- **모든 조작을 감사 로그에** — 누가·누구에게·무엇을·몇 개·사유(필수).
- 기능: 계정 검색 · 금화/카드/아이템 지급·회수 · 주문 조회·수동 확정·환불 처리 · 테스트 계정 표시.
- `SAMCHESS_DEV_GRANTS`는 로컬 개발용으로 남기되 운영에서는 부팅 거부.

## 6. 법·세무

### 6.1 사업자 (한국)

| 항목 | 내용 |
|---|---|
| 사업자등록 | 개인사업자로 시작 가능, 커지면 법인 전환 검토. 해외 법인은 초기엔 불필요(스토어·MoR가 해외 판매를 맡는다) |
| 통신판매업 신고 | 웹 직판(②)이면 필요. 앱스토어만이면 면제 기준 확인 필요 |
| 개발자 계정 | Apple·Google 조직 계정은 **D-U-N-S 번호** 필요 |
| 정산 | 외화 계좌. 스토어 세금 양식(W-8BEN / W-8BEN-E)으로 한미 조세협약 원천징수 감면 |
| PG 가입 심사 | 게임 업종은 **등급분류 필증**을 요구하는 경우가 많다 |

### 6.2 게임 규제 (한국)

- **게임물 등급분류** — 스토어는 IARC로 대체되지만 **PC 웹 직접 배포는 게임물관리위원회 등급분류를 따로 받는다.**
  현금 가챠는 청소년 등급 판정에 영향.
- **확률형 아이템 표시 의무**(2024-03) + **징벌적 손해배상 최대 3배 · 입증책임 전환**(2025-08) —
  게임사가 「고의·과실 없음」을 증명해야 책임을 면한다.
  - **최근 3년 연평균 매출 1억 원 이하 중소기업은 표시 의무 제외.** 그래도 스토어 정책(Apple 3.1.1 등) 때문에 공개는 한다.
  - 이 게임의 **계정별 유한 배열**은 뽑을수록 확률이 바뀌는 방식 → 시행령 별표 3의2의 「확률 변동」 표시 사항 확인 필요.
    레벨업 100%는 확률형이 아니라 이미 빠졌지만(GDD §11-8) **가챠 자체는 확률형 아이템이다.**
- **청약철회**(전자상거래법 7일) — 사용한 디지털 콘텐츠는 제한 가능하나 **결제 전 고지 필요**.
- **미성년자 결제** — 법정대리인 동의 없는 결제는 취소 가능(민법).
- **다크패턴 금지**(전자상거래법 개정, 2025-02) — 가격 쪼개 보여 주기·취소 방해 금지. 금화 가격·묶음 표시에 해당.
- **환전 금지** — 금화의 현금화·사용자 간 현금 거래 통로를 만들면 사행성 규제. 게임 안에서만 쓰면
  선불전자지급수단 규제도 피한다(확인 권장).
- **국내대리인 제도**(2025-10)는 **해외** 게임사 대상 — 한국 사업자와 무관.

### 6.3 해외

- **루트박스 규제**: 벨기에(유료 루트박스 사실상 금지) · 브라질(미성년자 대상 제한, 확인 필요) ·
  일본(컴프가챠 금지) · 중국(판호 필요, 별개 시장). 가장 쉬운 대응은 **배포 국가에서 빼는 것**.
- **개인정보**: GDPR · CCPA · COPPA(13세 미만 받지 않도록 연령 확인).

## 7. 로드맵 (다시 시작할 때)

| 단계 | 내용 | 사업자·법적 요건 |
|---|---|---|
| **P0** | 결제 원장·주문 테이블, `mutateProfile` 확장 또는 `grantPurchase()`, `FakeProvider` 회귀, 운영에서 개발용 지급 부팅 거부 | 불필요 |
| **P1** | 금화 충전 화면 + 토스페이먼츠 **테스트 모드**, 웹훅, 결제 내역 화면 | 불필요 |
| **P2** | 환불·청약철회 처리, 구매 확인창 고지 문구, 약관·환불정책·개인정보처리방침, 가챠 확률 공시 화면, 관리자 페이지 | 문서 작성 |
| **P3** | 실결제 전환 | 사업자등록 · 통신판매업 · **GRAC 등급분류** · PG 심사 |
| **P4** | 해외 웹 결제 (Xsolla 계열 MoR 어댑터) | MoR 계약 |
| **P5** | Android 인앱결제 어댑터 (배포 시점에 다시 논의) | Google 개발자 계정 |

P0~P2는 사업자 없이 바로 할 수 있다. 등급분류는 게임물 제출이 필요해 시간이 걸리므로 P1 무렵에 절차를 알아 둔다.

**미리 읽어 둘 것**: 토스페이먼츠 개발자센터(결제위젯·승인 API·웹훅) · 공정위 전자상거래법 청약철회
가이드와 모바일게임 표준약관 · 게임물관리위원회 등급분류 신청 안내와 확률형 아이템 표시 가이드라인 ·
(P4·P5 때) Xsolla Pay Station, Google Play Billing 「구매 처리」 문서.

## 8. 아직 정하지 않은 것

1. **환불 뒤 이미 쓴 금화** — 잔액 음수 + 결제 제한으로 갈지, 다른 방식으로 갈지.
2. **첫 결제 경로** — 웹(국내 PG)부터인지, Android 인앱결제와 함께인지.
3. **금화 팩 구성 확정** — 지금 표(10/60/120냥 ↔ 1,000/5,000/10,000원)를 그대로 쓸지, 보너스율.
4. **관리자 페이지 범위와 시기** — 결제 전에 먼저 만들지.
5. **개발용·운영용 Supabase 프로젝트 분리** 시점.
