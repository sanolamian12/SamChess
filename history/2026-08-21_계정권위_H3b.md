# 2026-08-21 — 계정 권위 H3b: 참가비·거절 군량·환불 서버 재검증

H3a(인증·계정 서버 이전)에 이어지는 세션. H3a는 신원(누가 접속했는가)만 서버가
검증했다 — 참가비·거절 페널티·환불은 여전히 클라이언트가 계산해서 그대로
`PUT /profile`했으므로, 클라이언트를 고치거나 API를 직접 호출하면 군량을 공짜로
채울 수 있었다(§5-61이 예고해 둔 자리). 이번 세션이 그 세 지점을 서버 권위로 옮겼다.

## 1. 설계 전 — 사용자 확인을 받은 것 둘

코드부터 짜지 않고 설계안을 먼저 정리해 확인받았다(HANDOFF가 그렇게 요청했다).

- **범위를 다시 가른다.** HANDOFF가 H3b에 "AI 대전 서버 이관을 이 세션에 넣을지"를
  함께 물어 뒀는데, **가르기로 했다** — AI 대전은 Colyseus 방이 아예 없어 이번
  패턴("서버가 이미 권위를 가진 사건에 반응한다")이 적용될 자리가 없고, 결국 전투
  시뮬레이션 자체를 서버로 옮기는 훨씬 큰 일이 된다. H1/H2/H3를 가른 것과 같은 이유.
- **구현 방식** — 클라이언트가 부르는 사용자-인증 액션 엔드포인트(`POST /match/spend`
  같은 것)가 아니라, **Colyseus 셸이 `server-api`를 직접 호출하는 내부 API**를
  골랐다. 참가비·거절·환불은 클라이언트가 임의로 주장하는 값이 아니라 이미
  `QueueRoom`/`BattleRoom`이 권위 있게 결정해 둔 사건이라, 그 사건이 일어나는 순간에
  직접 반영하는 편이 "같은 방을 두 번 정산" 같은 멱등성 문제를 새로 안 만든다.

두 번째 확인에서 **알려진 공백**도 명시적으로 남기기로 했다 — `PUT /profile`은
여전히 클라이언트가 보낸 `grain`을 통째로 신뢰한다(직접 API 호출로는 여전히
군량을 불릴 수 있다). 이걸 막으려면 시간 기반 군량 충전(`syncGrain`, 지금도
클라이언트가 "지금"을 넣는다)까지 포함한 **경제 전체**를 서버 권위로 옮겨야 하고,
그건 AI 서버 이관과 비슷한 크기의 별도 작업이다. 이번 세션은 온라인 매칭의
**정상 클라이언트 흐름**(참가비·거절·환불)만 막았다.

## 3. 결정 — 왜 그렇게 정했나

### 순수 판정과 부수효과를 갈랐다

`room-logic.ts`의 `step()`과 `queue-logic.ts`의 `enqueue`/`confirm`/`decline`/`gone`은
전부 순수 함수이고 시각만 인자로 받는다 — 가짜 시계로 판 하나를 통째로 미는 회귀가
그 순수성에 기댄다. `server-api` 호출은 네트워크 I/O라 순수할 수 없으므로, **판정이
이미 끝난 뒤** 그 결과에 반응하는 부수효과로 Colyseus 셸(`QueueRoom.ts`·
`BattleRoom.ts`)에 뒀다 — `out` 통을 뿌리는 것과 정확히 같은 자리(§5-79·80).

### 참가비는 좌석 예약 **전에** 기다리고, 거절·환불은 기다리지 않는다

`QueueRoom.openBattle()`은 `chargeGrain`(참가비) 둘을 `Promise.all`로 기다린 뒤에야
`matchMaker.createRoom`을 부른다 — "참가비는 방이 열린 순간에" 나간다는 §5-84의
의미가 서버 쪽에서도 실제로 지켜지게 하려는 것이다. 반대로 `doDecline()`의 거절
군량과 `BattleRoom.dispatch()`의 환불은 `void chargeGrain(...)`으로 기다리지 않는다
— 이미 큐 재배치·방 종료가 끝난 뒤의 정산이라 사용자에게 보이는 흐름을 막을 이유가
없다.

### 실패해도 판을 막지 않는다

`economy.ts`의 `chargeGrain`은 `fetch` 실패를 전부 잡아 로그만 남긴다.
"`server-api`가 꺼져 있어도 게임은 돈다"(§5-61)와 같은 결 — 재시도 큐 같은 내구성
장치는 이번 세션의 범위 밖으로 뒀다. `smoke:online`이 `server-api`를 **안 띄운
채로** 여전히 통과하는 것이 이 결정을 실제로 검증한다(`[grain] spend 호출 실패`
로그가 찍히고도 판은 271턴 끝까지 돈다).

## 4. 검증 — 화면 값만으로는 부족했다

`smoke_meta.ts`에는 이미 "참가비 — [전투준비]에서 10 → 7" 같은 검사가 있었는데,
이건 `window.__profile.current.grain`(클라이언트 React 상태)을 읽는다 — 클라이언트가
여전히 `spendGrain()`/`declineMatch()`를 로컬로 계산해 화면에 낸다(이번 세션에서
그건 안 바꿨다). 그래서 이 검사는 H3b가 실제로 도는지 증명하지 못한다 — 서버 호출을
통째로 지워도 통과했을 것이다.

`apiGet()`(서버 GET을 직접 부르는, 이미 있던 헬퍼)으로 참가비·거절 뒤 **서버가
가진 값**을 따로 확인하는 assertion을 둘 추가했다. 둘 다 통과했다:

```
✓ 거절 군량 — server-api가 직접 반영했다(H3b, 클라이언트 값이 아니라 서버 GET으로 확인)
✓ 참가비 — server-api가 직접 반영했다(H3b, 클라이언트 값이 아니라 서버 GET으로 확인)
```

**환불(`RoomClose.refund`) 경로는 자동화된 검증이 없다** — `smoke_online.ts`는
"한쪽이 끊겨도 유예 안에는 방이 그대로다"까지만 보고 실제로 방이 접히는 것까지는
안 본다(재접속 유예·유휴 상한이 실제 분 단위라 스모크에서 기다리기엔 비싸다).
`BattleRoom.dispatch()`의 환불 배선은 참가비·거절과 같은 `chargeGrain` 호출을 같은
`/internal/grain` 엔드포인트로 부르는, 구조적으로 동일한 5줄이라 코드 검토로
확인했다 — 검사가 안 잡는 것은 주장하지 말고 적어 둔다(CLAUDE.md의 그 규칙).
새 세션에서 강한 확신이 필요하면 room-logic의 이탈/유휴 상수를 짧게 바꾼 별도
스모크 경로를 만드는 것을 고려할 것.
