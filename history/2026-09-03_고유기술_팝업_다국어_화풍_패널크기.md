# 2026-09-03 — 고유기술 팝업 다국어화·화풍 리스킨·패널 크기 통일

> 이 문서는 **한 대화 세션의 기록**이다. 프로젝트의 현재 상태와 규칙은
> [`HANDOFF.md`](../HANDOFF.md)와 [`Design/GDD.md`](../Design/GDD.md)가 정본이며,
> 여기는 "무엇을 왜 그렇게 정했는가"와 "어디서 넘어졌는가"를 남긴다.

## 왜 이 작업인가

사용자가 궁궐 화면들을 계속 손보던 중, 고유기술 팝업(장수 카드에서 배너를
눌렀을 때 뜨는 「기술 명·기술 유래·기술 효과」 팝업)을 스크린샷으로 보여주며
세 가지를 요청했다: (1) 「기술 명」·「기술 유래」·「기술 효과」 라벨과 그
내용을 다국어 지원, (2) 팝업 배경이 글자는 잘 보이지만 삼국시대 화풍과
안 어울리니 생성형 AI 프롬프트를 만들어 적용, (3) 위 작업 확인 후 이어진
피드백 네 가지(라벨 다국어화 재확인·패널 크기 통일·기술명 표기 순서·
SP 위치 이동) — 총 세 라운드에 걸친 세션이다.

## 한 일

### 1. 고유기술 이름·효과 서술 다국어화

- `packages/data/src/index.ts`의 `UniqueSkillData`에 `origin`과 같은 규약으로
  `nameI18n`·`textI18n`(둘 다 `Partial<Record<StoryLang, string>>`) 추가.
- `tools/extract_data.py`의 `extract_skill_lore()`를 확장해 `sam_skills.csv`의
  `name_{lang}`·`text_{lang}` 열도 읽는다(`origin_{lang}`과 나란히). **`origin`은
  S+E급 31종만 있는데 `name`/`text`는 40종 전부** 있어야 해서, 언어 맵 셋을
  독립적으로 모으는 `collect()` 헬퍼로 갈랐다.
- `packages/client/src/i18n/story.ts`에 `pickSkillName()`(없으면 한국어
  `name`으로 물러남, `pickOfficerName`과 같은 규약)·`pickSkillText()`(같은
  규약, `text`로 물러남) 추가. `SkillModal.tsx`가 이 둘을 쓴다.
- **번역 콘텐츠는 두 차례 백그라운드 에이전트에 맡겼다**(40종 × 9개 언어 ×
  이름/효과 두 필드 = 720줄 규모라 직접 쓰기엔 컸다):
  - 1차: `assets/Languages/sam_skills.csv`에 `name_{lang}`·`text_{lang}` 열을
    새로 붙이고(9개 없던 A/B급 행도 새로 만듦), 40종 전부 채웠다. 효과 서술은
    HP/MP/SP/WT/Critical 같은 게임 용어를 라틴 표기로 유지하고, 숫자
    표기(`1.9일` → `1.9 days`)는 소수점을 그대로 썼다.
  - 라벨 4종(`skill.name`/`skill.origin`/`skill.effect`/`skill.close`, 새로
    추가한 `skill.sp`)은 직접 9개 언어 `strings/*.json`에 append했다 —
    `skill.close`는 기존 `levelup.back`의 번역을 그대로 재사용(같은 "뒤로"
    뜻). 처음엔 Python `json.dump`로 통째로 다시 써서 원본의 빈 줄 구분이
    사라지는 diff를 냈다가, `git checkout`으로 되돌리고 `Edit`로 꼬리에만
    append하는 방식으로 다시 했다 — **JSON을 파이썬으로 재직렬화하면 사람이
    넣어 둔 빈 줄 구분이 조용히 사라진다**는 걸 이번에 겪었다.

### 2. 기술명 표기 — 라틴 문자는 로마자 읽기, 몽골어는 키릴 발음

- 첫 번역 라운드에서 라틴 문자 언어(en/pt-BR/pt-PT/it/es-419)의 `name_{lang}`을
  "뜻 번역"(예: "Plucking the Arrow, Devouring the Eye")으로 채웠는데,
  사용자가 "한자 원문은 그대로 두고 각국 언어로 **읽는 법**을 써 달라"고
  정정 — 예시로 `Bal-si-dam-jung` 형태를 줬다.
- 라틴 문자 5개 언어는 **이미 있는 `skill.id`(로마자 슬러그)를 첫 글자만
  대문자로** 바꿔 재사용했다(`bal-si-dam-jeong` → `Bal-si-dam-jeong`) — 어차피
  `romanize(name)`로 계통적으로 뽑은 표기라 새로 만들 필요가 없었다. 이건
  코드(파이썬 한 줄 스크립트)로 CSV를 직접 고쳤다.
- 몽골어(키릴 문자)만 별도 에이전트에 맡겼다 — 한글 발음을 몽골 키릴로
  음절 전사하는 건 기계적으로 하기엔 실수하기 쉬운 언어 작업이라 판단했다.
  결과 예: `bal-si-dam-jeong` → `Бал-ши-дам-жон`. 한글 원문에 띄어쓰기가 있는
  3개 기술(`화용도 의석조조` 등)은 몽골어 출력에도 그 자리에 띄어쓰기를
  살렸다.
- 일본어·중국어(간체/번체)는 **손대지 않았다** — 그 언어들의 `nameI18n`은
  이미 한자(또는 그에 대응하는 신자체/간체) 표기라 원본 그대로 "읽을 수
  있는 형태"이기 때문이다.
- 마지막 라운드에서 사용자가 "한자 원문이 먼저 오고 괄호로 각국 발음"으로
  순서를 다시 정정 — `SkillModal.tsx`의 이름 줄을
  `<b>{skill.hanja}</b> <span className="reading">({name})</span>`로 바꿨다
  (예전엔 `<b>{읽기}</b> {한자}` 순서였다). CSS 클래스도 `.hanja`(전에는
  한자 자리)를 `.reading`(지금은 괄호 안 읽기 자리)으로 이름을 바꿔 뜻을
  맞췄다 — 클래스 이름이 실제로 담는 내용과 안 맞으면 다음에 헷갈린다.

### 5. 패널 크기 통일 — 진짜 원인은 CSS 값이 아니라 DOM 중첩이었다

가장 오래 걸린 항목. 사용자가 처음엔 "패널 크기가 안 변했어"라고만
말했는데, `.ofc-skill-modal`에 이미 `.ofcard-modal`과 같은
`max-width: 21rem`을 넣어 뒀었다 — **숫자는 맞는데 화면에서는 안 맞았다.**

원인을 실제로 그려서(정적 mockup이 아니라 `OfficerCardModal`을 진짜
`react-dom/client`로 마운트해 Playwright로 `getBoundingClientRect()`를 잰
값으로) 확인했다:

- `SkillModal`은 `OfficerCard`(클래스 `.ofcard`, `position: relative`)
  **안에서** 열린다(`{skillOpen && skill && <SkillModal .../>}`가
  `<section className="place-panel ofcard">` 안에 있었다).
- `.modal-back`은 `position: absolute; inset: 0`인데, 이 `inset: 0`의
  기준점(containing block)은 **가장 가까운 `position`이 static이 아닌
  조상**이다 — 그게 `.ofcard-modal`(21rem 폭의 진짜 카드)이 아니라
  `.ofcard` 자신이었다. `.ofcard`는 자기 테두리(`border-image` 9분할,
  `.scr-officers .place-panel`의 `border-width: 1.5rem 1rem`)만큼 이미
  안쪽으로 줄어든 상자라, 그 안에서 다시 `.modal-back`의 `padding: 1rem`까지
  빼면 실측 272px(17rem) — 카드의 336px(21rem)보다 눈에 띄게 좁았다.
  (`max-width: 21rem`을 넣어도 컨테이너 자체가 19rem이라 100% 규칙이 그
  좁은 값에 걸려 있었다.)
- 고친 방법: **CSS 숫자가 아니라 컴포넌트 구조를 고쳤다.** `RankingCommon.tsx`의
  `OfficerCard`에서 `skillOpen` 상태와 `<SkillModal>` 렌더를 걷어내
  `OfficerCardModal`(그 바깥 컴포넌트, `.ofcard-modal`과 형제 자리)로
  올렸다. `OfficerCard`는 `onOpenSkill` 콜백 prop만 받는다. 이제
  `SkillModal`의 `.modal-back`은 `.ofcard-modal`의 `.modal-back`과 **같은
  조상**(그 바깥의, `.scr-bg`에 `inset: 0`인 `.modal-back`)을 기준점으로
  쓰므로 폭이 정확히 같다 — 실측(진짜 컴포넌트 마운트) `outer: 336px`,
  `inner: 336px`, 같은 `x` 좌표.
- 세로 시작 위치는 별도로 안 맞춰도 됐다 — 둘 다 같은 바깥 `.modal-back`의
  자식이라 그 정렬 규칙(`.scr-officers`는 기본 가운데, `.scr-ranking-officer`는
  `align-items: flex-start`)을 똑같이 받는다. **폭만 맞으면 나머지는 같은
  조상을 공유하는 것만으로 저절로 맞았다.**

## 새 대화로 이어갈 때

- 고유기술 팝업의 다국어·화풍·크기 문제는 **완결**됐다 — 새 스킬이 추가되면
  `sam_skills.csv`에 그 스킬의 `name_{lang}`·`text_{lang}` 행만 채우면
  자동으로 배선된다(`npm run extract`).
- **중첩된 모달의 폭이 CSS 값을 맞춰도 안 맞으면, 가장 먼저 `position:
  relative`인 조상이 몇 겹인지부터 센다** — `max-width` 숫자가 아니라
  `.modal-back`의 실제 기준점(containing block)이 어디인지가 진짜 원인일
  수 있다(이번 세션의 핵심 교훈). CLAUDE.md의 "팝업은 「내용을 올리는」
  규칙에서 빼야 한다" 항목과 사촌 격 — 이번 것도 CLAUDE.md에 옮겨 적을
  가치가 있는 교훈이라 판단되면 다음 세션에서 추가할 것.
