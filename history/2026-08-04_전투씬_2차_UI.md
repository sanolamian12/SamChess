## 2. 기획자가 내린 결정 (이 세션에서 확정)

### 턴 3단계를 화면에 그대로 올린다

GDD §3.4의 구조를 UI가 그대로 따라간다. 기획자 지침(08-03)으로 확정했다.

```
[1] 고유기술?  조건이 되면 먼저 묻는다 → [고유기술 발동] [보류]   ← 턴을 소비하지 않는다
[2] 이동       갈 칸을 고른다. 제자리를 눌러 그대로 대기해도 된다
[3] 행동       공격 / 책략 / 명상 중 하나
```

「보류」를 따로 둔 이유는 **고유기술이 [3]의 선택지가 아니기 때문**이다. 이동해 버리면 못 쓰므로
턴 맨 앞에서 한 번 묻고 지나가야 한다. 안 물으면 "쓸 수 있었는데 이동해서 날린" 상황이 생긴다.

### WT 바는 「차오르는」 방향

GDD §3.10의 원문 "WT(흰색→회색)"가 두 갈래로 읽혀 확인했다.
행동이 멀면 빈 회색, 차례가 다가올수록 흰색으로 차오르고, 제어권을 얻으면 금색으로 가득 찬다.
**"다음이 누구냐"를 한눈에 읽기 위함**이다 — 잔여 WT를 길이로 보여주는 반대 방향이 아니다.

### 배지는 개수만, 이름은 팝업이 맡는다

상태이상이 22종인데 셀은 96×120이고 기본 줌에서는 30px대로 줄어 글자 배지가 뭉갠다.
그래서 타일에는 **점(dot)으로 개수만** 찍고, 무엇이 걸렸는지는 창에서 읽는다.

처음에는 제어 모달 하단에 붙였는데 눈에 안 띄어서 **독립 팝업으로 승격**했다(기획자 요청).
제어권과 무관하게 아무 기물이나 눌러 볼 수 있다 — "공격하려는 적에게 뭐가 걸렸나"를
확인할 통로가 필요했다. GDD §3.9 「정찰」의 기물 클릭과 같은 용도다.

### 데모 편성을 Lv9 · HP · 환술로

Lv1은 **책략이 하나도 없어 버프·디버프가 생기지 않는다.** 배지에 띄울 데이터가 없고
MP를 쓸 데가 없어 「명상」도 의미가 없었다. HP 50이면 한두 대에 죽지 않아 상태이상이
화면에 남아 있는 시간도 길어진다.

> **`tools/balance.ts`는 Lv1 그대로 뒀다.** 저기까지 바꾸면 5000판 실측치와 비교가 안 된다.

## 3. 밟은 지뢰 ★ 다시 밟지 말 것

### 3-1. 하이라이트가 유닛 타일에 가려진다 — 가장 오래 헤맨 것

책략 조준 후보를 칠했는데 **화면에 아무것도 안 나왔다.** `debugAimCells()`는 후보 2칸을
정확히 돌려주고, 그래픽 버퍼에도 명령이 쌓여 있었다. 데이터도 맞고 그리기도 했는데 안 보였다.

원인은 깊이였다. 하이라이트가 depth 5, 유닛 타일이 depth 10인데
**공격 대상과 조준 후보는 정확히 유닛이 서 있는 칸**이라 초상화가 그대로 덮어 버린다.
빈 칸을 칠하는 이동 하이라이트만 잘 보였던 것이라 여태 드러나지 않았다.

→ **하이라이트를 두 층으로 나눴다.** 채우기는 유닛 아래(depth 5), 테두리는 유닛 위(depth 15).
`smoke:ui`가 `debugMarkCommands() > 0`으로 이 회귀를 막는다.

> 기획자가 작업 지시에서 "투명도 처리가 필요할 수 있다"고 미리 짚었던 그 문제다.
> **먼저 예상된 문제를 그대로 밟았다** — 지시에 적힌 우려는 먼저 확인하고 시작할 것.

### 3-2. WT 게이지에 `unit.wt`를 그대로 쓰면 순간이동한다

`advanceTime()`은 다음 제어권까지 **한 번에 점프**하므로 `unit.wt`는 이미 점프가 끝난 뒤의 값이다.
화면(`displayTime`)은 아직 따라잡는 중인데 게이지만 먼저 도착해 있다.

→ 따라잡지 못한 만큼(`state.time − displayTime`)을 되돌려 더하면 실시간으로 차오른다.
`BattleScene.syncWaitBars()` 참조. 조용히 깨질 수 있는 종류라 스모크로 고정했다.

### 3-3. 검증 기준을 잘못 잡아 정상 동작을 실패로 판정했다

책략 시전을 "상태이상이 붙었는가"로 확인했는데, **환술은 저항당하면 상태가 안 붙고
MP만 소모된다**(GDD §3.7 확정). 규칙대로 동작한 것을 버그로 잡았다.

→ 시전 성사 여부는 **MP가 줄었는가**로 본다. 확률이 끼는 판정은 "결과"가 아니라
"비용이 나갔는가"로 확인해야 한다.

### 3-4. 그 밖에

- **모달을 화면 아래 가운데 두면 P1 진영(하단 5행)을 가린다** — 자기 유닛과 이동 후보 칸이
  그대로 덮인다. 오른쪽 여백으로 옮겼다.
- **기본 줌에서는 타일 위의 것이 안 보인다** — 20×25를 화면에 다 넣으면 셀이 30px대라
  5px 바 3줄이 뭉갠다. `npm run shot -- --zoom 2.4`를 만들어 제어권 유닛에 카메라를 붙였다.
- **스모크가 버튼을 `nth-child`로 찾고 있었다** — 버튼이 하나 늘자 조용히 엉뚱한 것을 눌렀다.
  `data-action`으로 바꿨다.
- **상대 차례는 350ms라 밖에서 폴링하면 놓친다** — 페이지 안에서 `requestAnimationFrame`으로
  표본을 모아야 잡힌다. 시간이 흐르는 구간(0.3초)도 마찬가지다.

## 4. 구조에서 기억할 것

### 대상이 필요한 행동도 활성 여부를 엔진에 묻는다 ★

「이동」·「공격」·「책략」은 의도 하나로 `validate()`를 물을 수 없다(대상이 있어야 판정된다).
그래서 **엔진이 준 후보를 하나씩 넣어 물어보고 하나라도 통과하면 켠다.**
조준 하이라이트도 같은 후보 목록이라 **화면에 칠해진 칸 = 엔진이 통과시킨 칸**이다.

이 설계가 값어치를 증명한 순간이 있었다. 3v3인데 조준 후보가 2칸만 나와서 확인해 보니
적 하나가 「백의도강」으로 무적이라 지정 조준에서 빠진 것이었다(GDD §12 A2).
**클라이언트에 그 규칙을 적은 곳은 한 줄도 없다.**

이를 위해 `effects.ts`를 패키지 밖으로 내보냈다(`aimingSpec` / `tacticMpCost`) —
조준 규약을 클라이언트가 다시 구현하지 않게 하려는 것이다.

### 제자리 대기는 엔진에 보낼 의도가 없다

이동은 원래 해도 되고 안 해도 되는 단계라 **"안 한다"를 선언하는 `Intent`가 룰에 없다.**
화면이 하는 일은 이동 하이라이트를 걷고 행동을 고르라고 알리는 것뿐이고,
「이동」을 다시 누르면 무를 수 있다. 없는 의도를 만들지 않는 편이 맞다.

### `STATUS_META` — 화면이 스스로 분류하지 않게

`types.ts`의 `StatusId` union에 주석으로만 있던 `// 버프` / `// 디버프` 구분을
기계가 읽는 표로 옮겼다. `Record<StatusId, …>`라 **상태를 새로 추가하면 표가 비어 컴파일이 깨진다.**
화면에 조용히 빠지는 일이 없다.

스모크도 같은 표를 보게 노출했다 — 목록을 테스트에 다시 적으면 둘이 어긋나도 통과해 버린다.

### 이름을 바꾸면 id가 바뀐다 ★

id는 이름에서 만든 로마자 슬러그다(GDD §9). 「장요」→「장료」로 표준을 바꾸자
`jang-yo` → `jang-ryo`가 되고 초상화 경로·웹용 파일까지 따라왔다.
**저장된 데이터가 없어 지금은 공짜지만, 메타(계정·보유 카드)가 붙은 뒤에는 마이그레이션이 따른다.**

「장료」건은 **표준의 방향을 뒤집은** 사례이기도 하다. "초상화 파일명이 표준"이라는 규칙(GDD §9)은
그대로 지키면서, 데이터를 파일명에 맞추는 대신 **파일명 쪽을 바꿨다.**

### 조종은 `statuses`가 아니라 `control`에 들어간다

「초선」·「삼고초려」의 조종 상태는 상태이상 배열이 아니라 별도 필드다.
배지·팝업 양쪽에서 빠뜨리기 쉬워 **디버프 하나로 세어** 함께 보여 준다.

## 5. 검증 방법

층 구성은 그대로 5개이고, 이번에 **화면 연동 층이 크게 늘었다** (확인 항목 3개 → 18개).

| 층 | 도구 | 이번에 추가된 것 |
|---|---|---|
| 데이터 정합성 | `npm run extract` | **연출 이미지 대조**(`check_skill_art`) |
| 순수 로직 | `npm test` (113건) | — (룰 엔진을 안 건드렸다) |
| 밸런스 | `npm run balance -- 5000` | — |
| 화면 연동 | `npm run smoke:ui` | HUD · WT 게이지 · 모달 3상태 · 턴 3단계 · 배지 · 팝업 |
| 눈으로 | `npm run shot -- --zoom` | 확대 옵션 (타일 위의 것은 확대해야 보인다) |

스모크가 확인하는 것 중 값어치가 큰 셋:

- **WT 게이지가 시간이 흐르면 실제로 줄어드는가** — `displayTime` 보정이 빠지면 여기서 걸린다
- **조준 후보가 유닛 위에 표시되는가** — 3-1의 회귀를 막는다
- **타일 배지가 센 개수가 엔진 상태와 같은가** — 화면이 거짓말을 하는지 본다

### 화면 확인용으로 뚫은 통로

- `?sp=15` — 고유기술은 SP를 4~7 모아야 열려 4~7일을 기다려야 한다. 그걸 건너뛴다
- `shot.ts --zoom` — 제어권 유닛에 카메라를 붙인다
- 씬의 `debug*` 접근자 — 조준 후보 · 잔여 WT · 배지 개수 · 그린 명령 수

## 6. 에셋 — `assets/SpecialSkills/`

기획자가 고유기술 시전 연출용 이미지 40장을 넣었다. 고유기술 40종과 개수가 정확히 일치한다.
**아직 화면에 붙지 않았다.**

파일명 규약은 `장수이름 기술이름.jpg`이고, 공유 기술은 이름을 쉼표로 잇는다.
**기술명 자체에 공백이 있는 3종**(「신재조영 심재촉」·「인중여포 마중적토」·「화용도 의석조조」)은
이 규칙과 충돌해서, 파일은 공백을 지워 붙여 쓴다 → 대조할 때 **양쪽 다 공백을 지우고** 비교한다.

`check_skill_art()`가 초상화 대조와 같은 자리에서 이걸 확인한다. 처음 8건이 어긋났고
기획자가 전부 정정해 지금은 0건이다. **지금은 경고로만 알리고 빌드를 막지 않는다** —
화면이 아직 이 이미지를 쓰지 않기 때문이다. 붙일 때 `fail`로 올리면 된다.

> 정정 과정에서 엑셀 원본도 갱신됐다 — 「십면매복」의 장노 행이 지워져
> GDD §9의 「제거할 행 1건」이 원본에서 해소됐다.

전투 씬 2차는 **다섯 항목이 전부 끝났다**(바·HUD·모달·시전 UI·배지).

`playback.ts`가 이미 "서버가 `BattleEvent[]`를 브로드캐스트하면 클라가 재생하는" 구조라
그 층은 다시 만들지 않는다. 넷코드에서 새로 필요한 것은 방·연결·재접속과,
지금 클라이언트가 로컬로 하고 있는 `apply()` 호출을 서버로 옮기는 일이다.

이번 세션에서 **UI가 이미 서버 권위 구조를 전제하고 있다**는 점이 도움이 된다 —
버튼 활성 여부도, 조준 후보도 전부 `validate()`에 물어서 만들었기 때문에
판정 주체가 서버로 바뀌어도 화면 로직은 그대로다.

### 남겨둔 것

| 항목 | 비고 |
|---|---|
| 디자인 지침 | 기획자가 따로 준다고 했다. 지금 화면의 색·크기·배치는 **기능 확인용**이다 |
| 하후돈 스킬 설명문 | 엑셀에 "time 490 동안 받는 내가 데미지가 절반이 됨"으로 어순이 뒤집혀 있다. 동작에는 무관 |
| 연출 이미지 화면 연결 | 붙일 때 `check_skill_art`의 `note`를 `fail`로 올린다 |
| A급↔B급 승률 격차 12%p | 밸런스 조정할 때 확인 |

### 작업 방식에서 확인된 것

- **기획자가 미리 짚은 우려는 먼저 확인하고 시작할 것.** 이번에 "투명도 처리가 필요할 수 있다"고
  적어 준 그 문제를 그대로 밟았다(§3-1).
- **정상 동작을 실패로 잡지 않도록 검증 기준을 먼저 따져볼 것.** 확률이 끼는 판정은
  결과가 아니라 비용으로 확인한다(§3-3).
- **애매한 결정은 선택지와 파급을 같이 물을 것.** 「장료로 통일」이 파일명만 바꾸는 뜻인지
  이름 표준을 뒤집는 뜻인지 갈렸는데, id까지 바뀐다는 걸 함께 보여 주니 한 번에 정리됐다.
