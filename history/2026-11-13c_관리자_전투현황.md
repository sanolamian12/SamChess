# 관리자 「전투」 — 지금 벌어지고 있는 판 (2026-11-13)

기획자 요청: 관리자 사이드 메뉴에 **「전투」** — 계정과 상관없이 **벌어지고 있는 전투**를 본다. 탭은 **야전 · 공성전 · 도적떼 전투 · 튜토리얼 전투**.
(같은 시각 다른 세션이 본 게임의 건물 화면 UI를 고치고 있어 그쪽 파일 — `i18n/strings/*` · `MarketScreen.tsx` · `style.css` — 은 건드리지 않았다.
`App.tsx`는 그 세션이 안 고치고 있어 접속 핑 세 줄만 더했다.)

## 1. 판이 어디 사는가 — 넷이다

| 탭 | 판 | 사는 자리 | 관리자 API가 읽는 길 |
|---|---|---|---|
| 야전 | 사람 대 사람(대기열) · 선전포고 | **대전 서버(Colyseus) 프로세스의 메모리**(`BattleRoom`) | 대전 서버의 새 내부 길 `GET /internal/battles`(서버 간 비밀) |
| 야전 | AI 대전 | 계정의 `aiBattle`(`status: fighting`, `defender` 없음) | `profiles` 행 |
| 공성전 | AI 대전 + 수비군 | 계정의 `aiBattle`(`defender` 있음) | `profiles` 행 |
| 도적떼 | 방어전 | 계정의 `raid`(`status: fighting`) | `profiles` 행 |
| 튜토리얼 | — | **서버에 없다**(클라이언트만 돈다, 서버는 끝낸 기록만) | 접속 핑에 판 id를 싣게 했다 — `presence.tutorial` · `tutorial_at` |

AI 대전은 전적 갈래로는 야전이 아니지만(전적에 안 센다), 기획자의 탭 넷에 들어갈 자리가 야전뿐이라 야전 탭에 「AI 대전」 표지로 둔다.

## 2. 고친 것

**계약** — meta `LiveRoomSummary` · `LiveRoomSeat`(대전 서버 ↔ 관리자 API — 두 프로세스가 서로 import하지 않아 meta에), 관리자 `AdminBattlesResponse` ·
`AdminLiveBattle` · `AdminBattleSide` · `AdminBattlePlayer` · `AdminBattleKind` · `AdminFieldVia`.

**대전 서버**
- `room-logic.ts`의 `roomSummary(room, roomId, war, openedAt)` — 순수, 회귀 하나(`room-logic.test.ts` 끝): 두 자리 · 명단 · 접속 · 살아 있는 수 · 단계.
- `BattleRoom.summary()` — 방이 열린 뒤에만(둘이 모이기 전은 `null`). 열린 시각 · 선전포고 id를 들고 있게 했다.
- `internalHttp.ts` — `GET /internal/battles`, `x-internal-secret`가 맞아야(비밀이 비면 아무에게도 안 연다), 그 밖의 길은 404.
- `main.ts` — HTTP 서버를 직접 만들어 `WebSocketTransport({ server })`로 넘긴다. Colyseus는 매치메이킹 경로만 가로채고 나머지 요청을 앞서 걸린 리스너로 넘긴다
  (`Server.attachMatchMakingRoutes`) — 그래서 같은 포트에 산다.

**게임 API** — `POST /presence`가 `tutorial`(알려진 튜토리얼 id만, `isTutorialId`)을 받아 `presence.tutorial`에 적는다. 시작 시각 `tutorial_at`은 **판이 바뀔 때만** 다시 찍는다.
스키마 두 칸(`sql/schema.sql`), 개발 DB에는 `db:migrate`를 돌렸다.

**클라이언트** — `App.tsx`가 튜토리얼 화면이면 그 id를 핑에 싣고, 바뀌면 바로 한 번 보낸다(`presence.ts`).

**관리자 API** — `admin/battles.ts`의 `listLiveBattles()` · `GET /admin/battles`(권한 view). 대전 서버는 3초까지만 기다리고, 못 닿으면 나머지 셋은 그대로 내고 `rooms.ok: false`.
**정산하지 않는다** — 게임의 읽기(`syncAtServer`)는 60분 방치된 판을 패배로 정산해 버리므로, 되접기만 하고 자동 정산 시각을 `autoEndAt`으로 싣는다(지났으면 화면이 「방치 · 정산 대기」).

**관리자 화면** — `BattlesPage.tsx`(메뉴 「전투」, `#/battles`). 탭 넷 + 판 수 · 탭마다 한 줄 설명 · 10초마다 다시 읽기 · 시험 계정 거르기 · 대전 서버에 못 닿으면 붉은 줄.
- 야전: 갈래(대기열 / 선전포고 / AI 대전) · 모드 · 남군 · 상대(계정 · 부대 · 전투력 · 명단, 사람 대 사람이면 접속 · 생존 n/m) · 단계(AI는 덧붙인 수) · 시작 · 자동 정산
- 공성전: 공격 · 수비(수성전 / 방침 전 야전 판) · 수 · 시작 · 자동 정산
- 도적떼: 도시 · 도적 수 · 파수꾼 · 수 · 시작 · 자동 항복
- 튜토리얼: 계정 · 판(전투 기초 1 … · S급 · 장수 이름) · 시작 · 마지막 핑

## 3. 확인

`npm test` 1436 · `typecheck` · `typecheck:admin` 통과. **`npm run look:battles`**(새 도구 `tools/battles_ux.ts`)가 진짜 서버로 다섯 갈래를 세워 본다 —
계정 둘이 대전 서버의 고정 방에 붙어 편성 · AI 대전(시작 70분 전 = 방치) + 도적떼 · 공성전(수성전) · 튜토리얼 핑 → API의 다섯 줄 · 화면 네 탭(1280px 가로 넘침 0) · 계정 정리.
다른 세션이 8787 · 2567을 쓰고 있어 제 것을 2568 · 8789에 따로 띄우고 주소를 넘겨 돌렸다(`SAMCHESS_SERVER` · `GAME_API`).

**도구가 잡은 것 둘**
- 새 접속 핑 SQL이 같은 자리표시자(`$2`)를 `timestamptz` 칸과 `case` 식에 함께 써 Postgres가 「inconsistent types deduced」로 거절했다 — 핑은 실패해도 게임을 멈추지 않게
  삼키므로 **아무 말 없이 접속 기록 전체가 끊겼을 것**이다(공성전 「접속 중」까지). 형을 적어 고쳤다. 타입 검사 · 회귀로는 안 잡히는 자리다.
- 방은 아이템을 빼는 게임 API 왕복 뒤에 열린다 — 고정 1.5초 기다림으로는 아직 안 열려 있었다. 열릴 때까지 다시 묻는다.

## 4. 남은 것

- 운영 DB에 `presence.tutorial` · `tutorial_at`이 없다 — **`db:migrate:prod` 전에 이 서버 코드가 올라가면 접속 핑이 전부 실패한다**(배포 메모에 더했다).
- 판을 **들여다보기**(관전 · 판 상태 그림)는 없다 — 한 줄 요약뿐. 사람 대 사람 판은 대전 서버가 상태를 갖고 있어 붙일 수 있고, AI 대전 · 공성전 · 도적떼는 덧붙인 수로
  재생할 수 있다(방어 기록 리플레이와 같은 길). 필요해지면 기획으로.
- 대전 서버가 여러 프로세스로 늘면 `matchMaker.query`는 다른 프로세스의 방까지 보이지만 `getLocalRoomById`는 제 프로세스의 방만 준다 — 그때 `remoteRoomCall`로 바꾼다.
- 대기열(`QueueRoom`)에서 상대를 찾는 중인 사람은 아직 판이 아니라 안 보인다.
