# 2026-08-27 — 랭킹 화면(도시·부대·장수) · 장수 카드 · 인물 서사 연결(G1)

> 이 문서는 **한 대화 세션의 기록**이다. 프로젝트의 현재 상태와 규칙은
> [`HANDOFF.md`](../HANDOFF.md)와 [`Design/GDD.md`](../Design/GDD.md)가 정본이며,
> 여기는 "무엇을 왜 그렇게 정했는가"와 "어디서 넘어졌는가"를 남긴다.

## 왜 이 작업인가

사용자가 `docs/*.pptx` 46~49쪽에 도시/부대/장수 랭킹 화면을, 50~52쪽에 디자인
심화 가이드를, 53쪽에 장수 카드 예시를 직접 그려 넣고 세션을 시작했다. 처음
요청은 "궁궐·병영처럼 메뉴 버튼을 만들어 도시/부대/장수 랭킹 세 화면으로
연결해 달라"였고, 이후 pptx 심화 가이드·실기기 스크린샷을 주고받으며 필터·
정렬·표 열·레이아웃·장수 카드까지 반복적으로 다듬었다. 전형적인 스크린샷
기반 반복 피드백 세션이다.

## 한 일 — 크게 넷

### 1. 랭킹 메뉴 + 도시/부대/장수 세 화면 (46~49쪽 → 50~52쪽으로 재설계)

첫 구현은 탭 하나짜리 화면이었으나, 심화 가이드 스크린샷을 받고 나서
**메뉴 → 그 안의 화면 셋**(궁궐·병영과 같은 결)으로 다시 짰다.

- `RankingScreen.tsx` — [도시 랭킹]/[부대 랭킹]/[장수 랭킹] 세 버튼만 있는
  메뉴(`PlaceScreen`과 같은 패턴). 예전 `CityRecordsScreen`을 대체한다.
- `CityRankingScreen.tsx`/`SquadRankingScreen.tsx`/`OfficerRankingScreen.tsx` —
  각 판의 화면. 공용 조각(`RankingCommon.tsx`)에 `FilterSelect`/`ModeSelect`/
  `FilterRow`(리스트 박스 두 개를 모드-왼쪽·상대-오른쪽 한 줄로), `SortMenu`
  ([정렬 필터] 버튼 → 팝업), `SearchBar`(입력+[검색] 버튼, 제출해야 나간다),
  `InfoHeadCell`/`NoteRow`("총점" 같은 계산식 열 머리를 누르면 바로 아래 줄에
  공식이 펼쳐진다 — 표 밑에 늘 떠 있던 안내문을 없앤 자리), `useRankingRows`
  (top-5/검색 서버 요청 훅)를 모았다.
- `packages/meta/src/ranking.ts`(신설) — `cityRankRow`/`squadRankRows`/
  `officerRankRows` 세 함수가 **서버(전체 유저 스캔)와 클라(내 프로필 하나)**에서
  똑같이 쓰인다. "내 랭킹" 하단은 이 함수를 클라이언트가 직접 돌려 만들므로
  **서버 왕복이 없다** — top-5·검색만 서버가 필요하다(§5-61과 같은 결, 서버가
  죽어도 내 것은 보인다).
- `packages/server-api/src/ranking.ts`(신설) + `GET /ranking` — 로그인 유저면
  누구나 조회. `profiles` 테이블을 통째로 스캔(`SCAN_CAP` 자리표시자, 지금
  규모용)해 위 순수 함수로 행을 뽑고 정렬·검색·자른다. 새 스키마 없음
  ("아이디" 열을 빼기로 해서 `auth.users` 조인도 필요 없어졌다).
- **부대에 전적이 없던 걸 이번에 발견**했다 — `Squad`에 `record`가 없어서
  이력(`matches[]`, 200줄에서 꼬리를 던다)에서 파생시키면 오래 쓴 부대일수록
  통산이 조용히 줄었을 것이다. 계정 전적과 같은 패턴으로 `Squad.record`를
  새로 붙이고 `applyBattleResult()`가 `outcome.mySquad`(부대 **이름**이다,
  `BattleScreen.tsx`가 그렇게 싣는다)로 찾아 같이 올리게 했다.

### 2. 표·필터·레이아웃 — 실기기 스크린샷 다섯 차례 반복

- **"전·승·무" 세 열을 "승/무/패" 한 열로 접었다** — 승×3−패+적격파가 총점이라
  전(출전 수)은 승+무+패로 다시 셀 수 있어 따로 안 보여준다.
- **모드·상대 필터를 리스트 박스(드롭다운) 둘로, 한 줄에** — 처음엔 알약
  버튼 줄이었는데 사용자가 지정했다.
- **위(서버 랭킹)는 스크롤, 아래(내 랭킹)는 화면 바닥에 고정** — `.rk-top`이
  `flex:1；overflow-y:auto`로 스스로 스크롤하고 `.rk-mine`은 `flex:none`이라
  제 내용만큼만 차지한다. 금색 윗선으로 둘을 눈으로 가른다.
- **열 폭을 고정 rem → `flex-grow` 비율로** — 실기기에서 옆으로 스크롤이
  생기거나(고정폭이 넓을 때) 오른쪽에 빈 여백이 남는(줄여도 폭은 그대로일 때)
  두 문제를 다 겪고서 비율로 바꿨다. 표 헤더 글자도 처음엔 본문보다 작아서
  (`.rk-thead`가 `.rk-row`보다 나중에 와 특정도 동률에서 이겼다) 키웠다.
- **부대 랭킹의 "전투력" 열을 없앴다(한 차례 뒤집었다)** — 매칭용
  `battlePower()`는 회귀 계수라 "왜 이 숫자인가"를 설명할 수 없어, 처음엔
  `squadDisplayPower()`(등급 점수×레벨의 합, 계수 없음)를 새로 만들었다.
  그런데 행을 누르면 구성(등급·레벨·HP·MP·AT)이 이미 펼쳐지므로 요약 숫자가
  하나 더 필요 없다고 사용자가 뒤집어, 함수째로 제거했다.

### 3. 인물 서사(G1) 연결 — 218/260명, 코드 밖 자산을 파이프라인에 연결

장수 카드에 쓸 초상·자(字)·인물 소개가 필요해지면서, 작업계획에 미뤄 두었던
**G1**("인물 서사 260명 — 이미 자리(`OfficerData.story?`)가 뚫려 있다")을
자연스럽게 착수하게 됐다.

  언어 전부) 열로 이미 갈라 둔 훨씬 안전한 소스**라는 걸 발견하고 옮겼다.

### 4. 장수 카드 (pptx 53쪽) — 다섯 차례 사용자 지정

- 초상화는 전투 수묵화가 아니라 **"체스 게임에 들어갔을 때 기물로 쓰는
  이미지"**(`assets/Chars/` → 빌드된 `portraits/{id}.png`, 알파 있는 보드
  타일)여야 한다는 지정이 있어, `ui/art.ts`의 `setOfficerArt()`에
  `primary: 'battle' | 'portrait'` 매개변수를 추가했다(기본값은 그대로 전투
  수묵화 우선이라 다른 화면은 안 바뀐다).
- 레이아웃: 이름(자·등급)이 카드 중앙 상단 → 그 아래 **4:6** 두 단(왼쪽
  기물 그림 한 장이 `align-items: stretch` 기본 동작만으로 칸을 채움, 오른쪽
  다섯 줄) → 인물 열전.
- 다섯 줄 최종 순서(세 번 뒤집었다): **① 전적(승/무/패·적격파) → ② 삼능력
  (무력·지력·통솔) → ③ 고유기술(있으면 이름, 누르면 기존 `SkillModal` 재사용
  — 없으면 "고유 기술 없음") → ④ 레벨·HP·MP·AT(AT는 기존 `atRange()`로 "2-5"
  범위) → ⑤ 배운 책략(칩 나열, 없으면 "습득한 책략이 없음")**. **다섯 줄
  전부 이제 "없어도 줄째로 안 사라진다"** — 처음엔 고유기술·책략 둘 다
  없으면 숨겼는데, 마지막에 뒤집었다.
- 고유기술과 책략은 **서로 다른 자리에서 온다**: 고유기술은 장수 고정값이라
  클라이언트가 `skillById`로 직접 찾고(레벨 무관, 행에 안 실어도 됨), 책략은
  **계정마다 다르므로**(같은 장수라도 레벨업으로 무엇을 배웠는지가 갈린다)
  `OfficerRankRow.tactics`에 서버가 `tacticsOf()`로 미리 계산해 실어 보낸다.
- 각 스탯은 `<Stat k v>`로 DOM에 따로따로 얹었다(문자열로 안 잇는다) —
  "이후 항목마다 다른 자리·꾸밈을 넣으려면 미리 나눠 둔 쪽이 CSS만으로
  끝난다"는 사용자 요청.
- **실기기 버그 하나** — 고유기술 줄만 다른 세 줄보다 눈에 띄게 커 보였다.
  원인은 `button.ofcard-clickable { font: inherit; }`(요소+클래스, 특정도
  0-1-1)이 `.ofcard-bar`(클래스 하나, 0-1-0)의 `.74rem`을 밀어내고 부모의
  더 큰 글자 크기를 물려받은 것 — `font: inherit` 한 줄을 지워서 고쳤다.

## 검증

- `npm run typecheck`·`npm test` — 매 단계마다 확인. 최종 463개 중 460 통과,
  실패 3건은 전부 이 세션이 만들지 않은 것이다: `backdrop.test.ts`의 게임
  제목·언어 목록 기대값이 예전부터 낡았던 것 2건(2026-08-25 세션이 이미
  발견하고 남겨 둔 것), `data.test.ts`가 `[시각효과] 'B_specialstatus.png'` 2장이
  아무 데도 안 쓰인다고 잡는 것 1건 — `npm run extract`를 다시 돌리다
  드러났는데, `assets/SpecialStatus/`에 이미 들어와 있던 이미지가 매핑이
  안 된 것이라 이번 작업과 무관하다(손 안 댔다).
- **헤드리스 브라우저가 없는 환경**이라 dev 서버 스크린샷 확인은 못 했다 —
  대신 실제 `style.css` 규칙을 그대로 옮긴 정적 목업 두 개를 Artifact로
  publish해 레이아웃 역학(스크롤 분리·바닥 고정·열 비율)만 확인하는 용도로
  썼고, 실제 화면 검증은 사용자가 직접 dev 서버에서 스크린샷을 찍어 오가며
  진행했다.
- **세션 중 사고 하나** — `npm run extract`가 이전 코드 기준으로도 도는지
  확인하려고 `git stash`를 했다가 `stash pop`이 생성물 충돌로 실패해, 세션의
  모든 추적 파일 변경이 스택 안에 갇힌 순간이 있었다. `git checkout --`으로
  충돌난 생성물 두 개만 버리고 `stash pop`을 다시 걸어 전부 복구했다 —
  작업 손실은 없었지만, **생성물이 있는 저장소에서 `git stash`는 위험하다**는
  교훈을 남긴다(다음엔 별도 워크트리나 `git stash -- <경로>`로 좁힐 것).
