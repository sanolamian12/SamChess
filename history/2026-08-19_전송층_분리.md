### 계약 — 메서드 넷과 통 하나

```ts
interface BattleTransport {
  readonly initial: BattleState;          // 첫 프레임용. 동기로 들고 있다
  readonly humanSide: Side | null;
  open(inbox: (msg: ServerMsg) => void): void;   // 첫 통이 여기서 온다
  send(intent: Intent): void;                    // 결과는 inbox로 돌아온다
  ready(): void;                                 // 「나는 밀리지 않았다」 — 로컬만 듣는다
  close(): void;
}

interface ServerMsg {
  t: 'sync';
  state: Omit<BattleState, 'log'>;   // ★ 로그를 뺀다
  events: BattleEvent[];             // 받는 쪽이 제 로그에 이어 붙인다
  deadlineInMs: number | null;       // ★ 절대시각이 아니다
}
```

떼고 붙이는 자리는 각각 **하나**다 — `toWire()` · `applyWire()`.
갈래를 `sync` 하나로 둔 것은 일부러다(「거부됨」은 부를 자리가 생기는 세션이 만든다).

### `LocalTransport` — 같은 프로세스에서 판정하는 「서버」

흉내가 아니라 **정말 판정한다.** 온라인 서버가 할 일을 그대로 하되 주소가 여기일 뿐이라,
**서버가 꺼져 있어도 AI 대전이 돈다.**

| 언제 | 무엇을 하나 |
|---|---|
| `open()` | 첫 통(지금 상태 + 마감)을 보내고, 배치 단계면 **상대 대신 `ready`를 낸다**(예전에는 재생기가 했다) |
| `send(intent)` | `validate()` → `apply()`. 거부는 **우리 UI의 버그**라 던진다 |
| `ready()` | 상태를 보고 **무엇을 만들지 스스로 정한다** — `control`이면 상대의 `takeTurn`, `running`/`scout`이면 `advanceTime` |
| 마감 | 단계가 **바뀔 때만** 다시 잰다. 통마다 재면 배치 중 30초가 되살아난다 |

온라인과 다른 것은 둘뿐이다 — **즉시 답한다**(그래서 클릭→갱신이 한 프레임도 안 밀린다) ·
**기다려 준다**(`ready()`를 받아야 다음 것을 만든다. 진짜 서버는 안 기다린다).

### `Playback` — 네 갈래가 하나로

| | 예전 | 지금 |
|---|---|---|
| 내 의도 | `apply()` 즉시 | `transport.send()` |
| 상대의 수 | `takeTurn()` | 도착한다 |
| 시간 진행 | `advanceTime()` | 도착한다 |
| 마감 시각 | `Date.now() + 30초` | 통이 실어 온다 |

안쪽은 **네 조각**이다.

- **`pump()`** — 큐에서 꺼내는 유일한 자리. 도착 콜백은 **넣기만 한다.**
  연출 중(`holdMs > 0`)에는 안 꺼낸다.
- **`consume()`** — 통을 상태에 반영하고 `onChange`. **`displayTime`은 안 건드린다**
  (시계는 스스로 앞서지 않고 뒤쫓기만 한다). **연출이 걸렸으면 걸음 정하기를 미룬다**(`settlePending`).
- **`settle()`** — **권위 상태의 단계 하나가** 재생기의 걸음을 정한다. 「어느 함수를
  지나왔는가」로 갈리지 않으므로, 재접속으로 한복판 상태가 통째로 떨어져도 같은 답이 나온다.
- **`request()`** — 「다음 것을 달라」. 통이 하나 올 때까지 **한 번만** 말한다.

**공개 표면은 한 글자도 안 바뀌었다** — `state` · `phase` · `humanSide` · `displayTime` ·
`busy` · `remainingSec` · `submit` · `submitReady` · `beginBattle` · `hold` · `start` · `update`.
그래서 `BattleScene`(1,200줄)과 UI 여덟 모듈은 **손대지 않았다.** 바뀐 것은 생성자 하나다.

**시계를 스스로 읽지 않는다** — `now`를 주입받는다(기본 `Date.now`). `bandForHour`·
`syncGrain`과 같은 규약이고, 그래서 회귀가 배치 30초·정찰 30초를 **가짜 시계로** 돌린다.

### `rules/src/timing.ts` — 값만 있고 시계는 없다

먼저 굳혔다」와 같은 결이고, 2026-08-04에 7과 8의 순서를 뒤집었던 근거와도 같다.

## 3. 왜 Colyseus의 상태 동기화를 안 쓰기로 했나 ★

`@colyseus/schema`로 `BattleState`를 다시 적으면 **상태가 두 벌**이 된다 —
스택 선택의 1순위 기준(「룰 엔진을 서버와 클라가 같은 코드로 돌린다」·HANDOFF §3)을
정면으로 어긴다. Colyseus는 **방 · 전송 · 재접속**으로만 쓴다(넷 중 셋).

그리고 이 결정에 **덤이 하나 붙어 있었는데, 이번에 그게 우연이 아니었음이 드러났다** —
Schema는 데코레이터(`@type`)를 쓰고 **Node 타입 스트리핑은 데코레이터를 못 넘긴다.**
아래 §6-③에서 실제로 같은 벽에 부딪혔다.

## 4. 왜 로그를 떼어 보내나 — 실측 ★

전투 한 판을 끝까지 돌려 전선에 실릴 값을 쟀다.

| | 스냅샷(로그 제외) | 로그 포함 | 턴 |
|---|---:|---:|---:|
| 3v3 | **2,408 B** | 27,743 B | 48 |
| 5v5 | **3,705 B** | 55,089 B | 104 |

로그를 실으면 **한 통이 판 길이에 비례해 커진다.** 매 턴 보내므로 전선에서 `O(턴²)`다 —
`cloneState()`가 로그만 얕게 복사하는 그 지뢰(실측 90배)가 **네트워크에 다시 나타나는**
것이고, 화면에는 「후반이 좀 버벅이네」로만 보인다.

뗀 로그는 받는 쪽이 **이벤트를 이어 붙여** 되만든다. 그게 정확히 같다는 것은 엔진이
보장한다 — `commit()`이 `state.log.push(...events)` 하고 그 `events`를 그대로 돌려주므로
**`이전 로그 ++ events === 다음 로그`**다. 회귀가 이 등식을 한 판 전체에서 고정한다.

> **이벤트만 보내고 받는 쪽이 상태를 재구성하는 길은 안 골랐다.** 이벤트에서 상태를
> 만드는 리듀서가 없고, 만들면 그게 `apply()`의 **두 번째 구현**이다. 스냅샷을 보내면
> 어긋남이 구조적으로 불가능하고, **재접속이 덤으로 풀린다** — 돌아온 사람에게는 지금
> 스냅샷 한 통이면 된다(이벤트만 보내는 설계였다면 로그 전체를 되보내야 했다).

## 5. 이음매가 왜 하나여야 했나 — 갈래가 넷이었다

`Playback`은 **네 자리**에서 직접 상태를 만들고 있었고, 넷 다 온라인에서
「무언가가 도착한다」로 바뀐다.

| | 예전 | 온라인 |
|---|---|---|
| 내 의도 | `apply()` 즉시 | 보내고 기다린다 |
| 상대 | `takeTurn()` (AI) | 서버가 보내 준다 |
| 시간 진행 | `advanceTime()` 즉시 | 서버가 보내 준다 |
| 마감 시각 | `Date.now() + 30초` | 서버가 준다 |

각각 갈아 끼우면 갈래가 여덟이 된다. 하나로 모으니 **「바뀌는 것은 상대가 사람인지뿐」
(§5-32)이 화면 문구가 아니라 코드에서 성립한다.**

계약은 메서드 둘이다 — `send(intent)`와 `ready()`. **`ready()`는 로컬만 듣는다**:
뜻이 「진행시켜 달라」가 아니라 **「나는 밀리지 않았다」**이고, 서버는 어차피 기다려
주지 않는다. 재생기는 저편이 누구인지 모른 채 같은 말을 한다.

**마감은 절대시각이 아니라 「남은 ms」로 싣는다** — 서버와 사람의 시계는 몇 초씩
어긋나 있어서, 절대시각을 그대로 보내면 빠른 시계는 배치 시간을 잃고 느린 시계는 이미
지난 마감을 아직 남았다고 적는다. 받는 쪽이 제 시계로 `지금 + 남은 ms`를 만든다.

## 6. 밟은 지뢰 다섯 ★

### ① 「도는 적이 없는 검사」를 또 만들었다 — 이번엔 **내가 만든 검사**였다 ★

`pump()`에 「연출이 도는 동안에는 큐를 안 꺼낸다」 잠금을 두고, 회귀도 넣고, 통과를 봤다.
그런데 **그 줄을 지우고 돌려 보니 회귀가 전부 통과했다.**

이유는 `LocalTransport`가 **청해야 답하기 때문**이다 — 통은 `ready()`를 부를 때만 오고,
연출 중에는 `update()`가 일찍 돌아가 청하지 않는다. 그래서 **큐가 늘 비어 있고**
잠금이 한 번도 시험되지 않는다. 내가 검사한 것은 잠금이 아니라 `update()`의 조기 반환이었다.

F가 밟은 「온라인이 늘 빈손이라 거절 검사가 실행조차 안 됐다」(§5-52)와 **정확히 같은
함정**인데, 이번에는 그 교훈을 알고 있으면서도 **새 코드에서 다시 만들었다.**

고친 방법도 그때와 같다 — **그 상태에 도달할 통로를 검사와 함께 만든다.**
`ScriptedTransport`(회귀 안에만 있는 판정 주체)가 **묻지도 않고 한 판을 통째로 밀어
넣는다.** 그게 곧 진짜 서버의 모양이고, H2의 `OnlineTransport`가 이 자리를 대신한다.

> **교훈: 「이 검사는 무엇을 깨면 실패하나」를 코드로 확인하기 전까지는 통과가 통과가
> 아니다.** 그리고 흉내 통로는 `?match=online` 같은 **개발용 통로**일 필요가 없다 —
> 회귀 안의 가짜 구현이면 화면을 안 더럽히고 낡지도 않는다.

### ② 연출이 도는 동안 단계가 미리 넘어갔다 — **스모크만 잡았다** ★

`smoke:ui`가 이렇게 말했다.

```
✗ WT 게이지가 시간이 흘러도 줄지 않는다 (151.0 → 151.0) — displayTime 보정이 빠졌다
```

새 `consume()`이 통을 받자마자 걸음을 정해 버려서, **때리는 연출이 도는 2.6초 동안
단계가 벌써 `advancing`**이었다. 화면은 아무것도 안 흐르는데 「시간이 흐르는 중」이라고
말하고 있었던 것이다. 옛 `stepOrHold()`는 「연출이 걸려 있으면 그것이 끝난 뒤에
진행한다」였는데, 그 성질을 옮겨 적으면서 **진행만 미루고 「걸음 정하기」는 안 미뤘다.**

`phase`는 화면이 읽는 값이라 거짓말을 하면 안 된다. `settlePending`을 두어 연출이 끝난
뒤에 정하게 고쳤고, **브라우저를 띄워야만 보이던 것을 단위 회귀로 내렸다**
(「연출이 도는 중에 단계가 바뀌었다」).

> **교훈: 상태 기계를 옮겨 적을 때 옮겨야 하는 것은 「무엇을 하는가」만이 아니라
> 「언제 하는가」다.** 그리고 화면 스모크는 단위 회귀를 보완하는 게 아니라
> **다른 종류의 버그**를 잡는다 — 이번에도 그랬다.

### ③ 타입 스트리핑이 파라미터 프로퍼티를 못 받는다 — 데코레이터와 **같은 부류**다 ★

회귀의 가짜 판정 주체를 `constructor(readonly initial: BattleState, …)`로 적었더니:

```
SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]:
TypeScript parameter property is not supported in strip-only mode
```

**타입만 지워서 되는 문법이 아니면 안 된다** — 파라미터 프로퍼티는 대입문을 만들어
내야 하고, 데코레이터·`enum`·`namespace`도 같다. §3에서 `@colyseus/schema`를 피한 것이
**설계 취향이 아니라 이 저장소의 물리적 제약**이었음이 여기서 실증됐다.

### ④ 임계값은 「정상값이 어디까지 올라가는지」를 재고 정한다

스냅샷 크기 회귀를 처음에 「뒤쪽 ≤ 앞쪽」으로 적었다가 5v5에서 깨졌다(3,401 B → 3,823 B).
스냅샷도 **조금은 는다** — 상태이상과 WT 보정이 유닛에 쌓이기 때문이다. 시드 40개로 재니
**최대/첫 = 3v3 1.54배 · 5v5 1.33배**였고, 로그를 실은 대조군은 **21~23배**였다.
사이가 열 배 넘게 벌어져 있어 **2배**로 그었다.

액션 띠의 `BAND_FILL`에서 밟은 것과 같은 것이고, **대조군을 함께 잰 것**이 이번에
더해진 부분이다 — 없으면 「원래 안 크는 것을 안 큰다고 확인」하는 검사가 된다.

### ⑤ 재진입 잠금은 검사로 안 잡힌다 — **과장하지 않고 사실을 적었다**

`pump()`의 잠금을 지우고 돌려도 회귀가 전부 통과한다. 잠금이 없으면
`소화 → ready() → 도착 → 소화`가 **재귀로 파고들 뿐 꺼내는 차례는 같기** 때문이다.
잠금이 막는 것은 **깊이**(스택이 판의 턴 수만큼 쌓인다)이지 순서가 아니다.

문서에는 「재진입 잠금이 이 함수의 요점이다」라고 적어 뒀었는데, **검사가 뒷받침하지
못하는 주장**이라 사실대로 고쳤다. 도는 적이 없는 검사를 하나 더 만드는 것보다,
**무엇이 검사로 안 잡히는지를 적어 두는 편**이 낫다고 봤다.

## 7. 검사가 실패하는 상태를 다섯 번 만들어 봤다

「방어를 넣었으면 발동하는 입력을, 검사를 넣었으면 실패하는 상태를」(B·E·F)에 따라,
실제로 코드를 깨고 회귀가 무엇을 잡는지 확인했다.

| 무엇을 깼나 | 회귀가 뭐라고 했나 |
|---|---|
| `toWire`가 로그를 안 뗀다 | `스냅샷에 로그가 딸려 왔다` · `스냅샷이 판 길이를 따라 커진다` |
| `applyWire`가 이어 붙이지 않고 갈아 끼운다 | `로그가 다르다` · `화면이 본 이벤트가 곧 로그다` 등 3건 |
| 마감을 통마다 새로 잰다 | `배치 의도가 마감을 되살렸다 — 통마다 새로 재고 있다` |
| 연출 중에도 큐를 꺼낸다 | **처음엔 안 잡혔다** → `ScriptedTransport`를 만든 뒤 `연출 중에 N통을 한꺼번에 꺼냈다` |
| `consume`이 걸음을 안 미룬다 | `연출이 도는 중에 단계가 바뀌었다 — 화면이 「흐르는 중」이라고 거짓말한다` |

`pump()`의 재진입 잠금은 **다섯 중 유일하게 깨도 안 잡히는 것**이었고, 그래서 §6-⑤로
적었다.

## 9. 기획자와 정한 것 (2026-08-19)

| 항목 | 결정 |
|---|---|
| **이번 세션의 범위** | **H1만** — 전송 층. 서버 코드 0줄 |
| **로그인 순서** | **Colyseus가 먼저.** 전투 프로토콜은 「누구인가」에 안 걸린다 — 걸리는 것은 재접속용 안정된 키 하나뿐이고 `deviceId`로 충분하다. 다만 **치팅은 로그인으로 안 막힌다** — 막히는 것은 계정이 서버로 갈 때(H3)다 |
| **서버 배포** | **로컬 개발만.** `ws://localhost`. 배포는 도메인·TLS·프로세스 관리가 딸려 오는 별개의 일이라, 그때 **코드가 아니라 설정**만 바뀌게 설계한다 |
| **참가비 확정 시점 (온라인)** | **방이 열린 순간.** [전투준비] 뒤에 「상대를 기다리는 중」이 한 상태 더 붙고, 상대가 거절하면 **한 톨도 안 나간다.** 45쪽에 없던 상태이고 오프라인은 그 순간이 즉시라 화면이 안 바뀐다 |
| **이탈 처리** | **한쪽만** 사라졌으면 배치 중이면 사라진 쪽만 참가비를 잃고(남은 쪽은 환불·전적 없음), 정찰 이후면 **항복과 같다**(승리·패배 보상과 전적). **양쪽 다** 사라졌으면 **단계와 무관하게 양쪽 다 환불**(전적·보상 없음) |

**이탈 규칙이 왜 이 모양인가** — 세션 마지막에 물어 답을 받았고, 근거가 처음 적은
것보다 한 겹 깊었다.

**① 사라진 쪽에게 환불하지 않는 진짜 이유는 「끊는 것이 거절보다 싸지면 안 된다」다 ★**

처음에 나는 이 비대칭을 **「버티고 있던 쪽을 지킨다」**(§5-15 거절의 취지)로만 적었다.
그것도 맞지만 **핵심이 아니었다.** 기획자가 짚은 것은 이쪽이다 —

```
매칭 화면에서 전투력 차이를 보고 상대를 물리는 정식 통로 = 「다시 찾기」 = 군량 −1
그런데 참가비를 낸 뒤 접속을 끊어서 돌려받을 수 있다면
                        = 같은 회피를 군량 0으로 = 거절 패널티가 통째로 무력
```

지금은 끊으면 참가비(3v3 **3** · 5v5 **5**)를 잃으므로 **언제나 거절이 더 싸다.**
「지켜 준다」로만 적어 두면 언젠가 **「사라진 쪽도 돌려주는 게 인정 아닌가」**로
되돌려지는데, 그러면 거절 −1이 조용히 죽는다. §5-65로 따로 적은 이유다.

> **교훈: 패널티에는 「무엇을 지키나」와 「무엇을 못 하게 하나」가 따로 있다.**
> 앞만 적으면 뒤가 사라져도 문서가 아무 말을 안 한다.

**② 양쪽이 다 사라지면 지킬 사람이 없다 → 양쪽 다 환불**

단계와 무관하다(배치든 전투 중이든). 대개 **시스템 장애**이고, 아니라면 둘이
**싸우지 않기로 합의한 것**으로 볼 수 있다 — 어느 쪽이든 **기다리느라 불편을 겪은
사람이 없다.** ①의 회피 유인도 서지 않는다: 짜고 둘이 끊어도 **얻는 것이 없어**
(보상도 전적도 안 남는다) 대전을 안 한 것과 같아진다.

**판정 시점도 같은 원리로 갈린다** — 먼저 끊긴 쪽의 유예가 끝나는 순간 **상대가 붙어
있으면 곧바로** 한쪽-이탈로 끝낸다(기다리는 사람을 더 기다리게 하지 않는다). 그때
상대도 끊겨 있으면 **재촉할 사람이 없으므로** 둘의 유예가 모두 끝날 때까지 둔다.

**③ 규칙이 기존 자리에 그대로 얹힌다**

- **갈림길이 엔진에 이미 있는 값이다** — `state.ready[side]`이고 `deploy → scout` 전이가
  정확히 그 순간이다. 「어디까지가 본 게임인가」를 두 군데서 적을 일이 없다.
- **항복 갈래에 새 규칙이 없다** — 서버가 사라진 쪽 대신 `{ t: 'surrender' }`를 적용하면
  `outcome: 'surrender'`가 그대로 나오고 §6.4 보상표가 그대로 걸린다. 룰 엔진도 보상
  층도 안 건드린다.
- **배치 중 이탈에 승리는 주지 않는다** — 주면 「상대를 끊게 만드는 것」이 이득이 되고,
  성립한 적 없는 전투의 전적이 남는다. 환불까지가 지킬 몫이다.

**③ 「끊긴 것」과 「가만히 있는 것」은 다르다 — 그 자리도 같은 세션에서 닫았다 ★**

붙어 있는데 아무것도 안 두면 이탈 규칙이 안 걸린다. 배치·정찰은 마감이 있어 서버가
넘기므로 **멈추는 곳은 제어 단계 하나**이고, 거기서는 절대시간이 멈춰 **`time 6000`
무승부 상한에 영원히 못 닿는다** — King이 멀면 잡을 수도 없다.

| | 무엇이 끝내나 | 결말 |
|---|---|---|
| **한쪽만 손을 놓았다** | 상대가 **`[차례 넘기기]`를 3번** 누른다 | 누른 쪽 **승리** (항복과 같은 보상·전적) |
| **양쪽 다 손을 놓았다** | **방 유휴 상한 2분** | **양쪽 환불 · 전적도 보상도 없다** |

내가 낸 안은 「N 동안 의도가 없으면 서버가 대신 항복시킨다」였는데, 기획자가
**이미 있는 단추에 횟수를 붙이는** 쪽으로 바꿨다. 이게 더 좋은 이유가 셋이다.

- **끝내는 것이 사람의 손이다.** 서버가 대신 항복시키면 「내가 안 했는데 졌다」가 남는데,
  3번 규칙은 **상대가 세 번 눌러서** 이긴다. 이탈(연결이 끊긴 것)은 사람이 확인할 수
  없어 서버가 판정하지만, 이쪽은 확인할 사람이 화면 앞에 있다.
- **값이 이미 비싸다.** 한 번 누르려면 상대가 **20초를 통째로 흘려보내야** 하므로
  3번은 **최소 60초의 무응답**이다. 별도의 「N」을 새로 정할 필요가 없다.
- **두 갈래가 겹치지 않는다.** 누르는 사람이 있으면 방은 유휴가 아니고, 아무도 안
  누르면 3번에 닿을 일이 없다 — 유휴 상한과 3번 규칙이 서로의 사각을 정확히 덮는다.

**내가 판단해 덧붙인 넷** (다르면 GDD §3.3 · §3.9만 고치면 된다).

| | 무엇 | 왜 |
|---|---|---|
| ① | **횟수는 누적** — 한 판 동안 세고 상대가 정신을 차려도 안 되돌린다 | 「먼저 3번」의 곧이곧대로의 읽기이고, 되돌리면 **20초씩 두 번 끌고 한 번 두는** 것이 공짜가 된다 |
| ② | **결말은 `outcome: 'surrender'`** | 사실상 포기이고, **이탈 처리와 같은 장치를 세 번째로 쓰는 것**이라 엔진에 새 결말이 안 는다 |
| ③ | **횟수는 화면에 「(2/3)」로 보인다** | 누르면 승리에 가까워지는 단추가 아무 말도 안 하면, 「눌리는데 아무 일도 없다」(§5-20)의 **반대쪽 함정**이 된다 |
| ④ | **유휴 상한 > 재접속 유예** | 끊긴 사람은 **유휴한 사람이기도 하다** — 두 규칙이 겹치는 유일한 자리이고, 상한이 짧으면 **돌아오는 중인 사람이 먼저 잘린다** |

**H1에서 구현하지 않았다.** §5-67은 이 트랙에서 처음으로 **룰 엔진을 건드리는** 규칙인데
(`BattleState`에 진영별 넘기기 횟수가 늘고 `validate`/승패 판정이 그것을 본다),
발동 조건인 **제어 20초 초과**가 `controlStartedAtMs`를 요구하고 **그 값은 서버가
주입한다.** 서버 없이 만들면 §5-52의 「도달할 수 없는 갈래」가 하나 더 생긴다 —
**서버와 같은 세션에서** 만든다. 저장 형식은 그대로다(`BattleState`는 런타임 상태다).

**④ 재접속 유예는 3번 규칙에서 유도된다 — 그리고 파생 규칙이 하나 딸려 나왔다 ★**

기획자의 유도: `[차례 넘기기]` 3번을 누르는 데 **1분**이 드니, 유예가 1분이면 돌아온
사람이 **3번에 닿기 전에** 도착한다. 제 차례에 1초라도 두면 그 턴은 세어지지 않으므로
**돌아오기만 하면 지지 않는다.**

덧붙이면 **60초는 하한**이다 — 3번은 「내 제어 창 세 번」이라 순수 대기가 `20 × 3`이고,
그 **사이에 상대의 턴들이 낀다.** 그래서 유예 1분은 언제나 3번보다 먼저 끝난다.

시간 셋이 맞물린다. **매칭 대기 상한과 같은 수인 것이 우연이 아니다** — 둘 다
「상대가 올 때까지 기다리는 시간」으로 **같은 것을 재고 있다.**

| | 값 | 관계 |
|---|---:|---|
| 재접속 유예 | **60초** | 3번 규칙의 하한과 같다 |
| 매칭 대기 상한 (`waiting`) | 60초 | 같은 기다림을 잰다 |
| 방 유휴 상한 | 120초 | 유예보다 길어야 한다 |

**그런데 숫자를 넣어 보니 배치 단계에서 어긋났다.**

```
배치 마감 30초  → 서버가 자동으로 [준비완료]를 건다
재접속 유예 60초
  → 배치 +0초에 끊기면 +30초에 ready가 서고, +60초에 유예가 끝날 때는 이미 정찰 이후
  → 「배치 중 이탈」이 아니라 「항복」으로 판정된다  ← 표의 첫 줄이 영원히 안 돈다
```

**§5-52의 「도달할 수 없는 갈래」가 이번엔 규칙 쪽에 생기는 자리다.** 오늘 코드에서 두
번 밟은 것과 같은 모양이 **사양에서** 나왔다. 그래서 파생 규칙을 함께 세웠다 —
**끊긴 사람에게는 자동 `[준비완료]`를 걸지 않는다.** 배치 마감의 자동 준비는 **자리에
있는데 시간이 다 된** 사람을 위한 편의이지, 없는 사람을 대신해 주는 장치가 아니다.
끊긴 쪽은 `deploy`/`waiting`에 그대로 두고 유예가 끝날 때 판정한다 — 그래서
`waiting` 상한과 유예가 같은 수인 것이 다시 한 번 맞아떨어진다.

> **교훈: 상수를 정하고 나면 그 값을 다른 상수 옆에 놓고 한 번 굴려 본다.**
> 「1분」 자체는 옳았는데, 옆에 있던 「배치 30초 자동 준비」와 만나자 **앞서 정한 표의
> 한 줄이 죽었다.** 규칙은 혼자 틀리지 않고 **서로 만나서** 틀린다.

## 10. 세션을 마친 뒤에 결정이 넷 더 붙었다 ★

H1 구현이 끝난 **뒤에** 기획자와 오간 물음 넷(§5-64~68)이 전부 H2의 것이었다.
「새 세션에서 물어야 하지 않나」라는 물음이 나왔고, **지금 답하는 쪽이 맞았다.**

- **기획 결정은 구현이 아니다.** H2가 할 일은 정해진 값을 코드로 옮기는 것이라,
  미룬다고 H2가 더 잘 결정하지 못한다 — **막힌 채로 시작할 뿐이다.**
- **세션 사이의 운반체는 문서다.** 지금 답하면 GDD 한 표와 §5 한 줄로 남고, 새 세션은
  읽고 곧장 짠다. 미루면 다음 세션이 **맥락을 다시 세운 뒤에야** 같은 질문을 한다.
- **그리고 실제로 값이 있었다.** §5-64를 물어서 §5-65(「끊는 것이 거절보다 싸지면
  안 된다」)가 나왔는데, 그건 **내가 근거를 얕게 적어 둔 것을 기획자가 짚어 준 것**이다.
  새 세션이었다면 내 얕은 문장만 읽고 그대로 굳혔을 것이다.

> **교훈: 「그 세션에서 물을 것」으로 미뤄 둔 기획 물음은, 답할 수 있을 때 답해 둔다.**
> 미뤄야 하는 것은 「이걸 어떻게 짤까」다 — 그건 코드를 열어야 판단이 서고,
> 미리 정해 두면 도리어 낡는다.
