# 2026-08-20 — 계정·로그인 H3a: 설계안과 `server-api` 첫 조각

H2b(대기열과 거절)가 끝난 뒤 이어진 세션. H3(계정·로그인·계정 권위) 전체를 설계안으로
정리하고, 그중 **서버 쪽 절반**(`server-api` 스켈레톤 — Supabase Auth 검증·Postgres
`profiles` 테이블·`GET/PUT /profile`)을 실제로 만들어 진짜 Supabase 프로젝트로 검증했다.
클라이언트(로그인 UI·`storage.ts` 전환·`playerId`=uid)는 **다음 세션**으로 남겼다.

## 1. 왜 H3를 H3a·H3b로 쪼갰나

H1을 H2와 가른 것(§5-53), H2를 H2a·H2b로 가른 것(§5-70)과 같은 이유다 — H3의 범위가
너무 넓어서 한 세션에 다 넣으면 **어긋났을 때 "인증 문제인가 정산 문제인가 AI 이관
문제인가"를 가릴 수 없다.**

```
H3a  인증(Supabase, 익명→이메일 승격) · server-api 신설 · Postgres · 로컬→서버 1회 이전 ·
     playerId=uid · ?seat=N 제거
H3b  참가비·거절 군량 서버 재검증 · RoomClose.refund 재검증 · AI 대전 서버 이관(§5-61)
```

**H3a가 끝나도 "치팅이 막힌다"는 아니다** — §5-61이 이미 그렇게 적어 뒀다. H3b에서야
막힌다. 이번 세션은 H3a의 **절반**(server-api 스켈레톤)까지다.

## 2. 결정 — 왜 그렇게 정했나

### 인증: Supabase Auth (Firebase 아님)

첫 설계안은 Firebase Auth + 카카오였다. 두 가지가 뒤집혔다.

1. **카카오를 뺀다.** 글로벌 배포가 목표인데 "한국 사람밖에 안 쓰는" 로그인 수단을
   기본으로 넣을 이유가 없다는 기획자 판단 — **이메일 인증으로 통일한다.**
2. **Firebase 대신 Supabase.** 카카오가 빠지면서 Firebase의 유일한 우위(성숙한 익명
   인증 → 승격 흐름)의 값어치가 줄었고, 대신 **DB로 이미 Postgres를 고른 상태**라
   Supabase Auth(GoTrue)가 **같은 Postgres 안에** 산다는 게 결정적이었다 — Firebase는
   신원(Firebase)과 계정 데이터(우리 Postgres)가 **서로 다른 두 시스템**으로 갈려
   "이 uid가 실제로 존재하는가"를 매번 신뢰해야 하는 경계가 하나 더 생긴다. Supabase는
   `profiles.uid`가 `auth.users(id)`를 FK로 직접 참조해 그 경계가 없다.

### `server-api`는 Colyseus와 완전히 분리된 프로세스

§5-54("Colyseus는 방·전송·재접속만 쓴다")를 안 깨려면 계정 CRUD를 `BattleRoom`/
`QueueRoom`에 얹으면 안 된다. `packages/server-api`(Fastify)를 새로 세웠다 —
`packages/server`를 한 글자도 안 건드렸다.

### `profiles` 테이블 — JSONB 한 행, **matches 분리는 미룬다**

설계안 초안에는 "이력(`matches[]`)은 별도 테이블로 뗀다"가 있었다(행 크기가 자란다는
이유). 구현하며 뒤집었다 — **지금 당장 뗄 이유가 없다.** `localStorage.ts`가 이미
`JSON.stringify(profile)` 한 덩어리로 저장하고 있고, `migrateProfile()`이 그 모양
위에서 "형식이 바뀌어도 채워 넣는다"를 이미 보장한다. 지금 떼면 `@samchess/meta`에
없는 "쪼개는 규약"을 새로 만들어야 하는데, 그건 행 크기가 **실제로** 문제가 될 때
(스냅샷/로그 분리 때 실측하고 결정한 것과 같은 결, §5-55) 하는 게 맞다 — 지금 하면
추측성 최적화다(CLAUDE.md "필요한 것 이상으로 설계하지 않는다").

### `profiles.uid → auth.users(id) on delete cascade`

계정을 지우면 프로필도 같이 지워져야 하는데, 정리하는 자리를 둘(서버 API 삭제 로직 +
Auth 삭제 로직)로 만들지 않고 **FK cascade 하나**로 모았다. 스모크가 실제로 "Auth
계정을 지우면 `profiles` 행도 사라지는가"까지 확인한다.

### 토큰 검증은 `/auth/v1/user` 호출로 — JWKS 로컬 검증은 나중

Supabase가 발급한 JWT를 로컬에서 서명 검증하지 않고, 매 요청 `${SUPABASE_URL}/auth/v1/user`를
그대로 호출해 유효성을 확인한다. 왕복이 붙지만 이 저장소는 최소 의존성을 우선한다
(CLAUDE.md) — 트래픽이 커지면 그때 JWKS 검증으로 바꾼다. **지금 바꾸는 건 이른
최적화다**(D의 "회귀는 관측 범위 밖에서 틀린다"와 같은 결 — 지금은 트래픽이 0이라
어느 쪽이 실제로 필요한지 잴 수도 없다).

### `PUT /profile`은 저장과 "가져오기"를 가르지 않는다

로그인 뒤 "서버에 없으면 로컬 걸 한 번 올린다"(1회 이전)와 평소 저장이 **같은
엔드포인트**(upsert)다. 둘을 가르면 클라이언트가 "이번이 처음인가"를 스스로 판단해야
하는데, 서버가 upsert면 그 판단이 필요 없다 — F의 "판정을 화면이 다시 하지 않는다"와
같은 결이다.

## 3. 밟은 지뢰 — Supabase 자격 증명 확인

`.env` 채우는 과정에서 세 번 넘어졌다. **전부 "설정 화면을 그대로 따라 했는데
안 되는" 종류**라 다음에 같은 프로젝트를 또 세팅할 사람(자신 포함)을 위해 남긴다.

1. **Direct connection은 IPv6 전용이다.** Supabase가 최근 만든 프로젝트의
   `db.<ref>.supabase.co`는 기본이 **IPv6 전용**이다(IPv4는 유료 애드온). 이 개발
   환경은 IPv6 아웃바운드 경로가 없어 `ENOTFOUND`로 실패했다 — DNS 자체는 정상
   응답했는데(`2406:da14:...`) 라우팅이 안 됐다. **해결**: Direct connection 대신
   **Transaction Pooler**(`aws-0-<리전>.pooler.supabase.com:6543`) 문자열을 쓴다 —
   IPv4로 붙고, 애초에 여러 연결을 짧게 여닫는 API 서버 쓰임에 더 맞는 방식이다.
   → **교훈: 클라우드 서비스의 "복사해서 붙여넣기" 값도 네트워크 환경에 따라
   조용히 막힐 수 있다.** 에러 메시지(`ENOTFOUND`)만 보면 "URL이 틀렸나" 싶지만
   DNS는 정상이었다 — `nslookup`으로 실제로 어떤 주소가 나오는지 먼저 봐야 했다.

2. **비밀번호 자리표시자 `[YOUR-PASSWORD]`의 대괄호까지 비밀번호로 넣었다.** 원래
   문자열이 `postgresql://...:[YOUR-PASSWORD]@...`인데, `YOUR-PASSWORD`라는 글자만
   실제 비밀번호로 바꾸고 감싸고 있던 `[`·`]`는 그대로 둔 채였다 — Postgres는 이걸
   완전히 다른 비밀번호로 본다. 비밀번호를 새 걸로 리셋해서 넣어도 계속 실패했던
   이유가 이거였다. 형식 검사(URL 파싱·문자 클래스)로는 안 잡히고, **비밀번호를
   URL 디코드한 뒤 첫·끝 문자 코드를 직접 찍어 봐서야** `[`(91)·`]`(93)가 보였다.
   → **교훈: 플레이스홀더 문법(`[...]`, `<...>`, `{...}`)이 있는 템플릿 값을
   사람이 손으로 채울 때는, 감싸는 기호까지 지웠는지 형식 검사가 아니라 값 자체를
   구조적으로 뜯어봐야 잡힌다.**

3. **Secret key가 두 형식으로 섞여 있었다.** 처음 받은 건 대시보드의 "Legacy API
   keys" 탭에서 온 **레거시 JWT**(`eyJ...`, 221자)였고, `role: service_role`로
   디코드돼 유효하긴 했지만 최신 값이 아니었다. 다시 받은 건 새 `sb_secret_` 접두사
   형식(41자)이었다 — **둘 다 지금은 유효하다**, 형식만 다르다. 값을 화면에 다시
   찍지 않고(비밀이니까) JWT면 payload의 `role`·`ref`만 디코드해 확인하고, 새 형식은
   접두사만 확인하고, **최종적으로는 둘 다 실제 Admin API를 호출해 살아있는지**
   확인했다 — 형식 검사만으로는 "맞는 키인지"와 "유효한 키인지"를 가를 수 없다.

## 4. 만든 것

```
packages/server-api/
  package.json    fastify · pg · @samchess/meta
  tsconfig.json
  sql/schema.sql  profiles(uid PK → auth.users FK cascade, data jsonb, updated_at)
  src/db.ts       pg.Pool — SUPABASE_DB_URL(Transaction Pooler) 하나만 읽는다
  src/auth.ts     토큰 검증 — /auth/v1/user 호출
  src/profileStore.ts  getProfile · saveProfile(upsert) · deleteProfile — migrateProfile()을 그대로 씀
  src/routes.ts   GET/PUT /profile
  src/main.ts     부팅 — Colyseus(packages/server)와 별도 프로세스

tools/
  migrate_db.ts   npm run db:migrate — schema.sql 적용(멱등)
  smoke_account.ts  npm run smoke:account — 진짜 Supabase로 로그인→저장→읽기→cascade 삭제까지
```

`npm run smoke:account`는 Admin API로 테스트 계정을 만들고, 비밀번호 로그인으로 진짜
액세스 토큰을 받아, 제 안에서 띄운 Fastify 인스턴스에 그 토큰으로 요청을 보낸다 —
`smoke:online`이 진짜 소켓을 지나야 Colyseus 버전 짝을 잡는 것과 같은 이유로, 여기서도
가짜 토큰으로는 `auth.ts`의 검증 경로 자체가 시험되지 않는다. 끝나면 테스트 계정을
지우고 `profiles` 행도 cascade로 함께 사라지는지까지 확인한 뒤 자원을 정리한다.

**확인 — 전부 실제 Supabase 프로젝트에 대고 돌렸다.**

```
npm run typecheck   →  exit 0 (packages/server-api 포함)
npm test             →  425/425 그대로 (server-api는 아직 node --test 단위 테스트가 없다 — 전부 스모크로 검증)
npm run smoke:account →  통과 — 로그인 · 404 · 저장 · 왕복 동일성 · upsert · 무토큰 401 · cascade 삭제
```

## 5. 다음 세션 — H3a 나머지

- 클라이언트에 Supabase 로그인(이메일) 붙이기 — 익명 시작 → 이메일 인증 시 승격
- `client/src/meta/storage.ts`를 `server-api` 호출로 전환 — **동기 → 비동기**라
  `App.tsx`를 비롯해 부르는 자리가 다 영향받는다. 로컬은 "서버 접근 실패 시 마지막
  스냅샷을 보여주되 쓰기는 막는" 캐시로 격하한다.
- 로그인 첫 진입 시 "서버에 없으면 로컬 걸 한 번 올린다" 1회 이전 — `PUT /profile`이
  upsert라 별도 엔드포인트는 필요 없다(위 §2).
- `Enlist.playerId`를 `deviceId` 문자열에서 Supabase uid로 — `BattleRoom`/`QueueRoom`의
  `onAuth`(정적 메서드)에서 액세스 토큰을 검증한다. **계정 데이터는 안 읽는다**,
  신원 확인만 해서 §5-54를 안 깬다.
- `?seat=N` 개발용 통로 제거(§5-78이 예고한 자리) — 로그인이 붙으면 진짜 계정 둘로
  탭 둘을 가른다.

H3b(참가비·거절 군량 서버 재검증 · AI 대전 서버 이관)는 그 뒤다.
