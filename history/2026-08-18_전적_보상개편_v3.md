## 1. 들어갈 때의 계획과 나올 때의 결과가 달랐다

계획서에 적혀 있던 C1은 이랬다.

```
전적 — OfficerInstance.record 를 기물별 × 모드별로. 온라인만 카운트
보상 — won: boolean → result. AI 대전은 승리 시 군량만
완료 조건 — … AI 대전이 전적·카드·재료를 하나도 안 건드림
```

나올 때는 **그 두 줄이 다 뒤집혀 있다.** 기획자가 설계안을 보고 되돌린 것이라 이 문서의
절반은 그 이야기다.

## 2. 왜 AI와 온라인을 같게 했나 ★

45쪽 원문은 「AI 대전 — 보상: 군량 / 전적 기록을 하지 않습니다」이고, 2026-08-04에도
「AI 대전은 군량만, 카드는 없다 — 봇 파밍 방지」로 확정했었다. 근거가 튼튼해 보였다.

기획자가 같은 자리에서 **문을 하나로 합치겠다**고 했다.

```
[출정하기] → 최대 30초 온라인 상대 탐색 → 못 찾으면 AI 상대를 전투력에 맞춰 생성
```

이 한 줄이 옛 규칙의 **전제**를 무너뜨린다. 「AI는 보상이 적다」가 성립하려면
**플레이어가 AI를 고를 수 있어야** 한다. 문이 하나면 상대가 사람인지 AI인지는 고르는
것이 아니라 **그때 접속한 사람이 있었는가**일 뿐이다. 보상이 갈리면 보상을 정하는 것이
실력도 선택도 아닌 **시간대**가 된다.

전적도 같은 이유로 뒤집혔다. 「AI는 안 센다」로 두면 한산한 시간대에 논 판은 전적에
아무 흔적도 남기지 않는다. 대신 **`[AI]` 라벨과 필터**(전체 / 온라인 / AI)를 두어
「사람과의 전적만 보기」를 살렸다 — 세지 않는 것과 갈라 보는 것은 다르다.

> **남은 위험은 정직하게 적어 둔다.** 사람이 적은 시간대에는 상대가 늘 AI이고, AI는
> 사람보다 약하다 — 몰아서 붙이면 카드를 더 쉽게 모을 수 있다. 지금은 확정대로 완전히
> 같게 두되, 막아야 할 때 손댈 자리를 **한 곳**(`CARD_GRADES`)으로 모아 뒀다.
> 저장 형식은 안 건드리고 바꿀 수 있다.

## 3. 전적을 「교차로 한 번만」 센 이유

40쪽 목업은 같은 숫자를 **세 가지 모양**으로 요구한다.

```
기물      출전 수  승리  적격파      ← 여섯 줄
총 출전 : XX  승리 : XX  적격파 : xx
3v3     : XX  …                     ← 모드별 두 줄
5v5     : XX  …
```

셋을 각각 세면 세 벌의 카운터가 생기고, **어긋나도 화면은 아무 말도 하지 않는다.**
그래서 칸을 `{상대}/{모드}/{기물}`로 **교차해 하나만** 두고 표의 모든 줄을 그 합으로 냈다.

```ts
record['online/3v3/King'] = { plays, wins, draws, losses, kills }
pieceRows / modeRows / totalTally  →  전부 sumTally() 하나를 지난다
```

- 「기물별 합 = 총합」이 **지켜야 할 계약이 아니라 산수**가 된다
- 필터도 조건 하나를 더 붙이는 것뿐이라 **표·요약·이력에 함께** 걸린다.
  (한쪽에만 걸리는 것이 이 화면에서 제일 그럴듯한 버그다 — 스모크가 글자가 아니라
  **합으로** 잡는다)
- 뛰지 않은 칸은 아예 만들지 않는다(희소). 저장이 커지지 않는다

**계정 전적은 따로 센다.** 장수 전적을 더하면 한 판에 3~5명이 뛰므로 출전 수가 사람
수만큼 부풀려진다 — 「도시 전적」(C2)이 곧바로 세 배가 될 뻔한 자리다.

## 4. 「DB로 옮길 것을 전제로」가 설계를 바꿨다

기획자가 「프로토타입은 브라우저지만 서비스는 DB로 간다, 이식성 좋게」라고 못박았다.
그 한 줄로 이력의 모양이 정해졌다.

| | 그래서 |
|---|---|
| 한 줄이 **DB 한 행** | 평평하게 두고 참조를 안 만든다. `seq`가 PK, `picks`가 자식 테이블 |
| 읽는 자리를 **둘로** 모은다 | `sumTally()` · `recentMatches()`. 옮길 때 이 둘만 쿼리로 갈면 화면은 안 바뀐다 |
| **집계와 이력을 따로 쌓는다** | 이력에서 집계를 파생시키면 꼬리를 덜어 낼 때 **통산이 조용히 준다** |
| 상한(`MATCH_LOG_CAP`)은 **상수 하나** | 브라우저에서만 자른다. 서버에서는 지우는 줄 하나다 |
| `at`(시각)은 **밖에서 넣는다** | meta는 시계를 안 읽는다 — `backdrop.ts`의 `bandForHour()`와 같은 규약 |

`matchSeq`를 따로 든 것도 그래서다. 꼬리를 덜어 내도 **번호는 앞으로만** 가야 한다 —
지운 줄의 번호를 다시 쓰면 이력의 순서가 뒤집힌다.

## 5. 무승부를 「고른 뒤에」 반영한다

45쪽 보상표의 무승부는 **셋 중 택1**(카드 · 재료 · 군량)이다. 여기서 「고르는 도중」이라는
상태가 생길 뻔했고, 그건 B에서 재설계를 되감기로 바꾸며 없앤 바로 그 종류다.

같은 답을 썼다 — **고르기 전까지 계정에 아무것도 반영하지 않는다.**

```
전투 종료 → (무승부면) 화면이 outcome을 들고 묻는다 → 고르면 applyBattleResult() 한 번
```

- 안 고르고 나가면 전적도 보상도 안 남는다. 아쉽지만 **저장할 중간 상태가 없다**
- `applyBattleResult()`는 택1 없는 무승부를 **던져서** 막는다. 조용히 아무것도 안 주면
  전적만 오르고 보상이 사라진 계정이 남는다
- 승리·패배는 예전처럼 전투가 끝나는 순간 반영된다 — 물을 것이 없기 때문이다

## 6. 밟은 지뢰

### 6-1. [항복]이 내 차례가 아니면 조용히 무시된다 ★

스모크에 「항복으로 전투를 끊고 결과 화면까지 걷는다」를 더했는데, 20초를 기다려도 결과
화면이 안 떴다. 콘솔 오류도 없다. 원인은 화면이 아니라 **규칙**이었다.

```ts
// playback.ts
submit(intent) {
  if (!pre && this.phase !== 'awaitingInput') return false;   // ← 조용히 버린다
```

내 차례가 아닐 때(AI가 두는 중, 연출이 도는 중) 낸 의도는 버려진다. **화면의 [항복]은
그때도 눌리고 아무 일도 안 일어난다.** 스모크는 「내 차례가 올 때까지 기다렸다가」 누르게
고쳤지만, **사람에게는 그 안내가 없다** — 「눌리는데 아무 일도 없으면 「고장인가」가
남는다」(§5-20)에 정확히 걸리는 자리라 GDD §12 미해결에 남겼다.

> 교훈: **조용히 무시하는 경로는 테스트에서 「없는 것」처럼 보인다.** 클릭이 성공했고
> 오류도 없으니 스모크는 20초를 기다린 뒤에야 알려 줬다.

### 6-2. 규칙이 아니라 **표본**이 틀렸다

「승리 군량 +1」 테스트가 열두 조합 중 넷에서 실패했다. 규칙을 세 번 다시 읽었는데,
새 계정은 **군량이 상한(20)에 붙은 채로 시작**한다. 받을 자리가 없으니 0이 맞았다.

고친 것은 코드가 아니라 테스트의 시작 상태다(`grain: 0`). 그러면서 **상한에 걸리면 들어간
만큼만 보상으로 적는** 규칙이 오히려 회귀로 굳었다 — 화면이 없는 군량을 「+1」로
보여 주지 않는다.

### 6-3. 훅은 이른 반환 뒤에 둘 수 없다

`RecordsScreen`에 「보유에서 빠진 장수면 일람으로 돌린다」 가드가 있고 그 아래에
`useMemo` 넷을 뒀다. 렌더마다 훅 호출 수가 달라지는 자리다. 합이 칸 수십 개짜리라
**훅을 아예 뺐다** — 캐시할 값이 아니었다.

### 6-4. 요약 줄이 「총 출전출전 4」로 읽혔다

`records.sum`을 「출전 {plays} · …」로 적었는데 앞에 이미 「총 출전」이라는 이름이 있다.
**700px 스크린샷에서 눈으로 보고서야** 알았다 — 표는 다 맞고 글자만 겹친 것이라
테스트는 조용하다. 「{plays}전 · …」으로 고쳤다.

같은 스크린샷에서 이력 목록에 **머리 줄이 없어** 열이 여덟인데 `—`가 무엇의 빈칸인지
알 수 없다는 것도 보였다(부대 이름은 E가 채운다). 머리를 붙였다.

  「화면이 그 셋을 함께 보여 주는가」는 스모크가 본다
