## 2. 원본이 균일하지 않았다 — 재기 전에는 몰랐던 것

154장을 전수 조사한 결과가 설계를 거의 다 정했다.

| 관찰 | 수치 |
|---|---|
| 크기 | 1535×310이 **아닌 것 10장** (1550×313 등, 순욱은 칸 폭이 306.8로 정수가 아니었다) |
| 가장자리 띠 | **140/152장**에 위 1~4px · 아래 1~2px 의 어두운 띠 |
| 칸 경계 침범 | 경계 608곳 중 **178곳(29%)** 에서 무기·이펙트가 옆 칸으로 넘어간다 |
| 잔디 | **71%** 에만 있다 |
| 몸통 높이 | 239~305px — **28% 차이** |
| 발 위치 | 283~310 (중앙 304) |

**균등 5분할이 틀렸다는 게 여기서 나왔다.** 눈으로 보면 5칸이 가지런해 보이는데,
실제로는 창이 무기와 마법진을 자르고 있었다. 빈틈으로 자르는 방법도 안 됐다 —
x축으로 끊어 보면 덩어리가 정확히 5개인 파일이 **24장뿐**이었다(이펙트가 떨어져
나가 6~20개로 갈리거나, 반대로 붙어서 4개 이하가 됐다).

### 통한 방법 — 몸통을 기준점으로

알파가 진한 부분을 라벨링해 **큰 덩어리 5개**를 뽑으면 그게 각 칸의 몸통이다.
작은 이펙트는 가장 가까운 몸통에 배정한다. **152/152 전수 성공**했고, 그 뒤 260장에서도
실패는 한 장뿐이었다(§4-4).

> 몸통 중심과 발끝을 원점으로 잡으면 창 크기도 수치로 나온다 — 좌우 ±164, 위 305,
> 아래 3px 이면 95%를 담는다. 그래서 창을 **330×310**으로 정했다.

## 3. 기획자가 내린 결정

| 항목 | 결정 |
|---|---|
| 저장 방식 | **가로 5칸 스프라이트시트 한 장.** 5개 파일 분리도, 런타임 crop도 아니다 |
| 프레임 크기 | 110×110 (보드 셀 96×120에 세로를 맞춘다) |
| 몸통 높이 | **칸의 90%로 통일.** 원본의 28% 편차를 없앤다 |
| 잔디 | **지우고 코드로 그린 타원 그림자**로 대체 |
| 명상 ↔ 책략 | **같은 칸(3번)** 을 쓴다 |
| 고유기술 | **평상.** 전용 배너(`skillFx`)가 판 전체를 덮으므로 타일까지 바꿀 필요가 없다 |

### 스프라이트시트를 고른 이유

Phaser에 `load.spritesheet(key, url, {frameWidth, frameHeight})` 가 있다. 로드 시점에
한 번 잘라 주고 상태 전환은 `setFrame(n)` — **텍스처 교체가 없다.**

| | 요청 수 | 상태 전환 | 애니메이션 |
|---|---:|---|---|
| 5개 파일로 분리 | 1300 | 텍스처 교체 | 직접 구현 |
| 매번 crop | 260 | crop 연산 | 직접 구현 |
| **스프라이트시트** | **260** | **UV만 바뀜** | `anims` 그대로 |

전송량은 문제가 아니다 — [`BattleScene.preload`](../packages/client/src/battle/BattleScene.ts)가
**전투에 나오는 유닛만** 불러온다(5:5면 10장).

### 확정된 시간표 (GDD §3.10에 옮겨 적었다)

| 상황 | 연출 |
|---|---|
| 이동 | 경로의 칸마다 **0.2초씩**. 미끄러지지 않고 한 칸씩 뛴다 |
| 공격 | 공격 0.2초 → 대기 0.2초 → **공격 2초**. 마지막 2초에 대상이 피격 |
| 책략·명상 | 점멸 없이 1초. **적에게 성공하면 1초 더**, 그 1초에 대상이 피격 |
| 퇴각 | 피격을 **0.4초 간격 3번 점멸** 후 소멸 |
| 그 외 | 평상 |

공격의 2초와 책략의 두 번째 1초는 **시스템 대화창을 읽을 시간**이다.

## 4. 밟은 지뢰 ★ 다시 밟지 말 것

### 4-1. 마젠타 테두리 — 알파까지 다시 풀어야 한다

생성기가 배경을 마젠타로 깔아 준 JPG를 기획자가 먼저 배경제거해 PNG로 넘겼는데,
**마젠타 테두리가 남았다.** 알파 구간별로 재 보니 원인이 한눈에 보였다.

| 알파 | 평균 RGB | 마젠타 지수 |
|---:|---|---:|
| 1~32 | (236, 12, 233) | 508 ← 거의 순수 마젠타 |
| 255 | (102, 90, 91) | 20 ← 깨끗 |

**RGB에 합성된 색이 그대로 남아 있었다.** 배경제거 도구가 알파만 만들고 RGB는
손대지 않은 것이다.

`p = a·F + (1−a)·B` 를 풀면 되는데, **색만 걷어내면 부족하다** — 저장된 알파가
과대평가돼 있어서 그 값으로 나누면 마젠타가 남는다(지수 470 → 216, 눈에 보임).
**알파까지 다시 풀어야** 사라진다(470 → 56).

> 순수 수학으로 `a ≥ max(G/255, 1−R/255, 1−B/255)` 하한을 쓰면 안 된다.
> 파란 투구(R이 낮다)가 84% 투명으로 깎인다. **이웃의 깨끗한 색을 참값으로** 삼아야 한다.

### 4-2. 그래서 JPG를 직접 받는 편이 낫다

같은 장수 8명을 두 경로로 처리해 비교했다.

```
JPG 직접   잔여 마젠타 ~100px
PNG 경유   잔여 마젠타 ~30,000px
```

**배경제거를 먼저 돌리면 「이 픽셀이 얼마나 배경이었는지」가 사라진다.** 그 정보가
있어야 위 식을 세울 수 있다. 도구는 두 갈래를 다 받지만, 앞으로는 합성본을 그대로 받는다.

### 4-3. 이엄의 피부가 초록이 됐다 — 배경 빼기가 안쪽까지 닿았다

이엄의 배경은 `(212,68,212)`로 다소 탁한 마젠타였고, **회색 갑옷과의 색차가 92밖에
안 됐다.** 그래서 갑옷이 「오염 안 된 속살」 판정에서 빠졌고, 거기에 마젠타 빼기가
적용되자 캐릭터가 통째로 물들었다.

→ 속살을 **색과 위치 둘 다로** 판정한다. 배경에서 3px 넘게 떨어져 있으면 색이 비슷해도 속살이다.

> 배경색을 파일마다 다시 뽑는 것도 이때 필요했다. 순수 마젠타가 아닌 것이 있다
> (이엄 `(212,68,212)`, 주강 `(252,132,252)`).

### 4-4. 정덕이 통째로 사라졌다 — 띠가 배경을 가뒀다

위·아래 어두운 띠가 배경을 완전히 둘러싸서, **캐릭터 사이의 빈 곳이 이미지 테두리와
이어지지 않았다**(배경 15조각 중 2개만 테두리에 닿았다). 플러드가 닿지 못해 배경이
77% 살아남았고, 그걸 「가장자리 띠」로 오인한 제거 로직이 그림을 다 지웠다.

→ 플러드 씨앗을 맨 가장자리가 아니라 **안쪽 16px 띠**에 놓는다.

### 4-5. 유엽의 5명이 하나로 붙었다 — 임계값을 잘못 잡았다

맨 아랫줄에 남은 띠가 다섯을 연결했다. 원인은 내가 잡은 `BAND_FILL = 0.5`인데,
**발치에서는 캐릭터 5명만으로도 폭의 65%가 찬다.** 띠가 아닌 걸 띠로 보고, 그러다
두께 상한(8px)에 걸려 아무것도 안 지웠다.

→ `0.9`로 올렸다. **진짜 띠는 폭의 100%를 채운다.**

> 임계값을 정할 때는 「정상값이 어디까지 올라가는지」를 먼저 재야 한다.
> 0.5는 아무 근거 없이 고른 숫자였다.

### 4-6. 갇힌 마젠타 — 기획자가 눈으로 찾았다

팔과 몸 사이, 들어올린 무기 아래, **마법진 안쪽**처럼 캐릭터가 둘러싼 공간은
테두리와 이어지지 않아 연결성만으로는 안 잡힌다. 260장을 다 돌린 뒤 기획자가
직접 그림을 넘겨 보고 찾았다.

→ 배경색에 아주 가까우면(색차 48 이내) 위치를 따지지 않고 배경으로 본다.
**이렇게 진한 마젠타를 캐릭터에 칠하는 일은 없다**는 기획자 확인을 받고 넣었다.

```
진한 마젠타 픽셀: 최대 2467 → 87
```

### 4-7. 대상이 너무 일찍 아파했다 — 유닛마다 시계가 따로 돌았다

연출을 붙인 뒤 실제 화면에서 20ms 간격으로 자세를 찍어 보니 이렇게 나왔다.

```
13390  P2-Bishop:1      이동 중
13790  P1-Bishop:4      ← 아직 걸어오는데 대상이 아파한다
13981  P2-Bishop:2      공격 시작
```

**유닛마다 타임라인을 0에서 시작한 게 원인이었다.** 때리는 쪽은 앞선 이동 0.6초만큼
밀리는데 맞는 쪽은 안 밀렸다. → 이벤트를 훑으며 **공용 커서**를 밀고 모든 구간을
그 위에 놓는다. 같은 이유로 퇴각 점멸도 죽인 공격이 끝난 뒤에 시작한다.

고친 뒤:

```
13351  P2-Bishop:1               이동 600ms = 3칸 × 200ms
13951  P2-Bishop:2               공격 점멸 0.2초
14169  (전원 평상)                간격 0.2초
14366  P1-Bishop:4 P2-Bishop:2   두 번째 공격 + 피격이 동시에
16358  (전원 평상)                2초 뒤 종료
```

### 4-8. 세션이 끊겨 253장이 옛날 것으로 남을 뻔했다

4-6을 고친 뒤 **7장만 다시 굽고** 다음 주제로 넘어갔다가 세션이 끊겼다. 다음 세션에서
`--force` 전체 재생성을 하고서야 맞았다.

> **파라미터를 고쳤으면 그 자리에서 전체를 다시 굽는다.** 일부만 굽고 넘어가면
> 폴더 안에 서로 다른 규칙으로 만든 파일이 섞이고, 그건 나중에 눈으로 못 찾는다.

## 5. 구조에서 기억할 것

### 연출은 엔진을 모르고, 엔진은 연출을 모른다

```
engine        BattleEvent[]           판정 — 언제 무엇이 일어났나
   ↓
poses.ts      PoseDirector.plan()     누가 몇 ms 동안 어떤 칸을
   ↓ (ms)
playback.ts   Playback.hold(ms)       그동안 시간·입력·AI 정지
   ↓
BattleScene   sprite.setFrame(n)      그린다
```

`PoseDirector`가 **Phaser를 부르지 않는다.** 이벤트와 시간만 다루고 그리는 일은
씬이 한다. 그 경계 덕에 **헤드리스로 시간표를 잴 수 있고**, `poses.test.ts` 15건이
거기서 나왔다. 눈으로는 0.2초와 0.3초를 구분할 수 없으니 이게 유일한 검증 수단이다.

`Playback`은 「몇 ms 기다려라」만 안다. 무엇을 그리는지는 모른다 —
온라인이 되어도 이 경계는 그대로다(서버는 기다려 주지 않고, 재생기가 뒤처질 뿐이다).

### 축소는 RGBa 를 거친다

투명 픽셀의 색이 평균에 섞이면 실루엣 가장자리에 배경색이 번진다. 원본에 실제로
지울 색이 남아 있다. 실측하니 Pillow 12는 그냥 RGBA로 줄여도 결과가 같지만,
버전에 딸린 성질이라 명시해 뒀다(2026-08-07 §3-1의 교훈).

> 시계열로 찍는 편이 빠르고 정확했다. 4-7의 버그도 그렇게 잡혔다.

## 7. 새 대화로 이어갈 때

### 이 세션에서 만든 것을 건드릴 때

- **시간표를 바꾸려면** `poses.ts` 위쪽 상수만 고친다. `poses.test.ts`가 먼저 깨지므로
  의도한 변경인지 사고인지가 바로 드러난다.
- **`assets/CharsAction/`에 새 그림을 넣으면** `npm run actions` 한 번이면 된다.
  크기가 달라도, 가장자리에 띠가 남아도, 무기가 칸을 넘어가도 흡수한다.
- **마젠타 합성본(JPG)을 그대로 넣는 편이 낫다.** 배경제거를 먼저 돌리지 말 것 (§4-2).

### 남겨둔 것

| 항목 | 비고 |
|---|---|
| 고유기술 자세 | 평상으로 뒀다. 전용 배너가 판을 덮으므로 충분하다는 기획자 판단 |
| `public/portraits/` | 보드 타일 자리를 액션 시트에 넘겼다. 정보 팝업의 폴백으로만 남는다 |
| 발밑 자갈 | 잔디는 색으로 갈라내지만 자갈은 갑옷과 같은 회색이라 일부 남는다 |
