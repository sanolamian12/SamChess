## 1. 전투력 계수 — 옮겼다 (기획자 결정)

`npm run power`(모드당 2만 판 + 보정 5천 판)를 다시 돌려 §6-1 값을 재현한 뒤, 판단 근거로 **옛 계수(그때의 `POWER_MODELS`)와
새 계수를 새 AI 5천 판에 함께 재 봤다**:

| | 옛 계수 | 새 계수 |
|---|---|---|
| 3v3 logLik · Brier | −2536.4 · 0.1682 | −2528.8 · 0.1679 |
| 5v5 logLik · Brier | −2810.8 · 0.1904 | −2812.2 · 0.1906 |

보정은 사실상 같았다(옛 계수가 「안 맞게 된」 것은 아니다). 그래서 「옮기지 않음」을 권했으나 기획자가 **옮김**을 골랐다 —
측정 대상과 같은 AI로 맞춰 두자는 쪽이다.

그 사이 AI가 한 번 더 바뀌었으므로(아래 2) **최종 AI로 다시 재서 그 값을 옮겼다**. §6-1과는 표준오차 1.5배 안에서 같다.

능력치 · 성장 계수는 비슷하다. 보정 3v3 −5.8 ~ +0.7%p · 5v5 −5.9 ~ +2.3%p(둘 다 40~45% 구간이 가장 어긋난다).
부대 폭 3v3 211 ~ 1273(옛 213 ~ 1322) · 5v5 256 ~ 1328(옛 243 ~ 1277).

- `power.ts` 계수 · 「§4 실측 기록」, `power.test.ts` 계수 · 고정 편성 7개(863 → 822 등).

## 2. 5v5 무승부 상한 여유 — AI만 고쳤다 (기획자 결정, 상한 6000 그대로)

먼저 **끝 꼬리가 무엇인지** 봤다. 상한을 늘려 재는 측정용 `--cap`을 `balance.ts`에 붙였다(엔진 상수는 안 건드리고 프로세스 안에서만 덮는다).

- **영구 교착** — Lv1 5v5의 상한 판정 1판은 **상한 30000에서도 안 끝났다.** 판을 따라가 보니 여섯이 턴만 넘겼다:
  북군 Bishop이 남군 군량고 **바로 위**에 섰는데 칸 색이 달라 영원히 못 들어가고, 거리를 줄이는 걸음이 없어 안 움직였다.
  북군 Knight는 King 두 칸 앞의 국소 최소에, 남군 수비는 다가갈 칸이 없어 같이 섰다. `stepToward`가 체비쇼프 거리만 보기 때문이다.
- **느린 판** — 레벨이 오르면 상한에 닿는 판이 는다(5v5 Lv5 0.9% · Lv9 0.4%). 상한을 없애면 7829 안에 끝나는 진짜 느린 판이다.
- 오래 끄는 판(4000+) 42개 중 대부분은 **King끼리 남은 끝내기**였다.

변형을 넷 재 봤다(같은 시드 · 같은 표본):

| | 5v5 Lv1 상한 / 최대 | 5v5 Lv5 | 5v5 Lv9 | 3v3 Lv5 |
|---|---|---|---|---|
| 지금 | 0.1% / 5745 | 0.9% / 5883 | 0.4% / 5984 | 0.5% / 5940 |
| 지키기 반경 4 → 3 | 0.1% / 5864 | | | |
| 맞받아치기 2 → 1 | 0.1% / 5585 | | | |
| 홀로 남은 King이 안전을 안 봄 | 0.1% / 5745 | | | |
| 상한 8000 | 0.1%(교착) | 0% / 7829 | ~0.1%(교착) / 6673 | 0.1% / 7167 |
| **막힘 풀기(길 찾기)** | **0** / 5243 | 0.6% / 5937 | 0.3% / 5827 | 0.15% / 5921 |
| 막힘 풀기 + 상한 8000 | | 0 / 7049 | 0 / 6950 | 0 / 7740 |

기획자가 **막힘 풀기만** 골랐다. `ai.ts`의 `unstick` · `pathStep` — 한 걸음으로 가까워질 칸이 없을 때만 **기물 걸음으로 BFS(깊이 6)** 해
적 군량고 · 적 King을 칠 자리, 아니면 아무 적이나 칠 자리로 가는 길의 첫 걸음을 고른다. 맞받아치는 장수도 같은 길 찾기를 쓴다. 평소 걸음은 그대로다.
등급 · 진영 승률은 오차 안이다(3v3 S 66.7 · D 39.1 · 남군 50.2%, 5v5 S 59.2 · D 43.1 · 남군 52.3%).

- 회귀 `supply.test.ts` 「한 걸음으로 가까워질 칸이 없으면 기물 걸음으로 길을 찾는다」 — **실제 교착 판의 자리**를 그대로 옮겼다.
  처음 짠 자리는 「가까운 적에게 다가가기」 갈래가 대신 움직여 **막힘 풀기를 빼도 통과했다** — 가장 가까운 적이 곁에 있어야
  두 갈래가 다 막힌다. 빼면 떨어지는 것을 확인했다.
- GDD §3.9 실측 줄 · 상한 줄, `FORMULA.drawTimeLimit` 주석을 고쳤다.

## 3. 탈취 장면 눈 확인 — `?supply=1|2`

- `createDemoBattle`의 `supply` — 그 진영의 King 아닌 장수 하나를 **기물 마스크로 적 군량고에 닿는 빈 칸**에 세우고 WT를 판 전체 최소로 당긴다.
  `1`이면 남군(사람)이 [이동]으로, `2`면 북군(AI)이 「지금 이길 수 있으면 이긴다」로 들어간다.
- 프레임 사진(700×1400, 90ms 간격 + 페이지 안 rAF 표본)으로 본 것:
  - 사람 — [확정] 뒤 카메라가 군량고 열(x 12.0)로 확대해 가고, 0.6초 뒤 받침이 남군 색(0.55 → 0.85) + 그림이 두 번 뛴다(×1.25),
    뛰기 시작부터 결과로 넘기기까지 1.35초, 그 뒤 판 전체로 물러난다. 군량고가 맨 윗줄이라 카메라는 판 끝에 걸려 군량고가 화면 위쪽에 선다.
  - AI — 들어가는 장수를 먼저 비추고(1초) → 판 전체로 걸음 → 군량고로 다시 확대 → 뛰기. 평소 AI 이동의 카메라 규칙 그대로다.
  - 뛰기는 카메라 확대가 75%쯤 왔을 때 시작한다(`look()` + `CAM_LEAD_MS`의 일반 규칙 — 다른 연출과 같다).
- `BattleScene.debugSupplyDepots()`가 받침 색 · 불투명도 · 그림 배율을 함께 내고, `debugFinishedAt`(결과로 넘긴 시각)을 더했다.
- `smoke:ui` 「군량고 탈취 장면」 — 카메라가 군량고 열 · 확대 1.5배 이상 · 받침이 승자 색 · 더 진하게 · 그림 ×1.2 이상 · 머묾 `SUPPLY_TAKEN_MS − 150` 이상.
  길이는 `poses.ts`의 상수를 import한다(스모크에 다시 적지 않는다). 첫 완주: 확대 0.18 → 0.45 · 0.55 → 0.85 · ×1.25 · 1416ms.

— **이 대기는 빼고 돌려도 통과했다**(경주라 대개 안 걸린다). 완주.
⚠ 같은 꼴(`.scr-new` 뒤 곧장 `.scr-main`)의 도구가 열 개 넘게 더 있다(`academy_ux` · `city_bonus_ux` · `collection_ux` · `forge_ux` …) — 같은 이유로 멈출 것이다. 이번엔 안 고쳤다.

## 5. 교훈

- **「상한을 늘리면 될까」는 상한을 크게 늘려 재 보면 답이 나온다** — 30000에서도 안 끝나는 판은 느린 게 아니라 멈춘 것이다. 꼬리를 하나로 보면 처방이 틀린다.
- **회귀가 노리는 갈래를 실제로 지나는지는 그 갈래를 빼 보고서야 안다** — 첫 자리는 다른 갈래가 대신 움직여 통과했다. 실제로 난 판의 자리를 그대로 옮기는 것이 빠르다.
- **측정 도중 AI를 또 바꾸면 이미 잰 계수의 전제가 바뀐다** — 기획자가 §6-1을 옮기기로 한 뒤 AI가 바뀌어, 최종 AI로 다시 재서 옮겼다(차이는 오차 안).
- 무거운 측정(전투력 적합)과 `smoke:ui`를 함께 돌리면 첫 검사가 시간 초과로 떨어진다(「사람 차례가 오지 않았다」) — 제품 문제가 아니라 CPU다.
