# 2026-10-22b — 관리자 화면의 손으로 맞춘 값을 계약으로

관리 일원화(2026-10-22) 뒤 첫 작업. 관리자 화면(`../SamChessAdmin`)은 서버 응답 타입을 `admin/types.ts`에서 `import type`으로
읽어 모양이 바뀌면 `npm run typecheck:admin`이 깨진다. 그런데 인수인계서 §3-2의 값들은 화면이 숫자 · 문자열을 **다시 적고**
있어서 본체가 바꿔도 아무 오류가 없었다. 그것들을 계약으로 올렸다.

## 방식 — 리터럴 타입 + `satisfies`, 안 되면 응답에 시각으로

화면은 `import type`만 쓴다(값을 import하면 SamChess 코드가 번들에 들어간다). 그래서 두 갈래로 나눴다.

| 갈래 | 언제 | 어떻게 |
|---|---|---|
| **리터럴 타입 + `satisfies`** | 값이 코드에 리터럴로 적힌 상수 | 계약이 `typeof X`(리터럴 타입)를 내보내고 화면이 같은 값을 적어 `satisfies`로 묶는다 — `mail.ts`의 `MAIL_LANGS`가 이미 하던 방식 |
| **응답에 싣기** | 엑셀에서 오는 값 · 계정마다 다른 값 | 서버가 정산과 같은 함수로 계산한 **시각**을 응답에 싣는다 |

둘째를 고른 이유: 시간 규칙 문장의 분(AI 60분은 곱셈, 도적떼 10분 · 60분은 `RAID.*Minutes` — 엑셀)은 타입이 `number`라 묶이지 않고,
**도적떼 응전 시간은 컬렉션(`raidResp`)으로 계정마다 늘어난다** — 화면의 「대기 10분」은 그 계정에서 이미 틀린 문장일 수 있었다.
분을 실어 화면이 더하게 하면 규칙을 화면이 다시 짓는 것이라, 시각 자체를 실었다. 경고는 이제 「그냥 두면 10/22 15:40(응전 마감)에 같은
처리가 된다」처럼 그 계정의 실제 시각을 말한다.

## 바꾼 것

| 값 | 전 | 후 |
|---|---|---|
| 정지 「영구」 36500 | `server-api/admin/store.ts`의 `BAN_DAYS_MAX`, 화면 `PERIODS` · `days === 36_500` 두 곳 | `BAN_DAYS_MAX`를 **`meta/src/admin.ts`로 옮김**(계약이 `store.ts`를 `typeof`로 읽으면 화면 typecheck에 `pg`가 딸려 간다) → `BanDaysMax`. 화면 `BAN_FOREVER_DAYS = 36_500 satisfies BanDaysMax` 하나를 BanPanel · 감사 로그가 함께 읽는다 |
| CS 정지 상한 7 | 화면 `SHORT_MAX_FALLBACK = 7`(§3-2에 없던 것) | `7 satisfies CsBanDaysMax` — `AdminMe.cs.banDaysMax`도 이 타입 |
| 감사 로그 `action` 이름 | 서버는 `string`, 화면 `ACTION_LABEL: Record<string, string>` | 계약에 **`AdminAuditAction`** 유니언(`adjust.${Adjustment['kind']}` · `resolve.${Resolution['kind']}` · `ban` · `unban` · `mail.send` · `mail.revoke`)과 묶음 `AdminAuditActionGroup`. 서버 `insertAudit()` · `mutateWithAudit()`이 이 타입만 받고, `AuditRow.action` · `AuditQuery.action`도. 화면은 `Record<AdminAuditAction, string>` · `Record<AdminAuditActionGroup, string>` |
| 우편 기한 30일 | meta `MAIL_TTL_MS = 30 * 24 * …`(곱셈 → `number`), 화면 `MAIL_TTL_DAYS = 30` | meta에 **`MAIL_TTL_DAYS = 30`**(리터럴)을 두고 `MAIL_TTL_MS`를 거기서 낸다 → `MailTtlDays`. 화면 `30 satisfies MailTtlDays` |
| 시간 규칙 경고(AI 60분 · 도적떼 대기 10분 / 전투 60분) | `ResolvePanel.tsx`의 문장 | `UserDetail.autoResolveAt { aiBattle, raid }` — meta의 새 `aiAbandonAt()` · `raidAutoSurrenderAt()`. **정산 함수 `syncAiBattle` · `syncRaid`도 이 둘을 쓰도록** 고쳐 시각을 내는 자리가 하나다 |
| 판 종류(`ai` · `raid` · `online`) | 화면 `ResolvePanel`의 `as const` 객체와 루프 배열 · 감사 로그의 객체, 세 벌 | 계약이 `CarriedBattle`을 내보내고 화면 `BATTLE_LABEL: Record<CarriedBattle, string>` 하나를 둘이 읽는다. 루프도 그 키로 |
| 한 쪽 50줄 | 화면 `api.ts`의 `limit: '50'`과 페이지의 `length === 50` | 화면 안의 중복이었다 — `PAGE_SIZE` 하나로(계약이 아니라 화면이 정해 보내는 값, 서버는 200까지) |

### 올리지 못한 것 — 인수인계서 §3-2에 이유와 함께 남김

- 감사 로그 `params`의 **모양** — `jsonb`에 옛 줄이 남는다. 지금 모양으로 박으면 옛 줄에 거짓말을 한다.
- 정리의 **뜻**을 적은 문장(태학 · 부상 · 아이템) — 문장이라 타입이 없다. 뜻이 바뀌면 `adminResolve.test.ts`가 먼저 깨진다.
- 대장간 「Lv × 1분이라 정리 대상이 아니다」 — 기능이 없는 줄의 설명이다.
- `syncAtServer()`의 범위 · 게임 데이터 표시 문구 · 새 재화를 넣을지 — 행동 · 문구 · 기획 결정.

## 검사

- **새 검사가 실패하는 것을 먼저 봤다** — 계약 쪽을 하나씩 바꿔 `typecheck:admin`을 돌리고 되돌렸다. 다섯 다 exit 2:
  `BAN_DAYS_MAX` 36501 → `BanPanel.tsx` TS1360 · `CS_BAN_DAYS_MAX` 6 → TS1360 · `MAIL_TTL_DAYS` 31 → `mail.ts` TS1360 ·
  유니언에 `city.rename` → `AuditPage.tsx`의 `ACTION_LABEL` **과** `GROUP_LABEL`(새 묶음 `city`) 둘 다 TS2741 ·
  `CarriedBattle`에 `arena` → `ResolvePanel.tsx` TS2741. 되돌린 뒤 exit 0.
- 서버 쪽도: `store.ts`에서 `'mail.revoke'`를 `'mail.recall'`로 바꾸자 본체 `npm run typecheck`가 TS2322 — 계약 밖 이름은 적을 수 없다.
- `adminResolve.test.ts`에 「저절로 정산되는 시각」 두 건 — `aiAbandonAt` · `raidAutoSurrenderAt`(대기 · 전투)이 **그 시각에** 정산되고
  1ms 전에는 그대로인지, 끝난 판은 `null`인지.
- `smoke_admin.ts`에 한 줄 — 계정 상세에 `autoResolveAt`이 실렸는지(판이 없는 계정이라 `null` 둘. 값은 회귀가 본다 — 이 줄은 칸이 빠지면 깨질 뿐이다).
- `npm test` 1020 통과 · `typecheck` · `typecheck:admin` 통과 · 관리자 `npm run build` exit 0(번들에 `parseMailDraft` · `ROLE_PERMISSIONS` ·
