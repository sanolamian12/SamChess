# 도시 삭제 — 장부에 남기기 · 받은 우편 다시 받기 막기 (2026-11-13)

기획자가 시험 계정을 도시 Lv2로 키우다 「도시 삭제」 후 새 도시(「오다도시」)로 다시 시험하던 중 「이 경우 추적이 어떻게 되나」를 물었다.
따라가 보니 빈틈이 둘이었다. **삭제 자체는 막지 않는다** — 운영에서도 `DELETE /profile`은 연다(기획자 확정, 코드 주석에 적음).
(같은 시각 다른 세션이 튜토리얼 전투를 고치고 있어 클라이언트 · `meta/guide.ts`는 건드리지 않았다. 공용 서버는 다시 띄우지 않고 저장 함수를 직접 불러 시험했다.)

## 1. 따라가 본 것 — 로그인 계정은 그대로, 도시만 바뀐다

`DELETE /profile`은 `profiles` 행과 수비군 스냅샷(`defenses`)만 지운다. 로그인 계정(`auth.users`)과 그 uid에 묶인 것 — 변화 장부 · 접속한 날 ·
감사 로그 · 이상 징후 · 방어 기록 · 260명 순번 — 은 남고, 도시 안의 것(건물 · 장수 · 가챠 순서 · 튜토리얼 · **우편의 받음 표시**)은 사라진다.
새 도시는 같은 uid로 첫 저장(`PUT /profile`)이 되어 장부에 `create` 줄이 생긴다. 「오다도시」 계정의 장부: … `#353` 증축 Lv2 · `#358` · `#361` 건물 → `#787` `create` Lv1.

## 2. 빈틈 ① — 지운 사실이 아무 데도 없었다 → 장부에 `delete` 줄

장부에도 감사 로그에도 남지 않아 옛 도시의 마지막 줄 다음에 `create`가 곧장 이어졌고, **옛 도시 이름은 어디에도 없었다**(장부의 값은 숫자뿐).

- 장부 단계에 `delete`를 더했다(`schema.sql`의 check · `note jsonb` 칸). 바뀐 만큼 = 지운 도시의 값 전부(음수), `after`는 비었다, `note`에 옛 이름 · 레벨.
- 적는 자리는 `ledger.ts`의 `writeDeleteLine` 하나, 부르는 자리는 `deleteProfile` — **지우기와 한 트랜잭션**(줄이 있으면 지워졌고 지워졌으면 줄이 있다).
  되접기가 못 읽는 행이어도 지운 사실은 남긴다(값은 비우고 이름만 원본에서). 출처는 요청 맥락 그대로(`DELETE /profile`, 도구면 `tool`).
- 관리자 계약 `AdminLedgerRow.phase`에 `delete` · `note`, 화면 「변화 내역」은 「도시 삭제 — 「옛이름」 Lv2 도시를 지움」 + 바뀐 만큼. `create`의 이름표를 「새 계정」 → 「새 도시」로.
- 이상 징후 점검은 그대로 맞는다 — 지운 계정은 `profiles`에 없어 안 보고, 새 도시는 `create` 줄이 새 기준이다.

## 3. 빈틈 ② — 받은 우편을 새 도시에서 다시 받았다 → `mail_claims`

우편이 보이는가는 **가입 시각**(`auth.users.created_at <= sent_at`, 한 사람 우편은 uid)으로 정해 도시가 바뀌어도 그대로인데, 「받았다」는 **도시 안**
(`mailbox[].claimed`)에만 있었다. 도시를 지우고 새로 세우면 기한이 남은 우편 — CS 보상 우편 포함 — 을 다시 받았다.
**재현함**: 한 사람 우편(금화 500) 받기 → 같은 도시에서 다시 받기 409 → 도시 삭제 → 새 도시 → **다시 받기 200**.

- 새 표 `mail_claims (uid, mail_id)` — 「받았다」의 정본. 받기와 **같은 트랜잭션**(`mutateProfile`의 `onWrite`)에서 `on conflict do nothing`으로 넣고,
  아무것도 못 넣으면 받기 전체를 되감고 409 `mail.claimed`. 미리 보지 않는다 — 받은 뒤 회수된 우편은 「못 받는다(404)」가 먼저다(smoke:admin이 잡았다).
- 우편함의 「받음」은 도시 쪽과 표 어느 쪽이든. 도시 쪽 기록은 그대로 둔다(화면 · meta 회귀가 읽는다).
- 관리자 우편 목록의 「받은 수」도 표에서 센다 — 지운 도시의 받기까지. 「읽은 수」는 그대로 도시 쪽(기한이 지나면 둘 다 `null`은 그대로).
- **채움**(`db:migrate`가 몇 번 돌려도 같다): ① 지금 도시에 적힌 받기, ② 변화 장부의 짝 `mail:{id}`(2026-11-12부터 — **이미 지운 도시의 받기까지**).
  ②는 `account_ledger`가 만들어진 뒤라야 해서 그 절 아래에 둔다(새 DB에서 순서가 틀리면 표가 없어 실패한다).
  개발 DB는 우편이 0통이라 채운 줄이 0 — 그래서 채움 두 문장을 `schema.sql`에서 꺼내 시험 계정으로 따로 돌려 봤다(① 1줄 · 도시를 지운 뒤 ① 0줄 · ② 1줄 · 다시 돌려도 1줄).
  ⚠ 직접 부른 `claimMailAction`은 요청 맥락이 없어 장부에 짝을 안 남긴다 — ② 시험은 진짜 받기 요청이 남기는 꼴의 줄로 했다.

## 4. 검사

- `npm test` 1460 · `typecheck` · `typecheck:admin` · 관리자 `npm run build`
- `smoke:admin`에 한 덩이 — 새 계정으로 우편 받기 → `DELETE /profile` → 장부 첫 줄이 `delete`(출처 `DELETE /profile` · 옛 이름 · 금화 음수) → `PUT /profile`로 새 도시 →
  우편함 「받음」 · 다시 받기 409 `mail.claimed` · 관리자 「받은 수」 1. 진짜 라우트(게임 · 관리자 앱을 제 안에 띄운 것)로 지난다.
- 개발 DB `db:migrate` 적용. **운영은 `db:migrate:prod`가 먼저**(표 `mail_claims` · 장부 칸 `note` · 단계 `delete`) — 없으면 받기 · 도시 삭제가 실패한다.
