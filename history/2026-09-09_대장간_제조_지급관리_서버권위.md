## 1. 설계 — 질문 다섯이 거의 다 정했다

사용자가 화면 요구사항(제조/현황/지급/해제, 제조 중엔 [주문 취소]만 가능,
Lv*n* = 실제 *n*주)을 먼저 준 뒤, 코드를 뒤져 확인해야 하는 것 다섯을 물었다.

1. **장수당 지급 슬롯** — 무기+방어구 각 1개 vs 종류 무관 1개 vs 무제한.
   → **종류 무관 1개.**
2. **동시 제조 슬롯** — 1건 vs 대장간 레벨만큼.
   → **1건.**
3. **제조 기간의 "게임 시간"** — 실제 경과 시간(`syncGrain`과 같은 벽시계
   방식)인가, 별도 게임 내 달력이 필요한가.
   → **실제 경과 시간**(이 저장소에 게임 내 달력 개념이 아예 없었다).
4. **이미 낀 장수를 다시 고르면** — 자동 교체 vs 선택 불가.
   → **자동 교체.**
5. (탐색 중 발견) **지난 세션이 이미 "계정당 1개씩만 제작 가능"을 확정**해
   두었다(`EquipmentData` 문서 주석, 가격 합 750금화가 그 증거) — 이번 세션이
   뒤집을 것이 아니라 그대로 설계에 반영했다.

이 다섯이 정해지자 데이터 모델이 저절로 단순해졌다 — 아이템이 계정당 최대
1개라 "재고 개수" 개념이 필요 없고, 장비 하나당 "보유 여부 + 지급 대상"만
있으면 된다.

## 2. 갈림길 — 서버 권위냐 클라이언트+PUT이냐

설계를 다듬던 중 2026-09-07 히스토리 문서의 "남은 것" 항목에서 이 문장을
다시 찾았다:

> 금화(클라이언트 소유)를 내고 아이템(서버 소유)을 받는 거래라 폴백을 하면
> 안 된다 — 물러나면 금화만 사라진다(`MarketScreen.buyMaterials`와 같은 구조).

이게 "지난 세션의 권고"인지 "이번 세션이 새로 정할 여지가 있는 것"인지
애매해서 사용자에게 다시 물었다 — 답은 **권고 그대로 서버 권위**였다.
그래서 제조 시작/취소는 `MarketScreen`의 건축 자재 구매(`POST
/market/materials`)와 완전히 같은 골격을 탔다: 클라이언트는 "무엇을"만
보내고, 판정·계산·시각은 서버가 하고, 실패해도 로컬로 물러나지 않는다.

**지급/해제는 다르게 갔다** — 이미 만든 것을 이 장수 저 장수로 옮길 뿐
총량이 안 늘어나므로, 다른 메타 화면들처럼 클라이언트가 직접 계산해 `PUT`으로
올린다. 그래서 `forgeOwned`의 경계도 한 덩어리가 아니라 **키(보유 여부)는
서버 소유, 값(지급 대상)은 클라이언트 소유**로 갈라야 했다.

## 3. 데이터 모델 (`packages/meta`)

### 3-1. `PlayerProfile`에 필드 둘 (버전 안 올림)

```ts
forgeOwned: Record<string, OfficerId | null>;   // 키가 있으면 보유, 값은 지급 대상
forgeOrder?: { equipmentId: string; startedAt: number };  // 진행 중인 주문, 슬롯 1개
```

기존 필드가 하나도 안 바뀌고 더해지기만 해서 `PROFILE_VERSION`을 올리지
않았다(§5-40과 같은 결). `migrateProfile()`은 **장수를 다 읽은 뒤에**
`forgeOwned`를 읽는다 — 지급 대상이 계정에 없는 장수를 가리키면 삭제하지
않고 "지급 해제"로 되접는다(장수 정정으로 사라진 지급 대상 정리, `readSquads`가
이미 쓰던 순서와 같은 이유).

### 3-2. `packages/meta/src/forge.ts` (신설)

`city.ts`의 `canBuild`/`applyBuild` 결을 그대로 따랐다.

- `craftDurationMs(unlockLevel)` = `unlockLevel × 1주`(ms)
- `craftableEquipment(profile)` — 해금 레벨 필터(`equipmentForForge`) 위에
  **이미 만든 것을 뺀다**(총량 750 제한의 실제 구현)
- `canStartForgeOrder` / `applyStartForgeOrder` — 해금 레벨 · 미보유 · 슬롯
  비어 있음 · 금화 검사 후 차감 + `forgeOrder` 기록
- `canCancelForgeOrder` / `applyCancelForgeOrder` — 전액 환불
- `collectForgeOrder(profile, nowMs)` — 기간이 지났으면 미지급 상태로
  `forgeOwned`에 넣는다. **`city.ts`의 `syncCity()`에서 호출한다** —
  군량·부상·병원 정산과 같은 자리 하나로 모아, 서버(`getProfile()`)도
  클라이언트(오프라인 폴백)도 따로 부를 필요가 없게 했다. `forge.ts`가
  `city.ts`의 `buildingLevel`을 쓰고 `city.ts`가 `forge.ts`의
  `collectForgeOrder`를 쓰는 **순환 import**가 생기는데, 둘 다 함수 몸통
  안에서만 서로를 참조해 모듈 평가 시점에는 문제가 안 된다.
- `equipOfficer` — 대상 장수가 이미 다른 병기를 끼고 있으면 **자동으로
  풀어 준다**(요구사항 4)
- `unequipOfficer`, `equippedBy`, `forgeSummary`(보유/지급/여유 집계)

### 3-3. `authority.ts` — 서버 소유 경계

`SERVER_OWNED_FIELDS`에 `forgeOrder`를 더했다(통째로 서버 값 유지).
`forgeOwned`는 이 목록으로 표현이 안 돼 `guardServerOwned()`에 전용 병합을
추가했다 — **서버가 가진 키 집합은 그대로 지키고**(클라이언트가 새 항목을
지어내 총량을 스스로 늘릴 수 없다), **이미 있는 키의 값(지급 대상)은
클라이언트가 보낸 것을 받는다**(정당한 지급/해제가 저장되어야 하므로).
`roster`의 부상 자국 보호와 방향이 반대인 사례라 주석으로 남겼다.

## 4. 서버 (`packages/server-api`)

`profileStore.ts`에 `ForgeAction`(`start`/`cancel`) · `applyForgeAction()`을
`applyCityAction()`과 같은 모양으로 추가했다. `routes.ts`에 `POST
/forge/order`(`{equipmentId}`) · `POST /forge/cancel`을 `/city/*`와 완전히
같은 골격(토큰 검증 → 판정 함수 → 400/결과)으로 붙였다. **지급/해제는
새 라우트가 필요 없다** — `PUT /profile`이 위 3-3의 경계로 그대로 받는다.

## 5. 클라이언트

- `packages/client/src/meta/city.ts`에 `startForgeOrderOnServer` ·
  `cancelForgeOrderOnServer` 추가 — `buyMaterialsOnServer`와 같은 `post()`
  헬퍼를 재사용해 **못 닿으면 로컬로 안 물러나고 말만 한다.**
- `BuildingScreen.tsx`가 `building === 'forge'`일 때 새 `ForgeScreen.tsx`로
  위임한다(태학·농지·병원 셋은 여전히 자리표시자 — 이번 세션 범위 밖).
  `App.tsx`의 `BuildingScreen`에 `onChange={setProfile}`을 추가해 배선했다.
- `ForgeScreen.tsx` — 홈(요약 + 버튼 둘) · 제조(목록 또는 "제작 중..." +
  취소) · 지급 관리(보유 목록, 행마다 지급/해제) 셋을 한 파일 안에서
  `MarketScreen`처럼 갈랐다. 상세 모달은 `item.loreI18n?.[lang] ?? item.lore`
  패턴을 미리 배선했다 — 번역 자체(`[[equipment-lore-i18n-plan]]`)는 이번
  세션에 안 넣었지만, 나중에 엑셀에 언어 열이 붙어도 화면은 안 바뀐다.
  장수 선택 모달은 이미 다른 병기를 낀 장수 옆에 "교체된다"는 것을 미리
  보여준다.
- `packages/data/src/index.ts`의 `EquipmentData`에 `loreI18n?:
  Partial<Record<StoryLang, string>>`을 옵션 필드로 추가했다(추출기는 안
  건드림 — 항상 `undefined`, 다음 세션이 채울 자리).
- `buildingText.ts`의 대장간 현황 줄을 "지었으면 실제 형편(보유·지급 수),
  안 지었으면 소개"로 승격했다(`farm`·`hospital`과 같은 결).
- `style.css`에 `.frg-*` 접두사로 새 클래스(전역 이름 충돌 규칙을 따름).

## 6. 에셋 — `tools/build_blacksmith.py` (신설)

원본 파일명이 한글(`LV1_무기_대감도.png`)이라 화면 코드가 그대로 쓰기
번거로워서, **레벨·종류·이름 세 값으로 원본을 찾고 `equipment.json`의
로마자 `id`로 저장**하는 도구를 만들었다(매핑표를 손으로 한 벌 더 적지
않고 정본을 그대로 읽는다). 원본이 물건 하나를 평평한 배경 위에 놓은
사진이라(693×378) `build_market.py`의 아이콘과 달리 알파 경계상자로
자르지 않고 **비율만 유지한 채 폭을 줄인다.** `npm run blacksmith`로
등록했고 실행해 15장 전부 확인했다. 출력 폴더(`packages/client/public/
blacksmith/`)는 다른 웹용 축소 에셋과 같은 이유로 `.gitignore`에 추가했다
— 원본처럼 git에 없고 각자 로컬에서 굽는다.

  것까지만 확인한 것이라, 실제 플레이 확인은 남은 일이다.

## 8. 이번 세션 범위 밖으로 남긴 것

- 장비 효과를 실제 전투(`FORMULA.damage`, 베리어 관통)에 연결하는 것 —
  2026-09-07 세션이 이미 "엔진 연결 없음"으로 남겼고 `battlePower()`는
  의도적으로 장비를 안 본다(과금 이점 유지, 기획자 결정).
- `loreI18n` 실제 번역 데이터 — 별도 세션(`[[equipment-lore-i18n-plan]]`).
- 장수 상세 화면에 낀 장비 표시 — 요청에 없었다.
- 실제 로그인 흐름으로 대장간 화면 플레이 확인.
