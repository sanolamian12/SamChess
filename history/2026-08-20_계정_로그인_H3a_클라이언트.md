# 2026-08-20 — 계정·로그인 H3a: 클라이언트를 server-api에 붙인다

H3a의 서버 절반(`history/2026-08-20_계정_로그인_H3a.md`)에 이어진 세션. 클라이언트에
실제 Supabase 이메일 로그인을 붙이고, `storage.ts`를 서버 정본으로 바꾸고,
`Enlist.playerId`를 서버가 검증한 uid로 바꾸고, `?seat=N` 개발용 통로를 지웠다.
**H3a가 이걸로 끝났다** — 다음은 H3b(참가비·거절 군량 서버 재검증)다.

## 1. 설계안 — 확인받은 것

세션 시작에 두 가지를 물어 정했다.

- **이메일 확인은 지금은 끈다.** 회원가입 직후 곧바로 세션이 온다 — "메일함을
  확인하세요" 상태를 안 만든다. 실제 배포 전에 다시 켤 것.
- **게스트 진입은 없다 — 로그인이 필수다.** §5-89가 이미 "이메일로 통일한다"고
  정했었는데, "그럼 게스트는 남기나"가 빠져 있었다. AI 대전도 로그인 계정으로 돈다.

## 3. 결정 — 왜 그렇게 정했나

### `@supabase/supabase-js`를 안 쓴다

`server-api/src/auth.ts`가 이미 `fetch`로 직접 Supabase Auth REST를 부르고 있었다 —
같은 결로 클라이언트도 직접 부른다. Supabase Auth REST(로그인·회원가입·리프레시)는
엔드포인트 세 개뿐이라 손으로 감싸는 비용이 크지 않고, 이 저장소는 최소 의존성을
우선한다(CLAUDE.md).

### 세션은 `client.auth.token`(colyseus.js)이 실어 나른다

Colyseus의 매치메이크 요청(`joinOrCreate`)은 `client.auth.token`이 설정돼 있으면
`_authToken` 쿼리 파라미터로 자동으로 실어 보낸다(colyseus.js의 `Client.buildEndpoint`).
서버의 `static onAuth(token, options, context)`가 `context.token`으로 그 값을 받는다 —
Colyseus 자체 인증 모듈(`client.auth.signInWithEmailAndPassword` 등, 서버의
`/auth/register` 엔드포인트를 부른다)은 **안 쓴다** — 우리는 Supabase가 인증을 하고
Colyseus는 그 토큰을 검증만 한다. `client.auth.token = supabaseAccessToken`만 하면 된다.

### `BattleRoom`의 `onAuth`는 대기열이 예약한 좌석에는 안 걸린다

`matchMaker.reserveSeatFor(room, options, authData)`의 세 번째 인자로 인증 데이터를
직접 넣을 수 있다(`@colyseus/core`의 `MatchMaker.js` 확인). `QueueRoom`이 이미
`onAuth`로 검증한 uid를 그 자리에 실어 보내면, `BattleRoom.onJoin(client, options, auth)`
가 `client.auth`로 그 값을 그대로 받는다 — `reserveSeatFor`를 직접 호출하는 경로는
매치메이크 HTTP 요청이 아니라서 `callOnAuth`(정적 `onAuth`를 부르는 자리)를 안 지난다.
`BattleRoom.onAuth`는 개발용 고정 방(`?match=room`, 지금은 `smoke_online.ts` 전용)
직접 접속 경로에만 걸린다. 이중 검증(대기열에서 한 번, 대전 방에서 또 한 번)을
피하면서도 신원 확인은 끊기지 않는다.

## 4. 밟은 지뢰 — 넷

### ① CORS — `@fastify/cors`의 기본 `methods`가 `PUT`을 빠뜨렸다

`server-api`는 원래 서버 대 서버(smoke:account)로만 확인했어서 CORS를 안 붙이고
있었다. 클라이언트가 직접 부르게 되며 붙였는데, `origin: true`만 주고 `methods`를
안 정하면 이 서버에서는 `access-control-allow-methods: GET,HEAD,POST`로 잡혔다 —
`PUT`이 없다. 브라우저는 **프리플라이트(OPTIONS)는 204로 통과시키고, 진짜 PUT
요청은 보내지도 않고 조용히 막는다** — 서버 로그(Fastify의 요청 로거)에도 OPTIONS와
그 앞의 GET만 찍히고 PUT은 아예 안 보였다. `curl`로 Node `fetch`를 직접 쏘면
CORS를 검사하지 않으니 200이 왔다 — **브라우저에서만 재현되는 버그**라 처음엔
"저장 함수가 왜 조용히 실패하지"로 보였다. `methods: ['GET', 'PUT']`을 명시해 고쳤다.
→ **교훈: 브라우저 전용 실패(CORS)는 서버 대 서버 curl/fetch로는 절대 재현되지
않는다** — 재현하려면 진짜 브라우저(Playwright)로 확인해야 한다.

### ② 저장이 겹치면 도착 순서가 안 지켜진다 — 쓰기 큐로 고쳤다

`smoke_meta.ts`의 재설계 → 재성장 검사가 **간헐적으로** "Lv2로 다시 올렸는데
새로고침하면 Lv1"로 실패했다. 재현할 때마다 다른 지점에서 났다. 원인은 `saveProfile()`이
부르고 기다리지 않는 fire-and-forget이라, 클릭이 잦으면 `PUT`이 여러 개 동시에
날아간다는 것 — 이 환경에서 PUT 왕복이 관측상 400ms~2.8s로 크게 흔들렸는데(원인은
못 밝혔다, 아마 로컬 Node/Windows 네트워킹 스택), **네트워크는 보낸 순서대로
도착한다고 보장하지 않는다.** 늦게 보낸 것이 먼저 도착해 저장되면, 그 뒤에 도착하는
(먼저 보낸) 옛 값이 최신 상태를 덮어쓴다. `storage.ts`에 쓰기 큐(앞선 저장의 응답을
기다린 뒤에야 다음 저장의 요청을 시작한다)를 넣어 도착 순서를 보낸 순서와 같게 만들었다.
→ **교훈: "기다리지 않는 저장"을 여러 번 부를 수 있는 화면에서는, 저장 자체가
직렬화돼 있지 않으면 마지막으로 부른 것이 마지막으로 저장된다는 보장이 없다.**

### ③ 비동기 전환이 "마운트 때 상태가 이미 있다"는 가정을 깼다

군량 시간 충전(`App.tsx`)은 `useEffect(..., [])`로 마운트 때 한 번 `tick()`을 불러
`syncGrain()`을 돌리고, 그 뒤 1분마다 인터벌로 돈다. `loadProfile()`이 동기이던
시절엔 마운트 시점에 이미 `profile`이 채워져 있어 이 첫 `tick()`이 뜻을 가졌다.
비동기로 바뀌자 마운트 순간 `profile`은 아직 `null`이라 첫 `tick()`이 헛돌고,
다음은 1분 뒤다 — 로그인 직후 곧바로 도시 화면에 들어가면 "군량이 안 찬다"로
보였다(`smoke_meta.ts`의 "세 시간에 군량이 셋 안 찼다" 검사가 잡았다). 의존성 배열을
`[Boolean(profile)]`로 바꿔 프로필이 **처음 채워지는 순간에도** 한 번 더 돌게 했다.
→ **교훈: 동기 초기화를 비동기로 바꾸면, 그 초기화 순간에 기대어 "마운트 때 한 번"
도는 다른 effect들을 전부 다시 확인해야 한다.**

### ④ 스모크의 "새로고침"이 아직 안 끝난 저장을 끊을 수 있다

`smoke_meta.ts`의 `reenter()`(F5 흉내)가 액션 직후 곧바로 `page.goto()`를 부르면,
그 액션이 건 `saveProfile()`의 `PUT`이 아직 응답을 못 받았을 때 페이지 전환이 그
요청을 끊어 버릴 수 있다 — 실제 브라우저의 일반적인 동작이라 앱이 막을 일은
아니지만, "끝난 저장이 실제로 남는가"를 보려는 스모크에게는 문제였다(②의 쓰기
큐를 넣은 뒤에도 이 문제는 남았다 — 큐는 순서를 보장하지, 완료를 기다려 주지
않는다). `App.tsx`의 확인용 통로에 `window.__profile.flush()`(대기 중인 저장을 전부
기다리는 프라미스)를 더해, `reenter()`가 `page.goto()`보다 먼저 그것을 부르게 했다.
→ **참고: 이건 앱을 고친 게 아니라 스모크를 고친 것이다.** 실제 사용자가 F5를
누르는 순간과 저장이 겹치는 것 자체는 이 세션의 범위 밖으로 남겨 뒀다(웹앱 일반의
받아들이는 위험) — SPA 안의 화면 전환(React 상태)은 페이지를 안 새로 그리므로
저장이 안 끊긴다, 실제로 위험한 건 진짜 새로고침/탭 닫기뿐이다.

## 5. smoke_meta.ts — 1520줄 전체 재작성

옛 동기 `localStorage` 모델(`samchess.profile.v1`을 직접 읽고 쓰는 자리 10곳 이상)에
깊이 결합돼 있어 로그인 필수 전환과 함께 전체를 다시 짰다.

- **진짜 Supabase 계정을 자리마다 만든다** — 주인공 하나(Admin API로 만들고 UI로
  로그인) + 대기열 봇마다 하나씩(`QueueRoom.onAuth`가 토큰을 요구해서다). 끝나면
  전부 지운다.
- **`server-api`도 스모크 안에서 함께 띄운다** — 이미 떠 있으면 그 자리를 그대로 쓴다
  (`npm run server`/`npm run dev`와 같은 관용구).
- **로컬 조작 → 서버 API 직접 호출로.** 군량 리깅(`setGrain`)·카드 세팅·전적 시딩은
  전부 `GET/PUT /profile`을 직접 부르는 것으로 바뀌었다. **저장 형식 마이그레이션
  시뮬레이션(v1·v2)만은 다르다** — `PUT`은 항상 되접으므로 옛 형식을 DB에 남길 수
  없다. `packages/server-api/src/db.ts`의 `pool`로 **DB 행에 직접** 옛 형식 JSON을
  심어 "그 뒤로 한 번도 안 열어 본 진짜 옛 계정"을 흉내 낸다.
- **검증용 읽기는 `window.__profile.current`로.** 서버 GET을 매번 다시 부르는 대신
  화면이 지금 그리고 있는 React 상태를 그대로 읽는다 — 저장(비동기)을 기다릴 필요가
  없고 항상 화면과 같은 값이다. **서버에 실제로 남았는가**를 봐야 하는 자리(v1/v2
  되접기의 "저장까지 올라왔는가")만 `apiGet()`으로 서버를 직접 물었다.

## 7. 다음 세션 — H3b

**아직 설계안이 없다.** 참가비·거절 군량이 여전히 클라이언트 계산 그대로 `PUT`되므로,
지금은 API를 직접 호출하면 군량을 공짜로 채울 수 있다. AI 대전을 서버로 이관할지도
같이 정해야 한다(§5-61) — 범위가 크면 H1/H2/H3를 가른 것과 같은 이유로 더 쪼갤 것.
