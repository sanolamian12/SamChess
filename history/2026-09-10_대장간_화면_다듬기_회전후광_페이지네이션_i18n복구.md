## 1. 상세 패널 — 회전 후광이 가장 오래 걸렸다

### 1-1. 시행착오: 2D 스프라이트 시트는 CSS로 못 돌린다

처음 받은 후광 그림은 6×4(24프레임) 스프라이트 시트였다. `background-position-x`/
`-y`를 각각 애니메이션시켜 프레임을 넘기려 했더니:

- 회전이 아니라 **대각선으로 미끄러지는** 움직임이 나왔다(두 축을 따로
  돌리면 중간 프레임에서 두 좌표가 동시에 안 맞아떨어진다).
- 24개 키프레임을 전부 펼쳐 `animation-timing-function: steps(1)`로 스텝마다
  박아도 같은 증상이 재현됐다 — 격자 좌표 계산 자체가 근본적으로 CSS
  애니메이션 타이밍과 안 맞는 문제였다.
- 그리고 쌓는 순서 실수로 후광이 무기 위로 올라와 가려 버리기도 했다.

**해결은 그림 쪽에서 왔다** — 사용자가 24프레임 시트를 버리고 **낱장 이미지
한 장**(`lightEffect_lv{1..5}_{색}.png`)으로 다시 그려 줬고, 그걸 순수
`transform: rotate()` + `steps(N)`으로 돌리는 쪽으로 전략을 완전히 바꿨다.
회전각을 15°→5°→3°→최종 **2°**(`steps(180)`, 칸당 0.1s, 전체 주기 18s)까지
사용자가 여러 차례 실험적으로 좁혀 나갔다(`.frg-item-glow`, `style.css`).

### 1-2. 부수 버그 — 회전이 만든 가로 스크롤

정사각 그림이 45°대 각도로 회전하면 대각선이 상자 경계를 넘는 순간이 있는데,
`.frg-item-wrap`이 `overflow-y: auto`라 스펙상 `overflow-x`도 함께 클리핑
모드로 굳어 있어서, 그 넘친 부분이 가로 스크롤을 만들었다. `.frg-item-frame`
자체에 `overflow: hidden`을 걸어 해결했다 — 회전하는 요소는 **자기 상자에서
잘라야** 바깥이 안다.

### 1-3. 쌓는 순서와 색

최종 순서는 **액자(불투명 검정 캔버스) → 후광(회전) → 사진(진짜 알파
컷아웃)** — 액자가 맨 아래가 아니면 위의 것을 통째로 가리고, 사진이 맨
위가 아니면 후광이 아무리 밝아도 무기가 가려진다. `mix-blend-mode: lighten`도
한때 썼다가(사진 배경이 불투명 검정인 줄 알고 "새어 나오게" 하려던 용도),
사진이 진짜 알파 컷아웃이라는 게 밝혀지며(§2 참조) 필요 없어져 지웠다 —
지워야 무기가 후광 위에 **무조건** 그려진다는 게 더 명확해진다.

### 1-4. 레벨 배지·제목 정렬

- 왼쪽 위 레벨 배지를 텍스트(`Lv1`)에서 `level2.png` 5칸 스프라이트로
  바꿨다(`LevelBadge` 컴포넌트, `background-position-x`로 칸 선택).
- 제목 줄을 **레벨 배지(왼쪽) · 제목 명패(가운데) · 닫기 X(오른쪽)** 한
  줄에 놓고 셋의 세로 중심을 맞췄다(`.frg-item-titlebar`, 줄 높이를 배지
  높이로 고정해 각각 `top`을 절반씩 맞추는 방식).
- 제목 명패는 `chip_neutral.png`를 재사용하되, 공용판(`ui/chip-neutral.png`)은
  `chip_selected.png`와 짝을 맞추려고 일부러 트리밍을 안 해 둔 자산이라(
  `build_ui.py`의 `FRAME_NO_TRIM`) 좌우 여백이 낭비된다 — **대장간 전용
  트리밍판**(`nameplate.png`)을 `build_blacksmith.py`에 새 빌드 스텝으로
  추가해 해결했다(실측 크롭 박스, 원본에 있는 장식 점 아티팩트 때문에
  `getbbox()`를 못 쓰고 손으로 좌표를 쟀다).
- 명패 너비는 처음엔 `flex:1`(이름 길이 따라 변함)이었다가, "패널 폭의
  70%로 고정, 센터에"로 바뀌었다(`.frg-item-nameplate { width: 70% }`).

### 1-5. 방어구가 무기보다 커 보이던 문제 (1차 대응)

방어구 그림은 캔버스를 거의 다 채우는 형태가 많아 무기보다 훨씬 커
보였다 — `.frg-item-photo[data-kind="armor"] { transform: scale(.8) }`로
종류별 일괄 축소(§6에서 이 해법의 한계가 다시 드러난다).

## 2. 사진 알파 컷아웃 버그

품목 사진의 배경이 불투명 검정으로 보여서 `mix-blend-mode`로 우회하려던
중, 원본 픽셀을 직접 찍어 보니(`getpixel()`) 모서리 알파가 실제로는 0이었다
— **`build_blacksmith.py`가 `im.convert("RGB")`로 접으면서 진짜 알파
투명도를 스스로 지우고 있었다.** `.convert("RGBA")` + `optimize=True`로
바꿔 고쳤다. 사진이 진짜 알파 컷아웃이 되고 나서야 §1-3의 쌓는 순서(사진이
맨 위, 후광이 비쳐 보임)가 의미를 가졌다.

## 3. 엑셀 오탈자 정정 — `EQUIP_TEXT_FIXES`

`docs/*.xlsx`는 읽기 전용이라 엄심경("베리어(추가 HP) +3 — 회복되지
않는다")의 문구를 더 명확하게("HP+3 베리어, 회복되지 않음.") 고치려면
엑셀을 못 건드린다. 기존 `SKILL_TEXT_FIXES`/`SKILL_NAME_FIXES`(CLAUDE.md에
이미 지뢰로 적혀 있는 패턴)와 같은 자리에 `EQUIP_TEXT_FIXES`/
`apply_equip_text_fixes()`를 `tools/extract_data.py`에 새로 만들었다 —
원본이 나중에 갱신되면 이 정정이 스스로 "필요 없어졌다"고 알리는 것도
같은 결로 맞췄다. `npm run extract` 재실행 후 `equipment.json`의 해당
`text` 필드만 바뀐 것을 `git diff`로 확인했다.

## 4. 제작 목록 카드(`.frg-tile`) 재설계

손그림 목업을 따라 여러 라운드를 거쳤다:

1. 각 아이템에 `frame_item_list.png` 금테 액자 적용, 레벨 아이콘(`level2.png`)
   추가.
2. 후광도 상세 패널과 같은 그림을 쓰되 **정지 이미지**로(`.frg-tile-glow`,
   `animation` 없음 — `GlowLayer`가 `className`으로 애니메이션 여부를 가른다).
3. 카드를 감싸던 회색 라운드 패널을 걷어냈다 — 이제 틀은 금테 액자 하나뿐.
4. 액자 그림 자체가 캔버스 색을 짙은 회색 → 검정으로, 치수도 927×672 →
   940×691로 바뀌어서(사용자가 새 파일을 주며 언급 안 함) 좌표를 전부
   재실측했다 — **에셋이 바뀌면 치수도 같이 바뀔 수 있다는 걸 매번
   확인해야 한다.**
5. 이름표를 액자 안쪽에 겹쳐 얹었다가 → 액자 **아래** 별도 줄로 다시
   물렀다(첨부 이미지 그대로). 왼쪽 레벨 배지 + 오른쪽 나무 명패(같은
   `nameplate.png` 재사용, 금색 글자) 조합.

## 5. 페이지네이션과 안내 문구

`?forgeLevel=5` QA 오버라이드(§7)로 15종 전부를 띄워 보니 한 화면에 5줄이
안 담기는 구조였다. 요구사항 셋:

1. 레벨 3까지 보인 뒤 페이지를 나눈다 — 레벨을 3칸씩 묶어
   `Math.floor((unlockLevel - 1) / 3)`으로 페이지를 나누는 일반식을 썼다
   (대장간 만렙이 나중에 5보다 커져도 이 계산은 안 바뀐다).
2. 페이지 전환 단추(‹ 1/2 ›, `.frg-pager`) — 페이지가 하나뿐이면 아예 안
   그린다. 제작 목록 진입/재진입 때마다 1페이지로 리셋한다.
3. 만렙 전에는 카드 목록 아래 "대장간 레벨이 오르면 더 다양한 병기구
   제작이 가능합니다."를 목록 제목과 같은 `hint` 스타일로 추가 —
   `buildingById.get('forge').maxLevel`을 직접 읽어(하드코딩 안 함) 만렙
   여부를 판정한다.

## 6. 무기/방어구 크기 불일치 — 세 번째 라운드 만에 진짜 원인을 찾았다

`?forgeLevel=5`로 15종을 한 화면에 띄우자 방어구가 유독 커 보인다는 지적이
다시 나왔다(§1-5의 종류별 일괄 축소가 목록 카드에는 아직 없던 상태).

1. **1차**: `.frg-tile-photo[data-kind="armor"] { transform: scale(.8) }`
   (상세 패널과 같은 배율 재사용) — 레벨 1~3 페이지는 해결됐다.
2. **2차**: 레벨 4~5 페이지의 셋째 칸(수면탄두연환개·방천화극)만 여전히
   커 보였다. 실측(`PIL.Image.getbbox()`로 알파 경계상자 대 캔버스 비율
   계산)해 보니 방천화극(무기, 창날이 캔버스 세로 93.9%를 채움)은 종류별
   규칙이 아예 안 닿고, 수면탄두연환개(방어구)는 0.8배를 적용해도 여전히
   크다는 사용자 보고가 있어 — 상세 패널 주석이 이미 남겨 둔 자리
   (`data-item` 스코프 보정, "그래도 남으면 품목별로")를 목록 카드에도 열어
   `data-item="bang-cheon-hwa-geuk"`/`"su-myeon-tan-du-yeon-hwan-gae"`
   각각에 `scale(.7)`/`scale(.68)`을 추가했다.
3. **3차(진짜 원인)**: 사용자가 스크린샷으로 "이미지가 아니라 **액자
   자체**가 옆 칸보다 넓다"를 짚었다 — 이게 결정적이었다. `.frg-list`는
   `display: grid; grid-template-columns: repeat(3, 1fr)`인데, 그리드
   아이템(`.frg-tile`)의 기본 `min-width`가 `auto`라서 **안쪽 이름표
   글자(`white-space: nowrap`)의 최소 폭이 그 칸의 최소 크기를 강제**하고
   있었다. "수면탄두연환개"(7자, 가장 긴 이름)가 낀 3열이 넓어지면 **그
   열을 공유하는 다른 행**(레벨 5의 방천화극)까지 같이 넓어진 것 — 왜
   레벨 4·5 페이지(가장 긴 이름이 사는 페이지)에서만, 왜 3열에서만
   증상이 났는지 이걸로 전부 설명된다. `.frg-tile { min-width: 0 }` 한
   줄로 고쳤다 — 안쪽 이름표·명패는 이미 `min-width: 0`을 갖고 있었지만
   (`text-overflow: ellipsis`로 줄어들 수 있게), 그 조상인 그리드 아이템
   자체가 `auto`로 남아 있으면 그 축소가 그리드 폭 계산에 반영되지 않는다.

**교훈**: 종류별/품목별 이미지 배율은 진짜 필요한 보정이었지만(1·2차),
"프레임 자체가 넓다"는 관찰은 이미지 크기 문제가 아니라 **레이아웃
버그**였다 — 사용자의 시각적 지적이 정확했고, 두 라운드를 더 돌고서야
가장 근본적인 원인(그리드 열이 행을 공유한다)에 도달했다.

## 7. `?forgeLevel=5` — 화면 전용 QA 오버라이드

레벨 5의 15종 전체 레이아웃을 확인하고 싶다는 요청에, 기존 `?match=fast`
(`meta/matchmaking.ts`)와 같은 자리·같은 결로 만들었다:

```ts
const debugForgeLevel = Number(new URLSearchParams(location.search).get('forgeLevel'));
const debugProfile = debugForgeLevel > 0
  ? { ...profile, buildings: { ...profile.buildings, forge: debugForgeLevel } }
  : profile;
```

**진짜 `profile`은 안 건드린다** — 제작 시작(`startForgeOrderOnServer`)은
여전히 서버가 실제 프로필로 재검증하므로, 이 값으로 잠긴 레벨 이상을
실제로 살 수는 없다(화면만 5로 보이고 주문은 서버가 거절한다). 화면
표시(`forgeLevel(debugProfile)`)와 목록(`craftableEquipment(debugProfile)`)
네 자리만 이 값을 쓴다.

## 8. 사고: `git checkout --`이 미커밋 i18n 작업을 지웠다

### 8-1. 무슨 일이 있었나

`?forgeLevel=5` 관련 정리를 하다가 실수로 만든 i18n 편집을 되돌리려고
`git checkout -- packages/client/src/i18n/strings/`를 실행했다. 이 명령은
**strings 디렉터리 전체를 마지막 커밋(HEAD)으로 되돌린다** — 그런데 이
디렉터리에는 이번 세션(과 그 이전 세션) 내내 진행해 온 **미커밋** 대장간
관련 i18n 작업이 쌓여 있었다:

- `ko.json` — 대장간 요약 필드명 개편(`summary.owned/assigned/spare` →
  `summary.level/total/stock/assigned`), 제작 목록 제목, 취소 문구,
  지급 관리 문구, 상세 패널의 `effectLine`/`craft`/`weeksSuffix`/`gold`/
  `durationLabel` 키 전체, `forge.kind.weapon/armor`, 완성 팝업 문구 등 —
  **커밋(`82d4a29`)에는 초기 버전만 있었고, 그 뒤 최소 7번의 편집 라운드가
  전부 미커밋 상태였다.**
- 나머지 9개 언어(en/es_419/it/ja/mn/pt_BR/pt_PT/zh_Hans/zh_Hant) — 대장간
  관련 문자열이 **단 하나도 커밋되어 있지 않았다**(전량 미커밋).

`git checkout --`는 스테이징 안 된 워킹트리 변경을 git object로 저장하지
않고 그냥 버린다 — 리플레이(reflog)로도 못 찾는다. 실제로 `git show
HEAD:...en.json | grep -c "forge\."`가 0을 찍으면서 사고를 확인했다.

### 8-2. 복구 — 세션 트랜스크립트를 되감았다

이 CLI 세션의 대화 기록(`~/.claude/projects/.../*.jsonl`, 이번 세션은
3만 줄대)에는 지금까지 실행한 모든 도구 호출(Edit의 `old_string`/
`new_string`, Bash로 실행한 Python 스크립트 원문, 그 실행 결과)이 순서대로
남아 있다. 이걸 이용해 두 갈래로 복구했다:

1. **`ko.json`**: 이 세션에서 `ko.json`을 직접 고친 `Edit` 호출 7건을
   트랜스크립트에서 찾아 `old_string`/`new_string`을 추출하고, 커밋
   `82d4a29`의 `ko.json`(즉 각 Edit이 적용되기 **전** 상태)에 **그 순서
   그대로 텍스트 치환을 재생**했다. 중간에 낀 3건의 Bash 정규식 스크립트
   (전체 언어 순회, `effectTagged` 문구 단순화·`priceTagged` 제거·
   `weeksSuffix` "×" 접두어 추가)도 같은 방식으로 재생했다. 결과를 실제
   `git show HEAD:...`와 diff해서 **정확히 그 7+3건의 변경분만** 남는 것을
   확인했다 — 다른 어떤 것도 우연히 섞이지 않았다는 뜻이다.
2. **나머지 9개 언어**: 이번 세션에서 딱 두 번의 큰 번역 라운드로 만들어진
   것이었다 — (a) `officers.*`/`forge.*` 전체를 처음 채워 넣은 스크립트
   (첫 시도는 `"\n".join()`에 쉼표를 빠뜨려 JSON이 깨졌고, 그 자리에서
   `git checkout`으로 되돌린 뒤 `",\n".join()`으로 고쳐 재실행한 것까지
   트랜스크립트에 남아 있었다), (b) `priceTagged`/`effectTagged`/`kind.*`
   추가 라운드, (c) `effectLine`/`craft`/`weeksSuffix`/`gold`/
   `durationLabel`로 갈아 끼운 마지막 라운드. 이 세 스크립트를 원본 그대로
   찾아 순서대로 재생했다.

복구 뒤 `npm run typecheck`가 즉시 47건의 "키가 `StringKey`에 없다" 에러를
냈다가(복구 전 중간 상태 확인용) → 전량 복구 후 깨끗이 통과, `npm test`도
기존 무관 실패 1건을 제외하고 전부 통과하는 것으로 복구가 완결됐음을
확인했다. 이번 페이지네이션·안내 문구(`forge.craft.levelHint`/
`forge.craft.page`) 10개 언어분은 이 복구 위에 다시 추가했다.

### 8-3. 교훈

- **`git checkout --`은 미스테이징 변경을 git 오브젝트로 남기지 않고
  버린다** — reflog에도 없다. 여러 파일이 걸린 넓은 경로(`-- <디렉터리>`)에
  쓸 때는 그 안에 무엇이 미커밋 상태로 얼마나 쌓여 있는지 먼저
  `git status`/`git diff --stat`으로 반드시 확인한다. 이번 사고는 딱 한
  파일의 나쁜 편집을 되돌리려다 디렉터리 전체를 지운 경우였다 — 되돌릴
  범위를 그 한 파일로 좁혔으면 안 났을 사고다.
- **CLI 세션의 트랜스크립트(`~/.claude/projects/**/*.jsonl`)는 미커밋
  작업의 마지막 안전망이 될 수 있다** — Edit/Write/Bash 호출의 입력이
  전부 순서대로 남아 있어서, git이 못 지키는 워킹트리 변경도 "무엇을
  어떤 순서로 했는지"를 재구성해 복구할 수 있었다. 다만 이건 **최후
  수단**이지 정상적인 작업 방식이 아니다 — 애초에 지우지 않는 게 맞다.
- **번역처럼 "커밋 없이 여러 세션에 걸쳐 누적되는 작업"은 중간중간
  커밋해 두는 편이 안전하다** — 이번 사고 자체가 "미커밋 상태로 여러
  라운드가 쌓여 있었다"는 조건이 없었으면 애초에 일어나지 않았다.
